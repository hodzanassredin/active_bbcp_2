# 5. Сообщения вместо общих данных

## 5.1. Кассир у окошка

В главах 2–4 счета лежали в общих переменных, и каждый кассир менял их сам. Чем больше задач
трогает общие данные, тем больше надо думать: где точки переключения, какой монитор, в каком
порядке. В настоящем банке так не делают. Клиенты к сейфу не подходят: они встают в очередь к
окошку, отдают кассиру заявку и ждут ответа. Сейф открывает только кассир.

Так же можно устроить и программу. Счета принадлежат одной задаче — кассиру. Остальные задачи их не
видят, а шлют кассиру *сообщения*: «переведи 60 со счёта 0 на счёт 1». Кассир берёт заявки по
одной, исполняет и отвечает. Раз данные трогает одна задача, вопросов «кто ещё их меняет» нет, и
мониторы не нужны.

Сообщения передают по *каналу*. В библиотеке `Async` их три вида, и разница — в том, ждёт ли
отправитель:

| Вид | Создание | Отправитель | Получатель |
|---|---|---|---|
| встреча | `AsyncChan.NewChan()` | ждёт, пока получатель не возьмёт сообщение | ждёт сообщения |
| буфер на `n` мест | `AsyncChan.NewBuffer(n)` | ждёт, только если все места заняты | ждёт, если буфер пуст |
| почтовый ящик | `AsyncChan.NewMailbox()` | не ждёт никогда | ждёт, если ящик пуст |

*Встреча* похожа на передачу из рук в руки: оба должны оказаться у окошка одновременно. *Буфер* —
лоток на несколько бумаг: отправитель кладёт и уходит, пока лоток не полон; так быстрый отправитель
не убегает слишком далеко вперёд от медленного получателя. *Почтовый ящик* принимает всё и сразу;
отправитель никогда не ждёт, но и не узнаёт, сколько писем скопилось. Сообщение — расширение записи
`AsyncSelect.Msg`; отправка — `Send`, приём — `Recv`. Все три вида подробно описаны в разделах 2–4
руководства `Docu/ru/Async.md`, примеры — `ObxChan0`, `ObxChan1`, `ObxChan2`.

## 5.2. Пример

Окошко кассы — почтовый ящик `window`: клиент кладёт заявку и не ждёт, пока кассир освободится.
Ответ кассир возвращает по встрече `reply`, которую клиент приложил к заявке: клиент ждёт на ней,
пока кассир не ответит. Управляющий дожидается всех клиентов и кладёт в окошко `NIL` — знак, что
касса закрывается.

```
MODULE ObxBank5;
	IMPORT AsyncChan, AsyncSelect, Tasks, Console, Strings;

	CONST n = 3;

	TYPE
		Request = POINTER TO RECORD (AsyncSelect.Msg)
			from, to, sum: INTEGER;
			reply: AsyncChan.Chan	(* сюда кассир кладёт ответ *)
		END;
		Answer = POINTER TO RECORD (AsyncSelect.Msg) ok: BOOLEAN END;
		Cashier = POINTER TO RECORD (Tasks.Task) END;
		Client = POINTER TO RECORD (Tasks.Task) id, sum: INTEGER END;
		Manager = POINTER TO RECORD (Tasks.Task) END;

	VAR window: AsyncChan.Mailbox;	(* окошко кассы *)

	PROCEDURE Say (IN what: ARRAY OF CHAR; x: INTEGER);
		VAR s: ARRAY 16 OF CHAR;
	BEGIN
		Strings.IntToString(x, s);
		Console.WriteStr(what); Console.WriteStr(s); Console.WriteLn
	END Say;

	(* Счета принадлежат кассиру: их видит только эта задача *)
	PROCEDURE (c: Cashier) Run;
		VAR balance: ARRAY n OF INTEGER; m: AsyncSelect.Msg; a: Answer; i, total: INTEGER;
	BEGIN
		balance[0] := 100; balance[1] := 100; balance[2] := 100;
		LOOP
			window.Recv(m);
			IF m = NIL THEN EXIT END;	(* касса закрывается *)
			WITH m: Request DO
				NEW(a); a.ok := balance[m.from] >= m.sum;
				IF a.ok THEN
					balance[m.from] := balance[m.from] - m.sum;
					balance[m.to] := balance[m.to] + m.sum
				END;
				m.reply.Send(a)
			END
		END;
		total := 0;
		FOR i := 0 TO n - 1 DO Say("balance ", balance[i]); total := total + balance[i] END;
		Say("total ", total)
	END Run;

	PROCEDURE (c: Client) Run;
		VAR r: Request; m: AsyncSelect.Msg;
	BEGIN
		NEW(r); r.from := c.id; r.to := (c.id + 1) MOD n; r.sum := c.sum;
		r.reply := AsyncChan.NewChan();
		window.Send(r);
		r.reply.Recv(m);
		IF m(Answer).ok THEN Say("done, client ", c.id) ELSE Say("refused, client ", c.id) END
	END Run;

	PROCEDURE (m: Manager) Run;
		VAR c: ARRAY n OF Client; i: INTEGER;
	BEGIN
		FOR i := 0 TO n - 1 DO
			NEW(c[i]); c[i].id := i; c[i].sum := 60 + 40 * i;
			IF i = 2 THEN c[i].sum := 250 END;	(* столько нет ни на одном счёте *)
			Tasks.Start(c[i])
		END;
		FOR i := 0 TO n - 1 DO Tasks.Join(c[i]) END;
		window.Send(NIL)	(* закрыть кассу *)
	END Run;

	PROCEDURE Do*;
		VAR k: Cashier; m: Manager;
	BEGIN
		window := AsyncChan.NewMailbox();
		NEW(k); Tasks.Start(k); NEW(m); Tasks.Start(m);
		WHILE Tasks.Count() > 0 DO Tasks.Step END
	END Do;

END ObxBank5.
```

Команда печатает:

```
done, client 0
done, client 1
refused, client 2
balance 40
balance 60
balance 200
total 300
```

Массив `balance` — локальная переменная задачи-кассира. До него просто нельзя добраться из другой
задачи, и это лучше любого правила «не трогай без монитора»: правило можно нарушить, а здесь
нарушать нечем. Заявки исполняются строго по одной, в порядке прихода в ящик, поэтому проверка
остатка и перевод неделимы, хотя ни монитора, ни транзакции нет.

## 5.3. Чем это хорошо и чем плохо

Хорошо то, что всё о счетах написано в одном месте — в `Cashier.Run`. Чтобы понять, может ли счёт
уйти в минус, достаточно прочитать один цикл. Плохо то, что кассир один: пока он исполняет заявку,
остальные ждут. Если заявок много, кассиров делают несколько, и счета делят между ними (счета
с чётными номерами — у первого, с нечётными — у второго). Перевод между счетами разных кассиров
снова становится разговором двух сторон; это та же беда, что у счетов на разных машинах (глава 8).

Сообщение дороже вызова процедуры. Обмен «туда и обратно» через две встречи стоит 389–483 нс, одно
сообщение через буфер на 64 места — 117–186 нс (Linux x86-64, одна нить, под нагрузкой;
`docs/measurements.md`, раздел 2.2). Для заявки в банк это незаметно; для сложения двух чисел —
слишком дорого.

## 5.4. Как это сломать

Если кассир забудет ответить на заявку — например, выйдет из цикла по ошибке, — клиент будет ждать
ответа вечно. Когда все задачи ждут и никто не спит со сроком, планировщик печатает тот же журнал
тупика, что в главе 3, только без мониторов: `Tasks: deadlock: no ready tasks and no wake-up
deadlines`. Такой журнал появится и в примере, если команда `Do` будет сама дожидаться клиентов и
только потом класть `NIL` в окошко: после последнего ответа кассир ждёт заявку, других задач нет, и
шаг планировщика объявит тупик раньше, чем команда закроет кассу. Поэтому кассу закрывает задача
`Manager`.

Вторая ошибка — неверный порядок разговора: клиент шлёт «перевод» до «представиться», или шлёт
две заявки, не дождавшись ответа на первую. Ошибка проявится у кассира, далеко от места, где её
сделали. Поэтому к каналу можно прикрепить *протокол* — автомат состояний, записанный строкой:

```
start: Hello > talk; talk: Data > talk; talk: Bye > done; done:
```

Канал проверяет каждое отправленное сообщение по протоколу и трапует при неверном шаге прямо у
отправителя. Как это устроено — раздел 6 руководства `Docu/ru/Async.md` и пример `ObxProto0`.

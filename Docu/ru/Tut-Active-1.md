# 1. Зачем это нужно

## 1.1. Окно, которое не отвечает

Бухгалтер нажимает кнопку «Пересчитать проценты по всем счетам». Счетов сто тысяч, на каждый уходит
немного времени, всего — полминуты. Если команда кнопки просто пройдёт циклом по всем счетам, эти
полминуты окно BlackBox не отвечает: не перерисовывается, не принимает щелчков, кнопку «Отмена»
нажать нельзя. Бухгалтер думает, что программа зависла.

Причина в том, как BlackBox обслуживает окно. У него один *главный цикл*: он берёт у операционной
системы очередное событие (щелчок, нажатие клавиши, просьбу перерисовать окно), вызывает его
обработчик, ждёт, пока обработчик вернётся, и берёт следующее. Всё это делает одна нить
операционной системы. Пока обработчик считает проценты, до следующего события дело не доходит.

Выход один: разбить долгую работу на куски и между кусками возвращать управление главному циклу. В
BlackBox для этого с самого начала есть *действие* (`Services.Action`). В этой ветке есть
ещё *задача* (`Tasks.Task`). Обе вещи решают одну беду, но пишутся по-разному, и эта глава о
том, в чём разница.

## 1.2. Действие

Действие — объект с методом `Do`. Его ставят в очередь вызовом `Services.DoLater(a, срок)`, и
главный цикл, когда до действия дойдёт очередь, вызывает `a.Do` — один раз. Если работа не
кончена, `Do` сам ставит себя в очередь снова. Между вызовами главный цикл успевает обработать
события окна.

Отсюда три свойства действия. Своего стека у действия нет: `Do` — обычная процедура, она начинается
с первой строки и обязана вернуться. Ждать посреди работы нельзя: если `Do` остановится, остановится
весь главный цикл. И место, где работа остановилась, программист хранит сам — в полях объекта.
Цикл «по всем счетам» превращается в «обработать счёт номер `a.i`, увеличить `a.i`, если ещё не
конец — поставить себя снова».

## 1.3. Задача

Задача — объект с методом `Run`, который пишут как обычную процедуру: цикл по счетам, внутри
работа. У задачи свой стек, поэтому она может остановиться посреди цикла и потом продолжить с того
же места: её локальные переменные и место в коде лежат на её стеке. Остановиться — значит вызвать
`Tasks.Yield` («уступи другим»), `Tasks.Sleep` («поспи столько-то миллисекунд») или другое ожидание
из следующих глав. Задачу запускают вызовом `Tasks.Start(t)`.

Задачи исполняет *планировщик* — само действие `Services`, которое главный цикл зовёт так же, как
все остальные. За один вызов планировщик даёт поработать готовым задачам, пока не кончится квант в
5 мс, и возвращает управление. Поэтому задачи и действия живут в одном главном цикле, на одной нити,
и окно остаётся живым, пока задачи работают. Подробности — в разделе 5 руководства
`Docu/ru/Tasks.md`.

## 1.4. Один пример в двух видах

Выписка по трём счетам: напечатать остаток каждого, но не все сразу, а по одному счёту за раз,
отдавая управление между ними. Модуль `ObxBank0` делает это дважды — действием и задачей:

```
MODULE ObxBank0;
	IMPORT Services, Tasks, Console, Strings;

	CONST n = 3;	(* число счетов *)

	TYPE
		Statement = POINTER TO RECORD (Services.Action) i: INTEGER END;
		StatementTask = POINTER TO RECORD (Tasks.Task) END;

	VAR balance: ARRAY n OF INTEGER; done: BOOLEAN;

	PROCEDURE Line (IN who: ARRAY OF CHAR; i: INTEGER);
		VAR s: ARRAY 16 OF CHAR;
	BEGIN
		Console.WriteStr(who); Console.WriteStr(": account ");
		Strings.IntToString(i, s); Console.WriteStr(s);
		Console.WriteStr(" balance "); Strings.IntToString(balance[i], s); Console.WriteStr(s);
		Console.WriteLn
	END Line;

	(* Действие: один счёт за вызов, место в работе хранит поле i *)
	PROCEDURE (a: Statement) Do;
	BEGIN
		Line("action", a.i);
		INC(a.i);
		IF a.i < n THEN Services.DoLater(a, Services.now) ELSE done := TRUE END
	END Do;

	(* Задача: обычный цикл, место в работе лежит на её стеке *)
	PROCEDURE (t: StatementTask) Run;
		VAR i: INTEGER;
	BEGIN
		FOR i := 0 TO n - 1 DO Line("task", i); Tasks.Yield END;
		done := TRUE
	END Run;

	PROCEDURE Do*;
		VAR a: Statement; t: StatementTask;
	BEGIN
		balance[0] := 100; balance[1] := 250; balance[2] := 40;
		NEW(a); a.i := 0; done := FALSE; Services.DoLater(a, Services.now);
		WHILE ~done DO Services.actionHook.Step END;
		NEW(t); done := FALSE; Tasks.Start(t);
		WHILE ~done DO Services.actionHook.Step END
	END Do;

END ObxBank0.
```

Команда печатает:

```
action: account 0 balance 100
action: account 1 balance 250
action: account 2 balance 40
task: account 0 balance 100
task: account 1 balance 250
task: account 2 balance 40
```

Результат одинаков, а тексты разные. Действию `Statement` понадобилось поле `i`: в нём хранится,
какой счёт следующий, и `Do` каждый раз начинает с начала, смотрит в поле и решает, что делать.
Задача `StatementTask` написана циклом `FOR`; переменная `i` локальная и переживает `Tasks.Yield`,
потому что лежит на стеке задачи.

Команда `Do` исполняется вне главного цикла — из консоли или коммандера — и поэтому крутит его сама
вызовом `Services.actionHook.Step`: один такой вызов — один проход главного цикла по готовым
действиям. Во втором цикле этот же вызов исполняет и задачу, потому что планировщик — тоже
действие. В окне BlackBox так делать не нужно: там главный цикл крутится сам.

На трёх счетах разница невелика. Она растёт вместе с алгоритмом. Пусть выписку нужно печатать по
отделениям, внутри отделения — по клиентам, а у клиента — по счетам, и после каждого счёта ждать,
пока принтер освободится. Задача остаётся тремя вложенными циклами с ожиданием внутри. Действие
превращается в автомат: поля «текущее отделение», «текущий клиент», «текущий счёт», «чего ждём», и
`Do` с ветвлением по ним. Программист сам делает работу, которую за задачу делает стек.

## 1.5. Что будет, если ждать в действии

Действие не может ждать, и это правило проверяется. Если `Do` вызовет `Tasks.Sleep`, программа
трапнет с номером 21 и текстом `Tasks: wait inside an action handler or domain broadcast`. Каркас
BlackBox рассчитывает, что обработчик события или действие исполнится до конца, прежде чем начнётся
следующее событие; остановленный посередине обработчик оставил бы каркас в недоделанном состоянии.
Действие, которое трапнуло в `Do`, главный цикл в очередь не возвращает — иначе сломанное действие
трапало бы на каждом проходе.

Задаче, наоборот, нельзя трогать окна и документы напрямую из своего `Run`, если для этого нужно
ждать посреди работы каркаса. Задача сделала свою часть, поставила действие, которое обновит окно,
и ждёт дальше у себя.

## 1.6. Когда что брать

| Нужно | Брать | Почему |
|---|---|---|
| Короткая работа «позже», один вызов | действие | ему не нужен свой стек; это дешевле задачи |
| Повторять что-то по таймеру, без ожиданий внутри | действие | `DoLater` со сроком и есть таймер |
| Работа из нескольких шагов с ожиданием между ними | задача | алгоритм пишется подряд, состояние на стеке |
| Много одновременных разговоров (клиенты, заявки) | задачи, по одной на разговор | у каждого разговора своё «где я остановился» |
| Обновить окно или документ | действие (из задачи — поставить его) | каркас рассчитывает на неделимые обработчики |
| Долгий счёт без ожиданий | задача с точками уступки или другая нить | глава 7 |

Правило такое: если в описании работы есть слово «ждать» — нужна задача. Если работа делается за
один короткий вызов — хватит действия.

## 1. Введение

Active Component Pascal — это Component Pascal с двумя добавлениями: исключающей процедурой и оператором
ожидания условия. Вместе они дают монитор в том виде, в каком его ввели Хоар и Бринч Хансен и в каком он
принят в языке Active Oberon: общие данные изменяются только под защитой, а задача, которой нечего
делать, ждёт, пока условие над этими данными не станет истинным.

Язык не добавляет зарезервированных слов. Исключающая процедура помечается системным флагом, оператор
ожидания — процедура псевдомодуля `ACTIVE`. Программа, которая не импортирует `ACTIVE`, остаётся
программой на Component Pascal: её текст, объектный код и символьный файл те же.

Процессы в этом сообщении называются задачами. Задача — не конструкция языка, а объект библиотечного
модуля `Tasks`. Сообщение описывает задачи лишь в той мере, в какой от них зависит смысл новых
конструкций.

Сообщение определяет язык. Оно не учебник и не описание библиотеки. Всё, что не сказано здесь, определено
«Сообщением о языке Component Pascal». Номера разделов без оговорки относятся к настоящему тексту.

Правило, которое компилятор не проверяет, помечено словами «Компилятор этого не проверяет». Такое правило —
соглашение: программа, нарушившая его, компилируется, но её поведение этим сообщением не определено.


## 2. Синтаксис

Синтаксис записан в расширенной форме Бэкуса — Наура, как в исходном сообщении. Сообщение меняет одно
правило и добавляет одно:

```
ProcDecl        =  PROCEDURE [SysFlag] [Receiver] IdentDef [FormalPars] MethAttributes
                   [";" DeclSeq [BEGIN StatementSeq] END ident].
SysFlag         =  "[" (ident | number) "]".
AwaitStatement  =  Qualident "(" Expression ")".
```

`AwaitStatement` — вызов процедуры, у которого `Qualident` обозначает `AWAIT` псевдомодуля `ACTIVE`
(`ACTIVE.AWAIT` или `A.AWAIT` при импорте `A := ACTIVE`). Он стоит там, где допустим оператор.

Системный флаг — средство платформы (приложение о модуле `SYSTEM`). Настоящее сообщение определяет одно
его значение — `exclusive`, числовая запись — `32`.


## 3. Словарь

`ACTIVE` — имя псевдомодуля. Модуль импортирует его обычным предложением `IMPORT ACTIVE`. Файла модуля
`ACTIVE` нет: его единственный объект, процедуру `AWAIT`, знает компилятор. В этом `ACTIVE` подобен модулю
`SYSTEM`.

`exclusive` — идентификатор системного флага. Он допустим только в модуле, который импортирует `ACTIVE`.

Импорт `ACTIVE` служит пометкой: модуль, в тексте которого есть это слово, рассчитан на исполнение
несколькими задачами.


## 4. Задачи

*Задача* — последовательное исполнение программы на собственном стеке. Задачу создаёт и запускает
библиотечный модуль `Tasks`; в каждый момент исполняется одна задача.

Исполняемая задача уступает процессор другой только в *точке переключения*. Точек переключения три рода:

1. вызов процедуры, которая по своему назначению приостанавливает задачу (`Tasks.Yield`, `Tasks.Sleep`,
   приём из канала и подобные);
2. вход в монитор, которым владеет другая задача (раздел 5.3), и оператор ожидания с ложным условием
   (раздел 6);
3. точка уступки в модуле, компилированном с ключом точек уступки (раздел 7).

Между двумя точками переключения задача исполняется неделимо по отношению к остальным задачам.
Последовательность операторов без точек переключения поэтому не нуждается в защите.

Программа исполняется также вне задач: тело модуля, команда, обработчик события среды. Такой код ведёт
себя как задача, которая никогда не ждёт. Оператор ожидания с ложным условием в нём — аварийное
завершение (раздел 8).


## 5. Исключающие процедуры

### 5.1. Синтаксис

Процедура, объявленная с флагом `exclusive`, называется *исключающей*.

```
PROCEDURE [exclusive] (b: Buffer) Put* (x: INTEGER), NEW;
PROCEDURE [exclusive] SetLevel* (x: INTEGER);
```

### 5.2. Монитор

С каждой исключающей процедурой связан *монитор* — объект, который в каждый момент принадлежит не более
чем одной задаче.

- Монитор метода — запись, обозначенная получателем. Разные записи одного типа — разные мониторы.
- Монитор процедуры уровня модуля — скрытая переменная модуля. Все исключающие процедуры одного
  модуля имеют общий монитор.

Монитором может быть любая запись; объявлять это в её типе не нужно.

### 5.3. Вход и выход

Вызов исключающей процедуры исполняется так:

1. Задача *входит* в монитор. Если монитор свободен, задача становится его владельцем. Если монитором
   владеет другая задача, вызывающая приостанавливается, пока монитор не будет передан ей (раздел 6.4).
2. Исполняется тело процедуры.
3. Задача *выходит* из монитора. Выход происходит при любом завершении тела: по достижении конца, по
   оператору `RETURN`, при аварийном завершении (раздел 8). Значение функции вычисляется до выхода.

Отсюда основное свойство: тела исключающих процедур одного монитора не исполняются вперемежку.
Утверждение о данных монитора, истинное при выходе из каждой такой процедуры и не нарушаемое вне их,
истинно при входе в каждую из них. Такое утверждение называют *инвариантом монитора*.

### 5.4. Повторный вход

Задача, владеющая монитором, может войти в него снова: вызвать другую исключающую процедуру того же
монитора или ту же самую рекурсивно. Такой вход не приостанавливает её. Монитор освобождается, когда число
выходов сравняется с числом входов.

### 5.5. Вложенные мониторы

Задача может владеть несколькими мониторами. Она выходит из них в порядке, обратном порядку входа;
вложенность вызовов обеспечивает этот порядок.

Две задачи, каждая из которых владеет одним монитором и ждёт входа в другой, не продолжатся никогда. Язык
этого не предотвращает. Программа избегает тупика, входя в мониторы в одном и том же порядке. Компилятор
этого не проверяет.

### 5.6. Ограничения

1. Флаг `exclusive` допустим только в модуле, который импортирует `ACTIVE`.
2. Исключающей может быть процедура, связанная с типом (метод), и процедура уровня модуля. Процедура,
   объявленная внутри другой процедуры, исключающей быть не может.
3. Флаг `exclusive` не сочетается с другими системными флагами.
4. Абстрактный метод может нести флаг, но кода у него нет. Процедура с пустым телом не входит в монитор и
   не выходит из него: её вызов не ждёт монитор.
5. Флаг относится к процедуре, а не к данным. Монитор не защищает поле записи, которое изменяется помимо
   её исключающих процедур. Экспорт поля для записи из другого модуля отменяет гарантию раздела 5.3.
   Компилятор этого не проверяет.
6. Флаг не входит в интерфейс: вызывающему безразлично, исключающая ли процедура. Метод, переопределяющий
   исключающий метод, сам исключающим не становится; ему нужен собственный флаг.

Нарушение правил 1–3 — ошибка компиляции (приложение B).


## 6. Ожидание условия

### 6.1. Синтаксис

```
ACTIVE.AWAIT(c)
```

`c` — выражение типа `BOOLEAN`, называемое *условием*.

### 6.2. Смысл

Если `c` истинно, оператор не делает ничего. Если `c` ложно, задача выходит из монитора своей процедуры и
приостанавливается. Она продолжается после оператора, когда одновременно выполнены два условия: `c`
истинно, и задача снова владеет монитором.

Следовательно, после оператора ожидания условие истинно. Повторная проверка в цикле, как при условных
переменных Хоара, не нужна.

```
PROCEDURE [exclusive] (b: Buffer) Get* (OUT x: INTEGER), NEW;
BEGIN
	ACTIVE.AWAIT(b.n > 0);
	x := b.a[b.out]; b.out := (b.out + 1) MOD LEN(b.a); DEC(b.n)
END Get;
```

Ожидание — точка переключения (раздел 4). Пока задача ждёт, монитором владеют другие. Поэтому инвариант
монитора истинен перед каждым оператором ожидания, как и перед выходом из процедуры. Компилятор этого не
проверяет.

Условие вычисляет не только ждущая задача, но и та, которая выходит из монитора (раздел 6.4). Локальные
переменные и параметры ждущей задачи доступны условию и сохраняют значения, которые имели в момент
ожидания.

`ACTIVE.AWAIT(TRUE)` — пустой оператор. `ACTIVE.AWAIT(FALSE)` приостанавливает задачу до её отмены
(раздел 8).

### 6.3. Передача монитора

Когда владелец выходит из монитора или начинает ждать, монитор передаётся так:

1. Условия ждущих задач вычисляются в порядке, в котором задачи начали ждать. Монитор получает первая
   задача, условие которой истинно; она становится готовой к исполнению.
2. Если такой задачи нет, монитор получает задача, которая раньше других приостановлена при входе.
3. Если нет и такой, монитор становится свободным.

Ждущая задача с истинным условием имеет преимущество перед входящими. Между моментом, когда условие
найдено истинным, и продолжением ждущей задачи ни одна другая задача монитором не владеет. Поэтому условие
не может стать ложным.

Ожидание освобождает только монитор той процедуры, в которой стоит оператор. Прочие мониторы задачи
остаются за ней на всё время ожидания. Если задача входила в монитор несколько раз (раздел 5.4), ожидание
освобождает его полностью, а при продолжении число входов восстанавливается.

### 6.4. Справедливость

Язык гарантирует порядок из раздела 6.3 и ничего сверх него. Задача, условие которой истинно лишь
временно, пока монитором владеет другая задача, может ждать бесконечно.

### 6.5. Ограничения

1. Оператор допустим только непосредственно в теле исключающей процедуры. Во вложенной в неё процедуре и в
   процедуре, которую она вызывает, он запрещён.
2. Аргумент ровно один. Он не имя типа и не имя процедуры, и его тип — `BOOLEAN`.
3. Условие не содержит вызовов процедур и присваиваний. Оно только читает.
4. Условие зависит лишь от данных, защищённых монитором, и от локальных переменных и параметров своей
   процедуры. Компилятор этого не проверяет. Условие над посторонними данными может стать истинным
   незаметно: ждущая задача продолжится лишь при следующем выходе какой-либо задачи из монитора.

Нарушение правил 1–3 — ошибка компиляции (приложение B).


## 7. Точки уступки

Задача, исполняющая длинный цикл без точек переключения, не даёт исполняться остальным. Модуль,
компилированный с ключом точек уступки (раздел 9.2), получает *точку уступки* в конце каждого повторения
операторов `WHILE`, `REPEAT`, `LOOP` и `FOR`. В точке уступки задача может уступить процессор.

Правила:

1. Задача, владеющая хотя бы одним монитором, в точке уступки не переключается. Внутри исключающей
   процедуры монитор отдаёт только оператор ожидания.
2. Код, исполняемый вне задачи, в точке уступки не переключается.
3. Ключ — свойство модуля, а не его интерфейса. Вызывающему неизвестно, есть ли в вызванной процедуре
   точки уступки.

В модуле, компилированном с ключом, неделимость из раздела 4 не действует: между двумя повторениями
цикла общие данные может изменить другая задача. Такой модуль защищает общие данные монитором.

Модули среды исполнения компилируются без ключа (раздел 9.2). Поэтому вызов процедуры среды из задачи
неделим.


## 8. Аварийное завершение

Аварийное завершение (трап) в задаче прекращает исполнение её процедур до ближайшего места, где оно
перехвачено. Если такого места нет, задача завершается. Остальные задачи продолжаются.

При аварийном завершении исключающей процедуры задача выходит из её монитора, как при обычном завершении.
Инвариант монитора при этом может быть нарушен; восстанавливает его программа. Компилятор этого не
проверяет.

Аварийное завершение вызывают:

- оператор ожидания с ложным условием вне задачи;
- ошибка при вычислении условия. Если условие вычисляла выходящая задача, аварийно завершается не она, а
  ждущая, которой условие принадлежит;
- отмена задачи. Отменённая задача аварийно завершается в ближайшей точке переключения, в том числе в
  операторе ожидания.

Тупик аварийного завершения не вызывает. Задача, условие которой никто не сделает истинным, ждёт. Когда
ждут все задачи, среда сообщает об этом и продолжает работу.

Номера трапов мониторов (модуль `Monitors`; перед трапом среда пишет в консоль строку «Kernel: <текст>»):

| Трап | Где | Причина |
|---:|---|---|
| 20 | вход | объект — `NIL` |
| 21 | вход | монитором владеет задача, а вызов исполняется вне задачи |
| 22 | выход, ожидание | монитор не у вызывающего |
| 23 | выход | мониторы отпускаются не в порядке, обратном входу |
| 24 | ожидание | ожидание вне задачи |
| 25 | ожидание | условие — `NIL` |
| 60 | ожидание | условие трапнуло при вычислении другой задачей; исходный номер — в консоли |
| 100 | аварийное завершение | цепочка взятий короче своей глубины (нарушен инвариант среды) |
| 127 | точка переключения | задача отменена (модуль `Tasks`) |

Трапы 22, 23 и 25 программа, составленная только из конструкций этого сообщения, не вызывает: их
порождают прямые вызовы `Kernel.Lock`, `Kernel.Unlock` и `Kernel.Await`.


## 9. Ограничения реализации

### 9.1. Платформа

1. Конструкции реализованы для процессоров x86 и AMD64. Импорт `ACTIVE` при другой цели даёт ошибку 151
   (`incorrect symbol file`); отдельного сообщения нет.
2. Все задачи исполняет одна нить операционной системы. Два оператора программы никогда не исполняются
   одновременно.
3. Модуль, код которого есть в кадре какого-либо стека, не выгружается. Вызов исключающей процедуры
   оставляет её кадр на стеке. Поэтому модуль, монитором которого владеют или входа в который ждут, тоже
   не выгружается; отдельной проверки таблицы мониторов при выгрузке нет.
4. Пустое тело и абстрактный метод не берут монитор (раздел 5.6, правило 4). Наблюдать это можно только
   по отсутствию ожидания при занятом мониторе.

### 9.2. Ключ компилятора

Ключ точек уступки — символ `^` после имени модуля в команде компиляции:

```
DevCompiler.CompileThis ObxLoop^
```

Тот же символ принимает строка параметров компилятора. Ключ не входит в текст модуля и в его символьный
файл.

Компилятор отвергает ключ у модуля среды исполнения (ошибка 225). Принадлежность модуля среде компилятор
определяет по имени. Модуль принадлежит среде, если его подсистема — часть имени до первой внутренней
заглавной буквы — одна из `System`, `Std`, `Text`, `Form`, `Host`, `Dev`, `Lin`, `Win`, или если он
входит в явный список модулей подсистемы `System`. Пользовательский модуль с таким префиксом ключ не
получит; модуль среды с другим именем его получит.


## Приложение A. Сводка синтаксиса

```
ProcDecl        =  PROCEDURE [SysFlag] [Receiver] IdentDef [FormalPars] MethAttributes
                   [";" DeclSeq [BEGIN StatementSeq] END ident].
SysFlag         =  "[" (ident | number) "]".
AwaitStatement  =  Qualident "(" Expression ")".
```

Ограничения контекста:

| Конструкция | Условие допустимости |
|---|---|
| `[exclusive]`, `[32]` | модуль импортирует `ACTIVE`; процедура объявлена на уровне модуля или связана с типом; других системных флагов нет |
| `ACTIVE.AWAIT(c)` | стоит непосредственно в теле исключающей процедуры; ровно один аргумент; `c` типа `BOOLEAN`, без вызовов и присваиваний |
| ключ `^` | имя модуля не принадлежит среде исполнения (раздел 9.2) |


## Приложение B. Отличия от Component Pascal

Приложение перечисляет всё, чем Active Component Pascal отличается от Component Pascal.

**Новые сущности языка.**

| Сущность | Вид | Раздел |
|---|---|---|
| `ACTIVE` | псевдомодуль, импортируется как `SYSTEM` | 3 |
| `ACTIVE.AWAIT(c)` | оператор ожидания условия | 6 |
| `[exclusive]` (`[32]`) | системный флаг процедуры | 5 |
| монитор | запись-получатель или скрытая переменная модуля | 5.2 |

**Ключ компилятора.** Символ `^` после имени модуля включает точки уступки (разделы 7 и 9.2). Без ключа
объектный код модуля тот же, что у Component Pascal.

**Ошибки компиляции.**

| Номер | Условие |
|---:|---|
| 120 | условие `ACTIVE.AWAIT` не типа `BOOLEAN` |
| 126 | аргумент `ACTIVE.AWAIT` — имя типа или процедуры |
| 151 | импорт `ACTIVE` при цели, отличной от x86 и AMD64 |
| 225 | `[exclusive]` в модуле без импорта `ACTIVE` |
| 225 | `[exclusive]` вместе с другим системным флагом |
| 225 | `[exclusive]` у процедуры, вложенной в другую процедуру |
| 225 | `ACTIVE.AWAIT` вне тела исключающей процедуры |
| 225 | вызов процедуры или присваивание в условии `ACTIVE.AWAIT` |
| 225 | ключ `^` у модуля среды исполнения |

Номера 120, 126, 151 и 225 — общие номера Component Pascal (`Dev/Rsrc/Errors.odc`): 120 — «type of
expression following IF, WHILE, UNTIL or ASSERT is not BOOLEAN», 126 — «this expression cannot be a type
or a procedure», 151 — «incorrect symbol file», 225 — «illegal sys flag». Отдельных сообщений для
расширения нет. Каждый случай проверяет набор
`Dev_dev/Reject` (`tools/check-reject.sh`).

**Скрытые сущности.** Компилятор порождает сущности, которых нет в тексте модуля и в его символьном файле:

- скрытую переменную модуля — монитор процедур уровня модуля (раздел 5.2);
- скрытую процедуру условия для каждого `ACTIVE.AWAIT`, вложенную в исключающую процедуру;
- скрытую локальную переменную с адресом кадра ждущей процедуры;
- скрытую область импорта `"$$"`, через которую идут вызовы ядра (приложение E).

**Правила-соглашения.** Компилятор не проверяет: порядок входа в мониторы (раздел 5.5), защиту полей
монитора (раздел 5.6, правило 5), инвариант перед ожиданием (раздел 6.2), зависимость условия только от
данных монитора (раздел 6.5, правило 4), восстановление инварианта после трапа (раздел 8).


## Приложение C. Отличия от Active Oberon

| Active Oberon | Active Component Pascal |
|---|---|
| блок `BEGIN {EXCLUSIVE} … END` | процедура с флагом `[exclusive]`; исключающего блока внутри процедуры нет |
| `AWAIT(c)` | `ACTIVE.AWAIT(c)`; условие без вызовов процедур и присваиваний |
| активный объект: тело `BEGIN {ACTIVE}` | нет; задачу создаёт модуль `Tasks` |
| повторный вход в свой монитор — ошибка | разрешён |
| ошибка в исключающем блоке оставляет монитор занятым | монитор освобождается |
| разделяемый доступ `{SHARED}` | нет |
| несколько процессоров | одна нить |


## Приложение D. Пример

Ограниченный буфер — классическая задача, на которой проверяют монитор. Производитель кладёт числа,
потребитель забирает; производитель ждёт, пока буфер полон, потребитель — пока пуст.

```
MODULE ObxBuffer;
	IMPORT ACTIVE;

	CONST N = 8;

	TYPE
		Buffer* = POINTER TO RECORD
			a: ARRAY N OF INTEGER;
			in, out, n: INTEGER	(* 0 <= n <= N; n элементов начиная с out *)
		END;

	PROCEDURE [exclusive] (b: Buffer) Put* (x: INTEGER), NEW;
	BEGIN
		ACTIVE.AWAIT(b.n < N);
		b.a[b.in] := x; b.in := (b.in + 1) MOD N; INC(b.n)
	END Put;

	PROCEDURE [exclusive] (b: Buffer) Get* (OUT x: INTEGER), NEW;
	BEGIN
		ACTIVE.AWAIT(b.n > 0);
		x := b.a[b.out]; b.out := (b.out + 1) MOD N; DEC(b.n)
	END Get;

END ObxBuffer.
```

Инвариант записан в комментарии к полям. Он истинен после `NEW`, каждая процедура сохраняет его, а поля
не экспортированы. По разделу 5.3 он истинен при каждом входе. Условие каждого оператора ожидания зависит
только от полей монитора, как требует раздел 6.5.


## Приложение E. Схема реализации

Приложение не определяет язык. Оно описывает перевод конструкций, чтобы читатель мог оценить их цену.

Исключающая процедура с непустым телом получает в начале вызов `Kernel.Lock(m)` и перед возвратом —
`Kernel.Unlock(m)`, где `m` — получатель или скрытая переменная модуля. Все операторы `RETURN` ведут к
одному месту выхода. У абстрактного метода и у процедуры с пустым телом этих вызовов нет.
Первый вход для данного объекта заводит запись монитора. Вход без соперников и выход берут записи
из свободных списков и памяти не выделяют; ожидание и вход в занятый монитор заводят записи
очередей.

Оператор ожидания переводится так:

```
@frm := SYSTEM.GETREG(BP);
IF ~c THEN Kernel.Await(P, @frm, m) END
```

`P` — скрытая процедура, вложенная в исключающую, с телом `RETURN c`. Ей передаётся адрес кадра ждущей
процедуры; через него условие читает её локальные переменные. Кадр существует на стеке ждущей задачи всё
время ожидания. Ядро вычисляет условие ещё раз в `Kernel.Await` через `Kernel.CallCond`, передавая кадр в
регистре `BX`. Отсюда оба ограничения раздела 6.5: условие вычисляет чужая задача, поэтому в нём нет
вызовов; кадр принадлежит одной процедуре, поэтому оператор стоит в её теле, а не во вложенной.

Вызовы ядра идут через скрытую область `"$$"`; загрузчик связывает её с `Kernel`. Поэтому модуль, не
использующий расширение, не получает лишнего импорта.

Монитор — не поле записи. Среда хранит сведения о занятых мониторах в таблице по адресу записи; запись о
мониторе существует, пока им владеют или его ждут. Свободный монитор не занимает записи в таблице:
она возвращается в свободный список.

Точка уступки — вызов `Kernel.Poll`. Он проверяет флаг, который планировщик поднимает каждые 5 мс, и
возвращается, если переключаться не нужно.

# Приложение B. Для тех, кто знает другие системы

Здесь соответствия для программиста, который уже писал на Go, Erlang, Active Oberon или
Concurrent ML. Соответствие приблизительное: похожая вещь служит той же цели, но правила у неё свои.
Общее отличие от всех четырёх одно: все задачи BlackBox исполняет одна нить ОС, без вытеснения.
Поэтому код между точками переключения неделим без замков, а параллельный счёт уходит в рабочие
нити и процессы (глава 7).

## B.1. Go

| Go | Здесь | Замечание |
|---|---|---|
| горутина, `go f()` | задача, `Tasks.Start(t)` | как Go с `GOMAXPROCS=1`, но без вытеснения: нужен `Yield` или точка уступки |
| `chan T` без буфера | встреча `AsyncChan.NewChan` | |
| `make(chan T, n)` | буфер `AsyncChan.NewBuffer(n)` | |
| — | почтовый ящик `AsyncChan.NewMailbox` | отправка не ждёт; в Go такого канала нет |
| `select` | `AsyncChan.Select` | из готовых побеждает первая по номеру, в Go — случайная |
| `time.After` в `select` | `AsyncChan.TimeoutAlt` | |
| `close(ch)` | нет; конец потока передают условным сообщением, например `NIL` | `ObxBank5` |
| `sync.Mutex` | исключающая процедура `[exclusive]` | замок связан с процедурой, а не берётся вручную |
| `sync.Cond` | `ACTIVE.AWAIT(условие)` | условие пишется прямо, без цикла `for !cond { Wait() }` |
| `context` с отменой | `Tasks.Cancel` | отмена — трап 127 в ближайшем ожидании |
| `errgroup` | группа `Tasks.NewGroup`, `StartIn` | провал участника отменяет остальных |
| `sync.WaitGroup` | `Tasks.Join` по каждой задаче или группа | |
| `sync/atomic` | не нужен: код между точками переключения неделим | |

Программист на Go узнает почти всё. Главное отличие — горутина без вызовов, которые ждут, в Go
рано или поздно будет вытеснена, а здесь задача держит нить до конца цикла. Обратная сторона того
же: гонок данных в смысле Go здесь не бывает. Цена операций сравнима с Go при одной нити: обмен
через две встречи в 2,1 раза дороже, создание задачи из пула — столько же (`docs/measurements.md`,
раздел 2.2).

## B.2. Erlang

| Erlang | Здесь | Замечание |
|---|---|---|
| процесс | задача | у задачи общий с другими адресное пространство; изоляцию соблюдает программист |
| почтовый ящик процесса | `AsyncChan.Mailbox`, который задача держит у себя | ящиков у задачи может быть несколько |
| `receive` с образцами | `Recv` берёт первое письмо; выбор по видам писем — `WITH` после приёма | выборочного приёма нет |
| `receive … after` | `Select` с `TimeoutAlt` | |
| `link`, выход по цепочке | группа задач | провал участника отменяет группу |
| супервизор, перезапуск | нет в этой ветке; надзор есть в ветке акторов | `docs/adr/0018-actors.md` |
| распределённые узлы | компутоны между процессами; акторы между машинами строятся | глава 8 |
| `gen_server` | задача-кассир с ящиком, ответ через однократную переменную | `ObxBank5`, `ObxBank6` |

Кассир главы 5 — это `gen_server` Erlang, записанный вручную. Отличие в том, что Erlang не даёт
процессу трогать чужие данные вовсе, а здесь это запрет по договорённости: память общая, и задача
может прочесть глобальную переменную модуля. Поэтому данные кассира делают локальными переменными
его `Run`, как в `ObxBank5`, — туда другая задача не дотянется. Подсистема акторов (Часть III)
сделает из этой договорённости правило.

## B.3. Active Oberon

| Active Oberon | Здесь | Замечание |
|---|---|---|
| активный объект, тело `BEGIN {ACTIVE}` | задача: запись `Tasks.Task` с методом `Run` | создаёт модуль `Tasks`, а не язык |
| блок `BEGIN {EXCLUSIVE} … END` | процедура с флагом `[exclusive]` | исключающего блока внутри процедуры нет |
| `AWAIT(c)` | `ACTIVE.AWAIT(c)` | та же схема: условия перепроверяет уходящий из монитора |
| повторный вход в свой монитор — ошибка | разрешён | |
| ошибка в исключающем блоке оставляет монитор занятым | монитор освобождается | |
| `{SHARED}` | нет | |
| несколько процессоров | одна нить | |

Тот, кто писал на Active Oberon, почувствует себя дома в главе 3: монитор и `AWAIT` здесь взяты
оттуда. Полное сравнение — приложение C сообщения о языке `Docu/ru/Active-CP-Lang.md`. Каналов,
выбора и транзакций в языке Active Oberon нет; здесь они в библиотеке `Async`.

## B.4. Concurrent ML и Hopac

Concurrent ML (CML, Джон Реппи) делает из события значение. `recvEvt ch` — не приём, а описание
приёма; его можно хранить, передавать и собирать с другими событиями: `choose [e1, e2]` — «одно из
двух», `wrap e f` — «когда случится `e`, применить к результату `f`», `guard g` — «перед ожиданием
вычислить событие заново», `withNack` — «если мою ветвь не выбрали, сообщить об этом».
`sync e` ждёт события. Hopac — то же самое для F#, с упором на скорость.

| CML, Hopac | Здесь | Замечание |
|---|---|---|
| `recvEvt`, `sendEvt` | `AsyncChan.RecvAlt`, `SendAlt` | заполняют запись `AsyncSelect.Op`, а не возвращают значение |
| `timeOutEvt` | `AsyncChan.TimeoutAlt` | |
| `choose` | массив альтернатив | один уровень; вложенного выбора нет |
| `sync` | `AsyncChan.Select(ops)` | возвращает номер, а не результат обработчика |
| `wrap` | `CASE` по номеру после `Select` | обработчик пишут после выбора, а не прикрепляют к событию |
| `guard` | код перед заполнением альтернатив | |
| `withNack` | `Signal.Disarm` у своего события | проигравшим альтернативам выбор сообщает сам |
| своё событие | расширение `AsyncSelect.Signal` | `AltSignal`; так устроен `AsyncComputon.AltPull` |
| `IVar` | `AsyncOnce.Once` | |
| `Mailbox` | `AsyncChan.Mailbox` | |

Внутри выбор устроен по образцу CML и Hopac: каждая альтернатива оставляет в канале *предложение*,
у всех предложений одного выбора общий флаг, выигравшее снимает флаг, проигравшие снимаются
(`docs/adr/0011-channels-on-offers.md`). Снаружи разница в том, что событий-значений нет:
альтернатива живёт только в одном вызове `Select`, её нельзя вернуть из процедуры и собрать из
неё новое событие. За это не платят выделением памяти на каждое событие, а выбор читается
как оператор `CASE`. Если нужна библиотека событий, которые складываются как в CML, её можно
построить поверх `AsyncSelect.Signal`; в этой ветке её нет.

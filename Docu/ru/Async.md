# Задачи, мониторы, `ACTIVE.AWAIT` и `[exclusive]`

Страница описывает расширения параллелизма этой сборки BlackBox:
задачи со своим стеком, мониторы на любом объекте и расширение
компилятора, которое делает типовые шаблоны короткими. Она написана
для программиста на Component Pascal; заметки о реализации порта —
в `docs/tasks.md` и в исходниках.

Реализация **кооперативная и однонитевая**: задачи переключаются
только в явных точках ожидания, каркас по-прежнему работает в
главной (единственной) нити ОС, вытеснения и параллельного
исполнения кода Component Pascal на общей куче нет.

## Задачи

Задача — расширяемая запись с методом `Run` и собственным стеком.

```
TYPE Worker = POINTER TO RECORD (Tasks.Task) n: INTEGER END;

PROCEDURE (w: Worker) Run;
BEGIN Tasks.Sleep(10); INC(w.n) END Run;

NEW(w); Tasks.SetName(w, "worker"); Tasks.Start(w)
```

Основные операции:

```
Tasks.Start(t);                    Tasks.StartIn(t, group);
Tasks.Yield;                       Tasks.Sleep(ms);
Tasks.Join(t);                     Tasks.Cancel(t);
Tasks.Park;                        Tasks.Unpark(t);
Tasks.Current();                   Tasks.InTask();
Tasks.State(t); Tasks.Failed(t);   Tasks.Deadlocked();
Tasks.SetStackSize(t, bytes);      Tasks.SetTimeSlice(t, ms);
Tasks.NewGroup(); Tasks.StartIn(t, g);
Tasks.Count(); Tasks.List();
```

Состояния: new, ready, running, sleeping, waiting, parked, finished,
cancelled. `Cancel` только ставит флаг; он проверяется в точках
ожидания (`Yield`, `Sleep`, `Join`, `Park`, ожидание монитора).
Отменённая задача получает обычный трап и раскручивается, поэтому
срабатывают уборщики и `Unlock`. Трап в одной задаче не трогает
остальные.

Память под стек выделяет ядро (`Kernel.AllocStack`, в Linux x64 —
`mmap` со сторожевой страницей) и освобождает после завершения
задачи. Размер по умолчанию — 256 КБ; страницы выделяются по
касанию.

## Мониторы

Монитор — запись побочной таблицы ядра по **адресу объекта**. Любой
объект может быть монитором; в заголовке записи места не нужно.
Запись живёт, пока объект занят или его ждут, затем удаляется.

```
Kernel.Lock(obj);                  (* войти в монитор *)
Kernel.Unlock(obj);                (* выйти *)
Kernel.Wait(obj);                  (* ручное ожидание *)
Kernel.Await(cond, frame, obj);    (* ожидание условия, см. ниже *)
```

Правила, как они реализованы:

- **Повторный вход разрешён** и считается. Одна задача может взять
  один монитор несколько раз; каждому `Lock` нужен `Unlock`.
- **Снятие — LIFO.** Задача отпускает мониторы в обратном порядке
  взятия. `Kernel.Unlock` монитора, который не является самым
  внутренним, трапает.
- `Lock` на мониторе, занятом другой задачей, усыпляет вызывающего
  до передачи монитора. Ждущий с истинным условием получает монитор
  **раньше** входящих, поэтому условие нельзя «перехватить» между
  проверкой и входом.
- `Unlock` последнего уровня вложенности передаёт монитор первому
  ждущему с истинным условием, иначе ждущему ручного `Wait`, иначе
  первому входящему, иначе освобождает запись.
- **Трап снимает мониторы.** Каждый `Lock` записывается в цепочку
  текущей задачи; `Kernel.Try` запоминает глубину цепочки на входе и
  при выходе или трапе снимает всё, взятое внутри. Это работает при
  вложенных `Try`: внешнее взятие переживает трап, пойманный
  внутренним `Try`.
- Сборщик мусора считает корнями объекты из таблицы мониторов и
  записи цепочек взятий.
- Для тестов и диагностики есть `Kernel.IsLocked(obj)`,
  `Kernel.MonitorCount()`, `Kernel.WaitersCount()` и
  `Kernel.DumpMonitors`.

Без загруженного `Tasks` ядро всё равно берёт и отдаёт свободные
мониторы, но ожидание — трап: **будить задачу некому**.

`Kernel.Wait` отпускает монитор и усыпляет вызывающего. Программа
обязана перепроверять условие в цикле:

```
Kernel.Lock(b);
WHILE b.count = 0 DO Kernel.Wait(b) END;
x := b.item; DEC(b.count);
Kernel.Unlock(b)
```

### Ожидание условия: `Kernel.Await`

`Kernel.Await(cond, frame, obj)` реализует схему Мюллера/Active
Oberon. `cond` — процедура типа
`PROCEDURE (frame: SYSTEM.ADDRESS): BOOLEAN`; `frame` — кадр ждущей
процедуры, поэтому условие читает локальные переменные и поля через
статическую связь. Ждущая задача регистрирует `(cond, frame)` у
монитора и спит.

Уходящая из монитора задача (`Unlock` или собственный `Await`)
перевычисляет условия ждущих **в их кадрах**. Первый ждущий с
истинным условием получает монитор вместе с владением и будится;
новые входящие ждут за ним.

Подробности:

- Компилятор проверяет условие сам и зовёт ядро только при `FALSE`;
  ручной вызов может вычислить его напрямую (процедуре условия
  уровня модуля кадр не нужен).
- `Await` без владения монитором трапает, как и `Wait` вне задачи.
- Трап при вычислении условия в чужой задаче **переадресуется**
  ждущей: её `Await` печатает
  `Kernel: Await: trap N in the condition` и поднимает трап 121.
- `Await` отпускает только монитор из `obj`. Остальные взятые
  мониторы остаются у задачи; это может привести к тупику, и журнал
  тупика показывает цепочку.
- Повторный вход через ожидание сохраняется: счётчик вложенности
  запоминается и восстанавливается.

## Где ждать нельзя

Ожидание — трап в таких контекстах:

- вне задачи (`Tasks.Current() = NIL`);
- в обработчике действия (`Services.Action.Do`), кроме собственного
  планировщика задач;
- в рассылке по домену (`Models.InDomainCast`).

Проверки делает `Tasks.CheckWait`; `Kernel.Wait`/`Await` сами
сообщают «wait outside a task».

Правило: **задача ждёт только в своём коде**, не в обратном вызове
каркаса. Код каркаса атомарен относительно других задач; задача
говорит с каркасом через действия и цикл событий.

### Журнал тупика

Когда у планировщика нет готовых задач, нет спящих со сроком и
остались живые задачи, `Tasks.Step` один раз печатает:

```
Tasks: deadlock: no ready tasks and no wake-up deadlines
Kernel: monitor dump
  monitor 7F...: held by "t1" count=1
    enters "t2"
  ...
```

`Tasks.Deadlocked()` сообщает состояние тестам. Журнал — диагностика,
а не фатальная ошибка: последующий `Tasks.Unpark` или `Cancel` может
дать прогресс. Задача, которая никогда не уступает, не
обнаруживается.

## Расширение компилятора (этап 6)

Следующий синтаксис и проверки — часть языкового расширения этой
ветки; среда исполнения для них — `Kernel`:

```
MODULE CtlPump;
	IMPORT ACTIVE;
	VAR level: INTEGER; running: BOOLEAN;

	PROCEDURE [exclusive] SetLevel* (x: INTEGER);
	BEGIN level := x END SetLevel;

	PROCEDURE [exclusive] WaitLow* (limit: INTEGER);
	BEGIN ACTIVE.AWAIT(level < limit) END WaitLow;
END CtlPump.
```

`ACTIVE` — псевдомодуль, встроенный в компилятор, как `SYSTEM`.
`IMPORT ACTIVE` помечает модуль, использующий задачи; импорт легко
найти по тексту. `SYSTEM` остаётся чистым.

### `[exclusive]`

- Разрешён у методов (`PROCEDURE [exclusive] (r: T) M`) и у процедур
  верхнего уровня модуля (монитор модуля). Запрещён у локальных
  процедур, вместе с `[code]`/`[ccall]` и без `IMPORT ACTIVE`.
- Пролог зовёт `Kernel.Lock` с получателем (метод) или со скрытым
  объектом-монитором модуля (процедура верхнего уровня). Монитор
  модуля — скрытая глобальная переменная, создаваемая до тела
  модуля; все `[exclusive]`-процедуры модуля взаимно исключают друг
  друга.
- Все выходы — каждый `RETURN`, естественное завершение, результат
  функции любого вида — идут через один эпилог с `Kernel.Unlock`.
  Трап снимает монитор через цепочку `Kernel.Try`.
- Повторный вход в свой монитор разрешён и считается.
- Флаг не пишется в символьный файл: вызывающему он не нужен.
- Выгрузка модуля с занятым или ожидаемым монитором запрещена, как и
  выгрузка модуля с кадрами на стеке задачи.

### `ACTIVE.AWAIT`

- Только внутри `[exclusive]`-процедуры или метода; в остальных
  местах — ошибка компиляции.
- Аргумент — выражение `BOOLEAN`. Компилятор проверяет его и зовёт
  `Kernel.Await` только при `FALSE`.
- Выражение **только для чтения**: можно читать переменные и поля,
  но нельзя вызывать процедуры и иметь побочные эффекты (проверяет
  компилятор). Условие вычисляется позже, в кадре ждущей задачи,
  возможно, пока другая задача уходит из монитора.
- Раскрытие: условие становится скрытой вложенной процедурой
  `@awaitN (frame: ADDRESS): BOOLEAN` с телом `RETURN cond`; оператор
  становится

  ```
  SYSTEM.GETREG(BP, @frm);          (* кадр ждущего *)
  IF ~cond THEN Kernel.Await(@awaitN, @frm, monitor) END
  ```

  Условие читает переменные ждущего через статическую связь CP:
  `Kernel.CallCond` зовёт `@awaitN`, положив `@frm` в `BX`, а кадр
  жив на стеке ждущего, пока задача спит. Если условие читает только
  глобальные переменные модуля, кадр всё равно передаётся так же.
- Компилятор вычисляет условие один раз до вызова; ядро вычисляет
  его ещё раз в `Await` перед засыпанием, а уходящая задача — в
  `Unlock` (`FindCondition`), как в Active Oberon. Монитор получает
  только ждущий с истинным условием и раньше новых входящих.

### Точки уступки

Необязательный ключ компиляции модуля вставляет вызов
`Kernel.Poll` на обратном переходе `WHILE`, `REPEAT`, `LOOP` и
`FOR`. Ключ — символ `^` после имени модуля:

```sh
echo 'DevCompiler64.CompileThis Test64Yield ^' | ./dev0Linux
```

Ключ — опция модуля; в символьный файл он не попадает, поэтому
вызывающему не нужно знать, есть ли у вызываемой процедуры точки
уступки.

- `Poll` уступает, только если планировщик поднял флаг, текущий
  стек — задача и задача не держит монитор. Внутри `[exclusive]`
  переключиться может только явный `ACTIVE.AWAIT`, поэтому монитор —
  граница целостной правки.
- Планировщик (`Tasks.Step`) поднимает флаг не чаще, чем раз в
  `pollPeriod` (5 мс); уступивший `Poll` флаг сбрасывает. Отменённая
  задача трапает на `Poll`, который действительно уступает, — ключ
  добавляет и точки отмены.
- Модули каркаса (System, Std, Text, Form, Host, Dev, платформенные
  Lin/Win) нельзя компилировать с ключом: компилятор отвергает опцию
  ошибкой. Вызов каркаса из задачи атомарен относительно других
  задач.
- Ключ реализован только для цели AMD64; 32-битный компилятор его
  отвергает.
- Вытеснения по сигналу нет; ключ — единственная неявная точка
  уступки, и код с ним обязан защищать общие данные.

## Примеры

### Ограниченный буфер на ручном API ядра

```
TYPE Buffer = POINTER TO RECORD
	item: ARRAY 8 OF INTEGER; head, tail, count: INTEGER
END;

PROCEDURE Put (b: Buffer; x: INTEGER);
BEGIN
	Kernel.Lock(b);
	WHILE b.count = 8 DO Kernel.Wait(b) END;
	b.item[b.tail] := x; b.tail := (b.tail + 1) MOD 8; INC(b.count);
	Kernel.Unlock(b)
END Put;

PROCEDURE Get (b: Buffer; VAR x: INTEGER);
BEGIN
	Kernel.Lock(b);
	WHILE b.count = 0 DO Kernel.Wait(b) END;
	x := b.item[b.head]; b.head := (b.head + 1) MOD 8; DEC(b.count);
	Kernel.Unlock(b)
END Get;
```

`Put` и `Get` — обычные процедуры; несколько производителей и
потребителей могут звать их из задач. Монитор — сам объект `Buffer`.

### Ограниченный буфер с `ACTIVE`

```
PROCEDURE [exclusive] (b: Buffer) Put* (x: INTEGER);
BEGIN
	ACTIVE.AWAIT(b.count < 8);
	b.item[b.tail] := x; b.tail := (b.tail + 1) MOD 8; INC(b.count)
END Put;

PROCEDURE [exclusive] (b: Buffer) Get* (VAR x: INTEGER);
BEGIN
	ACTIVE.AWAIT(b.count > 0);
	x := b.item[b.head]; b.head := (b.head + 1) MOD 8; DEC(b.count)
END Get;
```

Пролог и эпилог берут и отдают `b`; `AWAIT` отпускает его на время
ожидания и входит обратно уже с монитором.

### Монитор модуля: управление насосом

`CtlPump` выше — синглтон: все `[exclusive]`-процедуры модуля
разделяют один монитор, а `AWAIT` читает глобальные переменные
модуля. Две задачи могут звать `SetLevel` и `WaitLow` без явного
`Lock`.

## Каналы и выбор (этап 7)

Необязательная подсистема `Async` написана на том же расширении
`[exclusive]`/`ACTIVE.AWAIT`. `AsyncOnce` — однократная переменная:

```
o := AsyncOnce.New();
o.FillInt(42);          (* ровно один раз; повторный Fill — трап *)
x := o.ReadInt();       (* ждёт заполнения *)
```

`AsyncChan` даёт встречу `Chan`, ограниченный `Buffer` и неограниченный
`Mailbox`:

```
c := AsyncChan.NewChan();  b := AsyncChan.NewBuffer(8);
m := AsyncChan.NewMailbox();
c.Send(msg); c.Recv(msg);          (* встреча *)
b.Send(msg); b.Recv(msg);          (* ограниченная очередь *)
m.Send(msg); m.Recv(msg);          (* ящик *)
```

Сообщение — `AsyncSelect.Msg`, указатель на расширяемую запись; приём
через `WITH`. После отправки сообщение не меняется (дисциплина
Clojure/Erlang).

`Select`/`Alt` устроен по образцу Hopac/CML: альтернативы — описания в
массиве, `Select` возвращает номер сработавшей:

```
VAR ops: ARRAY 3 OF AsyncSelect.Op;
AsyncChan.RecvAlt(a, ops[0]);
AsyncChan.RecvAlt(b, ops[1]);
AsyncChan.TimeoutAlt(100, ops[2]);
i := AsyncChan.Select(ops);
```

Каждое предложение оставляет в канале offer с общим флагом решения.
Первый готовый канал под своим монитором ставит флаг и будит задачу
через `Tasks.Unpark`; проигравшие предложения владелец снимает после
пробуждения (nack). Активный вклад отправителя откатывается, если
решение принял другой канал. `Select` можно звать только из задачи.

`Poller` (`System/Mod/Poller.cp`) хранит реестр дескрипторов; консольный
хост опрашивает stdin и зарегистрированные дескрипторы одним `poll`.
`AsyncIO` строит на `CommStreams` «читать или ждать» и «писать или
ждать»:

```
AsyncIO.Read(s, buf, beg, len, read);
AsyncIO.Write(s, buf, beg, len, written);
AsyncIO.Accept(l, s, timeout);
```

У `CommStreams.Stream`/`Listener` появился `Handle()`; `CommTCP__Lin`
возвращает сокет и переведён с `select` на `poll` (`fd_set` ограничен
1024 дескрипторами), очередь accept увеличена. При тысяче открытых
молчащих соединений процесс за 1 с тратит 7–50 мс процессорного
времени.

Проверки протокола канала по образцу Zonnon пока нет. `AsyncTask` из
фреймворка Ивана в снимке отсутствует; роль автомата играет
`Tasks.Task`, а мост — общий планировщик и `Select`/`Park`/`Join`.

## Рабочие нити ОС (этап 8)

`AsyncWork` исполняет блокирующие вызовы ОС в пуле pthread-нитей. Тело
нити — `[ccall]`-процедура над `[untagged]`-памятью: без `NEW`, без
`Kernel.Try`, без каркаса и журнала. Задания и результаты лежат в
статических слотах под pthread-мьютексом; о готовности нить пишет байт
в pipe, главный цикл видит его через `Poller` и будит задачу:

```
id := AsyncWork.Execute(S.ADR(SomeJob), S.ADDRESS(arg));  (* из задачи *)
status := AsyncWork.Result(id);
```

Есть задания `ReadFileJob`, `WriteFileJob`, `ResolveJob`
(`getaddrinfo`). `Kernel.EnterWorker`/`WorkerAllocs()` — отладочный
счётчик обращений к куче из рабочей нити. SIGINT/SIGTERM в нитях
закрыты. Пул — только Linux AMD64; Windows не сделан. Блокирующий
вызов прямо из задачи по-прежнему замораживает каркас — его нужно
уводить в рабочую нить.

## Компутоны (этап 9)

`AsyncComputon` повторяет интерфейс `RobustParallel`:

```
TYPE Computon* = POINTER TO ABSTRACT RECORD (Stores.Store) END;
     PROCEDURE (c: Computon) Do*, NEW, ABSTRACT;

AsyncComputon.Start(n);
AsyncComputon.Push(c, rank, tag);
r := AsyncComputon.Pull(rank, tag);    (* точка ожидания *)
AsyncComputon.Try(rank, tag, r);
AsyncComputon.Stop;
```

Компутон сериализуется через `Stores` и исполняется в отдельном
процессе BlackBox (своя куча и сборщик), поэтому `Do` может звать
`NEW`. Транспорт — `fork` + `exec` того же `blackbox-console`, три pipe
на исполнителя. Тип компутона должен реализовать
`Externalize`/`Internalize`.

`Pull` из задачи — точка ожидания (`Tasks.Sleep` с дедлайном),
а `AsyncComputon.AltPull` — альтернатива `Select`: выбор умеет ждать
результат компутона вместе с каналами и тайм-аутом. При
гибели исполнителя `Poller` видит EOF и запрос повторяется на живом;
трап в `Do` ловится в исполнителе и возвращается кодом (`Pull` даёт
`NIL`, `LastError()` — код). Замер: 12 компутонов на 1, 4 и 16
локальных процессах дают одинаковый результат; убитый `SIGKILL`
исполнитель повторяется за 414 мс.

MPI в этой среде нет (`mpicc`/`mpirun`/`libmpi` отсутствуют), поэтому
транспорт MPI не делался; интерфейс от транспорта не зависит.
TCP-транспорт тоже не сделан.

## Отличия от Active Oberon и ограничения

- Условие — процедура плюс кадр (схема Мюллера), а не замыкание;
  ждущие перепроверяют его в своих кадрах, поддержка замыканий в
  сборщике не нужна.
- В отличие от нативного ядра A2, трап внутри `[exclusive]` снимает
  монитор (через цепочку замков задачи).
- В отличие от A2, повторный вход в свой монитор разрешён и
  считается.
- `Unlock` и `Await` вычисляют условия ждущих; трап там
  переадресуется ждущему, а не бьёт уходящую задачу.
- Component Pascal исполняет одна нить ОС; параллельного CP-кода нет.
  Блокирующий вызов ОС можно увести в пул рабочих нитей этапа 8;
  вызов прямо из задачи по-прежнему замораживает все задачи и каркас.
- `Select`/`Alt`, каналы, `Once` и ожидание ввода-вывода — в
  необязательной подсистеме `Async` (этап 7), на `Tasks.Park`/
  `Unpark` и мониторах.

## Состояние

В этой ветке реализованы: задачи, стеки, планировщик, отмена,
группы, мониторы (`Lock`, `Unlock`, `Wait`, `Await`), снятие при
трапе, корни сборщика, журнал тупика, интеграция с циклом событий.

В этой ветке реализованы и возможности компилятора (этап 6):
псевдомодуль `ACTIVE`, `ACTIVE.AWAIT` со схемой условия Мюллера,
`[exclusive]` у методов и процедур верхнего уровня, мониторы модуля,
ключ точек уступки `^` и снятие замков при трапе через цепочку
`Kernel.Try`.

Реализовано в этой ветке (этап 7): `AsyncOnce`, `AsyncChan` (`Chan`,
`Buffer`, `Mailbox`), `AsyncSelect` (`Alt`/`Select` с предложениями,
nack и тайм-аутом), `Poller` и `AsyncIO`.

Реализовано (этап 8): `AsyncWork` (пул pthread, pipe результатов,
`getaddrinfo` и файловые задания), `LinThreads`, `LinNative`, счётчик
`Kernel.WorkerAllocs`.

Реализовано (этап 9): `AsyncComputon` (локальные процессы BlackBox
через pipe, `Push`/`Pull`/`Try`, повтор после гибели исполнителя,
ошибка `Do`). MPI- и TCP-транспорты не сделаны: MPI в системе нет.
Проверка протокола канала по образцу Zonnon не сделана.

### Замечания о реализации компилятора

- Точки входа ядра для сгенерированного кода (`Kernel.Lock`,
  `Unlock`, `Await`, `Poll`) лежат в скрытом импортируемом модуле
  `"$$"`; загрузчик подменяет его на `Kernel`, поэтому формат
  объектного файла и загрузчики не менялись.
- `[exclusive]` — обычный положительный флаг процедуры (32),
  допустимый только при `IMPORT ACTIVE` и только один. Нарушение —
  ошибка компиляции 225 («illegal sys flag»); условие не типа
  `BOOLEAN` — ошибка 120.
- Условие `AWAIT` может читать переменные, поля и элементы массивов,
  но не может вызывать процедуры и присваивать; компилятор отвергает
  `Ncall`/`Nassign` внутри условия.
- `tools/bootstrap.sh` дважды собирает всю подсистему `Dev` и
  проверяет, что второй проход побайтно совпадает с первым, кроме
  12-байтовой метки времени компиляции в каждом `.ocf`.
- Отказы компиляции проверяет `tools/check-reject.sh`.

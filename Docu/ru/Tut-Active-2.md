# 2. Первая задача

## 2.1. Кассиры и управляющий

В банке три счёта, на каждом по 100. Три кассира переводят деньги по кругу: первый — со счёта 0 на
счёт 1, второй — с 1 на 2, третий — с 2 на 0; каждый делает пять переводов своей суммой. Перевод,
на который не хватает денег, кассир отклоняет: счёт не должен уйти в минус. Управляющий ждёт, пока
все кассиры закончат, и проверяет кассу: сумма по счетам должна остаться 300. На стене висят часы —
задача, которая работает, пока её не остановят; управляющий останавливает их в конце дня.

Каждый участник — задача. Задачу описывают расширением записи `Tasks.Task` с методом `Run`:

```
MODULE ObxBank1;
	IMPORT Tasks, Console, Strings;

	CONST n = 3;

	TYPE
		Clerk = POINTER TO RECORD (Tasks.Task) from, to, sum: INTEGER END;
		Clock = POINTER TO RECORD (Tasks.Task) END;
		Manager = POINTER TO RECORD (Tasks.Task) END;

	VAR balance: ARRAY n OF INTEGER; refused: INTEGER; clock: Clock;

	PROCEDURE Total (): INTEGER;
		VAR i, s: INTEGER;
	BEGIN
		s := 0; FOR i := 0 TO n - 1 DO s := s + balance[i] END;
		RETURN s
	END Total;

	PROCEDURE Say (IN what: ARRAY OF CHAR; x: INTEGER);
		VAR s: ARRAY 16 OF CHAR;
	BEGIN
		Strings.IntToString(x, s);
		Console.WriteStr(what); Console.WriteStr(s); Console.WriteLn
	END Say;

	(* Перевод: проверка и обе записи без точки переключения между ними *)
	PROCEDURE Transfer (from, to, sum: INTEGER);
	BEGIN
		IF balance[from] >= sum THEN
			balance[from] := balance[from] - sum;
			balance[to] := balance[to] + sum
		ELSE
			INC(refused)
		END
	END Transfer;

	PROCEDURE (c: Clerk) Run;
		VAR i: INTEGER;
	BEGIN
		FOR i := 1 TO 5 DO Transfer(c.from, c.to, c.sum); Tasks.Yield END
	END Run;

	PROCEDURE (c: Clock) Run;
	BEGIN
		LOOP Tasks.Sleep(1000) END	(* «часы на стене»: работают, пока их не отменят *)
	END Run;

	PROCEDURE (m: Manager) Run;
		VAR g: Tasks.Group; c: ARRAY n OF Clerk; i: INTEGER;
	BEGIN
		g := Tasks.NewGroup();
		FOR i := 0 TO n - 1 DO
			NEW(c[i]); c[i].from := i; c[i].to := (i + 1) MOD n; c[i].sum := 40 + 30 * i;
			Tasks.StartIn(c[i], g)
		END;
		FOR i := 0 TO n - 1 DO Tasks.Join(c[i]) END;
		FOR i := 0 TO n - 1 DO Say("balance ", balance[i]) END;
		Say("refused ", refused);
		Say("total ", Total());
		Tasks.Cancel(clock)
	END Run;

	PROCEDURE Do*;
		VAR m: Manager;
	BEGIN
		balance[0] := 100; balance[1] := 100; balance[2] := 100; refused := 0;
		NEW(clock); Tasks.Start(clock);
		NEW(m); Tasks.Start(m);
		WHILE Tasks.Count() > 0 DO Tasks.Step END;
		Say("clock state ", Tasks.State(clock))
	END Do;

END ObxBank1.
```

Команда печатает:

```
balance 200
balance 20
balance 80
refused 3
total 300
Tasks: cancelled
clock state 7
```

## 2.2. Что здесь происходит

`Tasks.Start(t)` выделяет задаче стек и ставит её в очередь готовых. Сама задача начнёт работать,
когда до неё дойдёт планировщик. Команда `Do` исполняется вне задачи, поэтому сама крутит
планировщик: `Tasks.Step` — один его шаг, и цикл `WHILE Tasks.Count() > 0` идёт, пока живы задачи.
В окне BlackBox этот цикл не нужен (глава 1).

Управляющий создаёт *группу* (`Tasks.NewGroup`) и запускает кассиров в неё (`Tasks.StartIn`).
Группа связывает судьбы: если кассир трапнет, остальных кассиров группы отменят, а сам управляющий
не завершится, пока в группе есть живые. Подробно правила группы разобраны в разделе 4 руководства
`Docu/ru/Tasks.md` и в примере `ObxTasks3`.

`Tasks.Join(c[i])` — «дождаться, пока задача `c[i]` закончит». Управляющий засыпает в `Join` и
просыпается, когда кассир вышел из `Run`. Пока он спит, работают другие задачи.

`Tasks.Sleep(1000)` усыпляет часы на секунду. Спящая задача не тратит процессор: планировщик
разбудит её, когда наступит срок. Часы спят в бесконечном цикле, и без вмешательства цикл в `Do`
никогда бы не кончился. Управляющий зовёт `Tasks.Cancel(clock)`. Отмена — это просьба: она ставит
задаче флаг и будит её; задача замечает флаг в ближайшем ожидании и завершается трапом 127. Строку
`Tasks: cancelled` печатает эта отмена, состояние часов становится 7 (`Tasks.Cancelled`). Задача,
которая считает и нигде не ждёт, отмену не заметит, пока не дойдёт до ожидания.

## 2.3. Почему перевод не нуждается в замке

Посмотрите на процедуру `Transfer`. Она читает остаток, сравнивает его с суммой, уменьшает один
счёт и увеличивает другой. Три кассира работают «одновременно», и в обычной многонитевой программе
это опасно: нить могут прервать между проверкой и списанием, другая нить спишет с того же счёта, и
счёт уйдёт в минус. Поэтому в Java или C# такой перевод закрывают замком.

Здесь замок не нужен. Все задачи исполняет одна нить, и задачу никто не прерывает: она отдаёт
процессор сама и только в известных местах. Эти места называются *точками переключения*:

1. вызов `Tasks.Yield`, `Sleep`, `Park` или `Join`;
2. вход в монитор, который держит другая задача, и `ACTIVE.AWAIT` с ложным условием (глава 3);
3. ожидание в канале, выборе, однократной переменной (главы 5 и 6);
4. точка уступки в модуле, скомпилированном с ключом `^` (глава 7).

Всё, что задача делает между двумя точками переключения, другие задачи видят как одно неделимое
действие. В `Transfer` точек переключения нет, поэтому проверка и обе записи происходят «разом». Итог
`total 300` и отсутствие минусов — не удача, а следствие этого правила при любом числе запусков.

Кассир зовёт `Tasks.Yield` после каждого перевода — уступает очередь другим кассирам. Без этого
первый кассир сделал бы все пять переводов подряд; результат остался бы верным, но кассиры работали
бы по очереди, а не вперемежку.

## 2.4. Как это сломать

Перенесите `Tasks.Yield` внутрь перевода — между проверкой и списанием:

```
IF balance[from] >= sum THEN
	Tasks.Yield;	(* точка переключения посреди перевода *)
	balance[from] := balance[from] - sum;
```

Теперь между проверкой «денег хватает» и списанием другой кассир успевает снять со счёта свою сумму,
и остаток может стать отрицательным. Компилятор этого не заметит. На практике `Yield` редко
ставят посреди перевода намеренно; чаще ожидание прячется внутри вызванной процедуры: записать в
журнал на диск, спросить подтверждение, отправить сообщение. Об этом следующая глава.

## 2.5. Цена

Задача дешёвая, но не бесплатная. Стек по умолчанию — 256 КБ адресного пространства; физическая
память выделяется по мере касания, поэтому тысячи задач помещаются в память без труда. Создание и
завершение задачи, когда стек берётся из пула, стоит 822–911 нс, переключение `Yield` между двумя
задачами — 84–113 нс (Linux x86-64, одна нить, машина под нагрузкой; `docs/measurements.md`,
раздел 2). Значит, задачу заводят на каждый разговор с клиентом или на каждую заявку, а не на
каждое сложение.

Все задачи исполняет одна нить, поэтому задачи не ускоряют счёт на многоядерной машине. Они
делают программу отзывчивой и позволяют писать ожидание прямым текстом. Как считать на нескольких
ядрах, рассказывает глава 7.

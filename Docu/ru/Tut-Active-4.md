# 4. Транзакции

## 4.1. Деньги, которые пропали

Кассир переводит 50 со счёта 0 на счёт 2. Он уже списал деньги со счёта 0 и тут обнаруживает, что
счёт 2 арестован: зачислять на него нельзя. Программа трапает. Задача кассира погибает, а 50 уже
списаны и никуда не зачислены. Сумма по счетам уменьшилась — нарушено первое правило банка.

Монитор из главы 3 здесь бессилен: он не пускает чужие задачи, а беда случилась в своей. Можно,
конечно, переставить проверку перед списанием. В этом простом переводе — можно. Но в настоящей
программе между списанием и зачислением бывает много кода, и трап может случиться в любой его
строке: деление на ноль, выход за границу массива, `NIL`.

Нужна возможность сказать: «эти изменения либо делаются все, либо ни одно». В базах данных это
называется *транзакцией*. В этой ветке транзакции для данных в памяти даёт модуль `AsyncStm` (STM —
software transactional memory, транзакционная память).

## 4.2. Как пишется транзакция

Транзакция — объект-расширение `AsyncStm.Tx` с методом `Do`. Данные, которые транзакция умеет
откатывать, лежат в *транзакционных переменных*: `AsyncStm.IntVar`, `BoolVar`, `RealVar`, `RefVar`.
Значение читают методом `Get`, пишут — `Set`. Вызов `AsyncStm.Atomically(t)` исполняет `t.Do`.
Первая запись в переменную запоминает её прежнее значение в журнале; если `Do` трапнет,
`Atomically` вернёт все переменные к прежним значениям и передаст трап дальше с тем же номером.

Счета `ObxBank4` — три `IntVar`, признак ареста — `BoolVar`:

```
MODULE ObxBank4;
	IMPORT Tasks, AsyncStm, Console, Strings;

	CONST n = 3;

	TYPE
		Transfer = POINTER TO RECORD (AsyncStm.Tx) from, to, sum: INTEGER END;
		Either = POINTER TO RECORD (AsyncStm.Tx) first, second: Transfer END;
		Clerk = POINTER TO RECORD (Tasks.Task) END;
		Buyer = POINTER TO RECORD (Tasks.Task) END;
		Payroll = POINTER TO RECORD (Tasks.Task) END;

	VAR
		balance: ARRAY n OF AsyncStm.IntVar;
		frozen: AsyncStm.BoolVar;	(* счёт 2 арестован: зачислять на него нельзя *)

	PROCEDURE Show (IN what: ARRAY OF CHAR);
		VAR i, sum: INTEGER; s: ARRAY 16 OF CHAR;
	BEGIN
		Console.WriteStr(what); Console.WriteStr(":"); sum := 0;
		FOR i := 0 TO n - 1 DO
			Strings.IntToString(balance[i].Get(), s); Console.WriteStr(" "); Console.WriteStr(s);
			sum := sum + balance[i].Get()
		END;
		Strings.IntToString(sum, s); Console.WriteStr(", total "); Console.WriteStr(s); Console.WriteLn
	END Show;

	PROCEDURE (t: Transfer) Do;
		VAR from, to: AsyncStm.IntVar;
	BEGIN
		from := balance[t.from]; to := balance[t.to];
		IF from.Get() < t.sum THEN AsyncStm.Retry END;	(* ждать денег *)
		from.Set(from.Get() - t.sum);
		IF (t.to = 2) & frozen.Get() THEN HALT(30) END;	(* трап посреди перевода *)
		to.Set(to.Get() + t.sum)
	END Do;

	PROCEDURE (t: Either) Do;
	BEGIN
		AsyncStm.OrElse(t.first, t.second)	(* с первого счёта, а нет — со второго *)
	END Do;

	PROCEDURE NewTransfer (from, to, sum: INTEGER): Transfer;
		VAR t: Transfer;
	BEGIN
		NEW(t); t.from := from; t.to := to; t.sum := sum;
		RETURN t
	END NewTransfer;

	PROCEDURE (c: Clerk) Run;
	BEGIN
		AsyncStm.Atomically(NewTransfer(0, 2, 50))
	END Run;

	PROCEDURE (b: Buyer) Run;
		VAR t: Either;
	BEGIN
		NEW(t); t.first := NewTransfer(1, 0, 120); t.second := NewTransfer(2, 0, 120);
		AsyncStm.Atomically(t);
		Show("buyer paid 120")
	END Run;

	PROCEDURE (p: Payroll) Run;
	BEGIN
		Tasks.Sleep(10);
		balance[2].Set(balance[2].Get() + 100);
		Show("salary 100 to account 2")
	END Run;

	PROCEDURE Do*;
		VAR c: Clerk; b: Buyer; p: Payroll;
	BEGIN
		balance[0] := AsyncStm.NewInt(100); balance[1] := AsyncStm.NewInt(100);
		balance[2] := AsyncStm.NewInt(50); frozen := AsyncStm.NewBool(TRUE);
		Show("start");
		NEW(c); Tasks.Start(c);
		WHILE Tasks.Count() > 0 DO Tasks.Step END;
		IF Tasks.Failed(c) THEN Show("clerk trapped") END;
		NEW(b); NEW(p); Tasks.Start(b); Tasks.Start(p);
		WHILE Tasks.Count() > 0 DO Tasks.Step END
	END Do;

END ObxBank4.
```

Команда печатает:

```
start: 100 100 50, total 250
clerk trapped: 100 100 50, total 250
salary 100 to account 2: 100 100 150, total 350
buyer paid 120: 220 100 30, total 350
```

Вторая строка показывает откат. Кассир списал 50 со счёта 0 и трапнул на `HALT(30)`; задача
погибла (`Tasks.Failed(c)` истинно), но счёт 0 снова 100, и сумма та же.

## 4.3. Retry: подождать денег

В главе 3 ожидание денег писалось `ACTIVE.AWAIT(balance >= n)` внутри монитора. В транзакции то же
самое пишется `AsyncStm.Retry`: «продолжать рано». `Retry` откатывает всё, что транзакция успела
сделать, и усыпляет задачу, пока не изменится одна из переменных, которые транзакция прочитала.
Потом `Do` исполняется заново, с начала.

Разница с `AWAIT` в том, что условие может охватывать любые переменные, а не только данные одного
монитора. Транзакция сама запоминает, что она прочитала; программист не объявляет, кого ждать.

## 4.4. OrElse: с первого счёта, а нет — со второго

Покупатель хочет заплатить 120: со счёта 1, а если там не хватает — со счёта 2. Каждая попытка —
отдельная транзакция `Transfer`, и обе умеют `Retry`. `AsyncStm.OrElse(first, second)` исполняет
первую; если она сделала `Retry`, откатывает её записи и исполняет вторую. Если `Retry` сделали обе,
ждёт вся транзакция — пока не изменится переменная, прочитанная в любой из ветвей.

В примере на счёте 1 — 100, на счёте 2 — 50, обе ветви делают `Retry`, и покупатель засыпает.
Задача `Payroll` зачисляет 100 на счёт 2 обычной записью вне транзакции; запись будит покупателя.
Он пробует снова: первая ветвь опять `Retry`, вторая проходит. Покупатель заплатил со счёта 2, и на
нём осталось 30.

Транзакции складываются. `Atomically`, вызванный внутри другой транзакции, становится её частью: два
перевода в одном `Do` исполняются как одно целое, и трап во втором откатывает и первый. С мониторами
так не получится: две исключающие процедуры, вызванные подряд, — это два отдельных шага.

## 4.5. Чего нельзя внутри транзакции

Внутри `Do` нельзя ждать: `Tasks.Sleep`, `Yield`, ожидание в канале, вход в занятый монитор. Причина
в том, как устроена неделимость. Транзакция неделима потому, что внутри неё нет точек переключения;
если бы задача уснула посреди `Do`, другие увидели бы половину перевода. Поэтому ожидание внутри
транзакции трапует 25 с текстом `Tasks: wait inside an atomic section`, и записи откатываются.
Единственный способ подождать — `Retry`.

Второе правило: откатываются только транзакционные переменные. Вывод в консоль, запись в файл,
отправка сообщения, обычные поля объектов остаются сделанными, а при `Retry` повторяются при каждом
новом исполнении `Do`. Поэтому в транзакции читают и пишут только транзакционные переменные, а
внешние действия делают после `Atomically`, по результату. В примере `Show` стоит после
`Atomically`, а не внутри `Do`. Компилятор этого не проверяет. Остальные нарушения и их номера —
в разделе 8 руководства `Docu/ru/Async.md`.

## 4.6. Монитор или транзакция

| Положение | Брать |
|---|---|
| Данные одного объекта, короткие операции | монитор |
| Нужно ждать посреди работы (сверка, ответ, ввод) с занятыми данными | монитор; транзакция ждать не может |
| Изменение нескольких объектов разом, и трап не должен оставить половину | транзакция |
| Ждать условия над несколькими объектами | транзакция с `Retry` |
| «Сделать это, а если нельзя — то другое» | транзакция с `OrElse` |
| Важна каждая наносекунда | обычные поля между точками переключения (глава 2) |

Цена. Перевод «два чтения, две записи» транзакцией стоит 76–82 нс, исключающей процедурой — 62–72
нс, прямой записью в поля — не больше 1 нс (AMD64, одна нить, миллион переводов, машина под
нагрузкой; `docs/measurements.md`, раздел 11). Транзакция дороже монитора примерно на 10 нс; её
берут ради отката и ожидания по нескольким объектам, а не ради скорости.

Граница. Транзакция неделима только внутри одного процесса BlackBox: её держит одна нить без
вытеснения. Если счета лежат в разных процессах или на разных машинах, транзакции между ними нет;
как переводят деньги там, рассказывает глава 8.

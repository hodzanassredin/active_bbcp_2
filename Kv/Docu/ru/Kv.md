# Хранилище Kv

Программа ведёт журнал событий в файле: пишет запись, потом ещё одну, потом обновляет счётчик в начале
файла. Посреди записи пропадает питание. После включения в файле лежит половина записи и старый
счётчик, а программа не знает, где кончаются целые данные. Переписать файл целиком тоже не помогает:
питание может пропасть посреди перезаписи, и тогда нет ни старого файла, ни нового. Подсистема `Kv`
решает эту задачу для данных вида «ключ → значение»: каждое изменение либо целиком попадает на диск,
либо не попадает вовсе, и после любого сбоя база открывается в последнем зафиксированном состоянии.

`Kv` — встроенное упорядоченное хранилище с транзакциями. Устройство следует BoltDB и LMDB: B+-дерево
с копированием при записи, один писатель, читатели по снимку, две мета-страницы с контрольной суммой.
Журнала нет, восстановления при открытии нет, фоновой работы нет. Модули: `KvPages` — страница и её
байты, `KvStore` — файловый слой, `KvLin` — файл Linux, `KvFault` — хранилище в памяти со сбоями для
тестов, `KvTree` — дерево и курсор, `KvDb` — база и транзакции.

## 1. Первая база

Пример `ObxKv0` открывает файл, записывает четыре пары, читает одну и обходит диапазон ключей:

```
MODULE ObxKv0;
	IMPORT Console, KvStore, KvLin, KvDb;

	CONST path = "/tmp/obxkv0.db";

	VAR db: KvDb.Db;

	PROCEDURE Put (tx: KvDb.Tx; IN key, val: ARRAY OF CHAR);
	BEGIN
		tx.Put(KvDb.Str(key)^, KvDb.Str(val)^)
	END Put;

	PROCEDURE Show (c: KvDb.Cursor);
		VAR k, v: ARRAY 64 OF CHAR;
	BEGIN
		KvDb.ToStr(c.Key(), k); KvDb.ToStr(c.Val(), v);
		Console.WriteStr(k); Console.WriteStr(" = "); Console.WriteStr(v); Console.WriteLn
	END Show;

	PROCEDURE Do*;
		VAR s: KvStore.Store; tx: KvDb.Tx; c: KvDb.Cursor; res: INTEGER;
			v: KvDb.Bytes; str: ARRAY 64 OF CHAR;
	BEGIN
		KvLin.Delete(path);
		KvLin.Open(path, s, res); KvDb.Open(s, db, res);
		tx := db.Begin(TRUE);
		Put(tx, "fruit/apple", "red"); Put(tx, "fruit/banana", "yellow");
		Put(tx, "fruit/cherry", "dark red"); Put(tx, "veg/carrot", "orange");
		tx.Commit(res);
		tx := db.Begin(FALSE);
		IF tx.Get(KvDb.Str("fruit/banana")^, v) THEN
			KvDb.ToStr(v, str); Console.WriteStr("banana: "); Console.WriteStr(str); Console.WriteLn
		END;
		c := tx.Seek(KvDb.Str("fruit/b")^);
		WHILE c.Valid() & (c.Key()[0] = ORD("f")) DO Show(c); c.Next END;
		tx.Abort;
		db.Close; KvLin.Delete(path)
	END Do;

END ObxKv0.
```

Ключ и значение — массивы байтов, ключи упорядочены побайтно без знака. Строки в байты переводят
`KvDb.Str` и `KvDb.ToStr` (UTF-8). Всё чтение и изменение идёт внутри *транзакции*: `Begin(TRUE)`
открывает пишущую, `Begin(FALSE)` — читающую. Пишущая транзакция кончается `Commit` или `Abort`,
читающая — `Abort`. Курсор `Seek` встаёт на первый ключ, не меньший заданного; `Next` и `Prev` идут по
порядку ключей. Разбор вывода — на странице `Obx/Docu/ru/Kv0.md`.

Именованных таблиц нет. Данные разных видов разделяют префиксом ключа, как `fruit/` и `veg/` в примере:
префикс собирает ключи одного вида в непрерывный диапазон, и курсор обходит его от `Seek(префикс)`,
пока ключ начинается с префикса.

## 2. Страница и дерево

Файл базы — массив страниц по 4096 байтов (`KvPages.size`). Номер страницы 32-битный. Страницы 0 и 1 —
меты, остальные — узлы дерева, список свободных страниц или свободные.

Пары лежат в *B+-дереве*. Лист хранит пары по возрастанию ключа. Ветвь хранит пары «ключ, номер
страницы потомка»: ключ `keys[i]` — нижняя граница ключей потомка `i`. Поиск идёт от корня: в каждой
ветви двоичный поиск выбирает последнего потомка, граница которого не больше искомого ключа. При
тысячах пар на странице дерево из трёх уровней держит миллионы ключей, и поиск читает три страницы.

Узел, который не помещается в страницу, делится на куски. Обычно куски заполнены наполовину: тогда
вставка в середину не делит узел сразу снова. У журнала событий ключи растут, и вставка всегда идёт в
правый край; половинные куски оставили бы файл наполовину пустым. Поэтому узел у правого края дерева,
в конец которого дописывали, делится на почти полные куски (девять десятых страницы), как при
`FillPercent` в bolt. Значение больше страницы занимает *страницы продолжения*: узел из одного большого
элемента лежит на нескольких страницах подряд, а в заголовке первой записано их число.

Узел меньше четверти страницы при фиксации сливается с соседом. Слитый узел, ставший больше страницы,
снова делится. Так дерево не вырождается после удалений.

## 3. Копирование при записи

Транзакция не меняет ни одной страницы, которую видит кто-то ещё. Чтобы изменить лист, она делает его
копию в памяти; чтобы родитель указал на копию, она копирует и родителя, и так до корня. При фиксации
изменённые узлы записываются на свободные страницы, а старые становятся свободными. Вставка ключа `d`
в дерево с корнем на странице 5:

```
до:                              после:
     [5: a | m]                       [5: a | m]        [9: a | m]
      /       \                        /       \          /     \
[3: a b c]   [4: m x]           [3: a b c]  [4: m x]  [8: a b c d]  (4)

меты: 0 -> корень 5             меты: 1 -> корень 9; страницы 3 и 5 свободны,
                                когда их не видит ни один читатель
```

Новое дерево делит со старым всё, что не менялось (страница 4). Старое дерево остаётся целым до конца:
кто начал читать до фиксации, дочитает старое. Цена — запись всего пути от листа до корня на каждую
транзакцию; поэтому изменения выгодно собирать в одну транзакцию.

Внутри транзакции большой узел делится сразу, когда превысит две страницы, а не только при фиксации:
иначе сто тысяч вставок в одну транзакцию сдвигали бы элементы одного растущего листа.

## 4. Две меты и два Sync

Мета — это корень дерева, страница списка свободных, число страниц файла и номер транзакции, с
контрольной суммой CRC32. Транзакция с номером `txid` пишет мету в страницу `txid MOD 2`. Фиксация
идёт в четыре шага:

1. записать новые узлы и список свободных на свободные страницы;
2. `Sync` — дождаться, пока они дойдут до носителя;
3. записать мету в страницу `txid MOD 2`;
4. `Sync`.

Диск не обещает порядка: записи между двумя `Sync` могут дойти в любом порядке, частично, а страница —
наполовину. Шаг 2 гарантирует, что мета никогда не укажет на страницу, которой нет на носителе. Если
питание пропало до шага 3 или посреди него, вторая мета цела: она пишется в другую страницу. Открытие
читает обе меты, отбрасывает ту, чья контрольная сумма не сходится, и берёт оставшуюся с большим
номером. Шаг 4 нужен только для обещания «после `Commit` изменения переживут питание». Больше ничего
не требуется: на диске всегда лежит одно целое дерево, на которое указывает целая мета.

Если выбросить первый `Sync`, мета может дойти раньше страниц, и после сбоя база укажет на мусор. Тест
`Kv_devCrash` ловит это: он обрывает каждую запись и каждый `Sync` фиксации, выключает питание (всё
несинхронизированное пропадает целиком или по жребию) и требует, чтобы база была цела и равна
состоянию до или после транзакции.

Открытие не восстанавливает ничего. Номер транзакции 64-битный и только растёт.

## 5. Снимок читателя

Читающая транзакция запоминает мету на момент `Begin` и читает дерево её корня. Писатель не трогает
страницы этого дерева, поэтому читатель видит *снимок*: всё, что зафиксировано до его начала, и ничего
после. Читателей может быть сколько угодно, они не ждут писателя и друг друга. Пример `ObxKv1` открывает
читателя, дописывает 500 событий и показывает, что читатель по-прежнему видит 1000, а новый — 1500.

Писатель один. Если `Begin(TRUE)` зовёт другая задача, пока пишущая транзакция открыта, она ждёт
её конца. Ждущие задачи стоят в очереди по порядку прихода; отменённая ждущая задача уходит из
очереди с трапом 127. Если вторую пишущую открывает та же задача или код вне задачи — трап 21:
такое ожидание было бы вечным, а на главном стеке ждать нельзя.

Рекомендованный способ — `KvDb.Update(db, body, res)` и `KvDb.View(db, body)`. Тело — объект с
методом `Do(tx)`. `Update` исполняет тело и фиксирует; если тело упало трапом (или задачу отменили,
127), транзакция откатывается, и трап идёт дальше с тем же номером:

```
TYPE Add = POINTER TO RECORD (KvDb.Body) END;

PROCEDURE (a: Add) Do (tx: KvDb.Tx);
BEGIN
	tx.Put(KvDb.Str("k")^, KvDb.Str("v")^)
END Do;

...	NEW(add); KvDb.Update(db, add, res)
```

`Begin` остаётся для ручного управления. Нарушение с ценой: трап между `Begin` и `Commit` оставляет
транзакцию открытой. Компилятор и `Kv` этого не ловят. Открытая пишущая запирает базу: следующий
`Begin(TRUE)` этой задачи — трап 21, другие задачи ждут вечно. Открытая читающая держит страницы
(раздел 6). Тест `Kv_devTasks.TestUpdateTrapRollsBack` показывает, что `Update` эту цену снимает.

`Begin(TRUE)` — единственная точка переключения в `Kv`, и только когда приходится ждать. Внутри `Get`, `Put`, `Delete`, курсора и `Commit` нет точек переключения: ввод-вывод
синхронный. Задача, которая держит транзакцию, не уступает процессор посреди операции, но может
уступить между операциями; транзакция остаётся открытой. Долгий `Sync` останавливает все задачи —
так же, как любой блокирующий вызов ОС из задачи.

## 6. Свободные страницы

Страницу, которую освободила транзакция `w`, ещё видят читатели снимков с номером меньше `w`. Такая
страница ждёт в списке ожидающих с номером `w`. Когда пишущая транзакция начинается, ожидающие
страницы переходят в свободные, если у каждого открытого читателя номер снимка не меньше `w`. На диск
пишется общий список свободных и ожидающих: после открытия читателей нет.

Незакрытая читающая транзакция — нарушение с ценой. Компилятор и `Kv` его не ловят. Пока читатель жив,
все страницы, освобождённые после его начала, не используются, и файл растёт на путь от листа до корня
с каждой фиксацией. В тесте `Kv_devTree.TestReaderHoldsPages` сто фиксаций при открытом читателе
увеличивают файл больше чем на двадцать страниц; после `Abort` читателя файл перестаёт расти. Файл
не сжимается никогда: освобождённые страницы используются заново, но не отдаются ОС.

## 7. Ошибки и проверка

Ошибки среды возвращаются в `res`, как в `Files`: `ok`, `ioError`, `corrupt`. Ошибка чтения внутри
транзакции записывается в `tx.res`; после неё операции транзакции ничего не делают, а `Commit`
возвращает тот же код и откатывает транзакцию. Ошибка записи или `Sync` при фиксации оставляет базу
неисправной: каждая следующая транзакция получает тот же `res`, базу закрывают и открывают заново.
Обе испорченные меты — `Open` возвращает `corrupt`, без трапа.

Нарушение контракта — трап: 20 — транзакция закрыта, 21 — вторая пишущая той же задачи или вне задачи, изменение в читающей,
22 — ключ длиннее `KvTree.maxKey` (1024 байта) или курсор после изменения дерева. Пустой ключ и пустое
значение невозможны: массивов длины 0 в языке нет.

`tx.Check` проверяет снимок, с которого начата транзакция: ключи узлов возрастают и лежат в границах
родителя, все листья на одной глубине, и каждая страница файла — ровно одно из: мета, узел, список
свободных, свободная. Тесты зовут её после каждой фиксации; пользователь — после подозрительного сбоя.

## 8. Цена

Замеры — `docs/measurements.md`, раздел 13 «Хранилище Kv». На amd64 под нагрузкой машины около 20
одна пишущая транзакция вставляет около 25 тыс. ключей в секунду по порядку и около 9 тыс. вразброс;
случайный `Get` — около 40 тыс. в секунду: каждый узел пути декодируется из байтов страницы. Фиксация
с `fsync` стоит около 2 мс (540 в секунду на NVMe), без `fsync` — около 50 мкс. Поэтому мелкие
изменения выгодно собирать в одну транзакцию.

## 9. Границы и сравнение с LSM

Один писатель; файл не сжимается; долгий читатель держит страницы. Номер страницы 32-битный — до
16 ТБ. `mmap` нет: страницы читаются обычным чтением через кеш на 1024 узла, поэтому память ограничена,
а ошибки чтения — коды, а не сигналы. Подсистема собирается для amd64 и i386 под Linux; для Windows
нужен свой файловый слой.

LSM-дерево (LevelDB, RocksDB) пишет изменения в журнал и таблицу в памяти, а на диск — большими
отсортированными файлами, которые сливает фоновая работа. Запись у него дешевле: нет пути до корня на
каждую фиксацию, нет случайных записей. Чтение дороже: ключ ищут в нескольких уровнях. LSM лучше,
когда записей много больше, чем чтений, и данных больше памяти. B+-дерево с копированием при записи
проще, читает быстрее и не требует фоновой работы — в однонитевой системе задач это решает.

## 10. Интерфейс

```
DEFINITION KvDb;

	CONST
		ok = 0; ioError = 1; corrupt = 2;

	TYPE
		Body = POINTER TO ABSTRACT RECORD
			(b: Body) Do- (tx: Tx), NEW, ABSTRACT
		END;

		Bytes = KvPages.Bytes;
		Cursor = KvTree.Cursor;

		Db = POINTER TO RECORD
			(db: Db) Begin (write: BOOLEAN): Tx, NEW;
			(db: Db) Close, NEW;
			(db: Db) Pages (): INTEGER, NEW
		END;

		Tx = POINTER TO RECORD
			write-: BOOLEAN;
			res-: INTEGER;
			(tx: Tx) Abort, NEW;
			(tx: Tx) Check (OUT msg: ARRAY OF CHAR): BOOLEAN, NEW;
			(tx: Tx) Commit (OUT res: INTEGER), NEW;
			(tx: Tx) Delete (IN key: ARRAY OF BYTE): BOOLEAN, NEW;
			(tx: Tx) First (): Cursor, NEW;
			(tx: Tx) Get (IN key: ARRAY OF BYTE; OUT val: Bytes): BOOLEAN, NEW;
			(tx: Tx) Last (): Cursor, NEW;
			(tx: Tx) Put (IN key, val: ARRAY OF BYTE), NEW;
			(tx: Tx) Seek (IN from: ARRAY OF BYTE): Cursor, NEW
		END;

	PROCEDURE Open (s: KvStore.Store; OUT db: Db; OUT res: INTEGER);
	PROCEDURE Str (IN s: ARRAY OF CHAR): Bytes;
	PROCEDURE ToStr (IN b: ARRAY OF BYTE; OUT s: ARRAY OF CHAR);
	PROCEDURE Update (db: Db; body: Body; OUT res: INTEGER);
	PROCEDURE View (db: Db; body: Body);

END KvDb.
```

`Open` открывает базу в хранилище; пустое хранилище становится пустой базой.

```
Пред: s # NIL — 20
Пост: res = ok — db открыта; corrupt — нет целой меты или испорчен список свободных; иначе db = NIL
```

`db.Begin` начинает транзакцию над снимком последней фиксации.

```
Пред: база не закрыта — 20
Пред: write -> пишущую не держит эта же задача; вне задачи — пишущей нет — 21
Пост: транзакция открыта; после ошибки фиксации её res # ok
```

Пишущая из другой задачи ждёт по очереди прихода; отмена ждущей — трап 127.

`Update` открывает пишущую транзакцию, исполняет `body.Do` и фиксирует; `View` — то же с читающей.

```
Пред: как у Begin
Пост: тело кончилось — res = код Commit; трап тела — транзакция закрыта, трап передан с тем же номером
```

`db.Close` закрывает хранилище. `db.Pages` — число страниц последней фиксации.

```
Пред: открытых транзакций нет — 22
```

`tx.Get` ищет ключ.

```
Пред: транзакция открыта — 20
Пост: TRUE — ключ есть, val — копия значения; FALSE — ключа нет или ошибка среды (res # ok)
```

`tx.Put` связывает ключ с копией значения; `tx.Delete` удаляет ключ.

```
Пред: транзакция открыта — 20
Пред: транзакция пишущая — 21
Пред: LEN(key) <= KvTree.maxKey — 22 (только Put)
Пост: Delete = TRUE — ключ был и удалён
```

`tx.Seek`, `tx.First`, `tx.Last` дают курсор на первом ключе не меньше `from`, на наименьшем и на
наибольшем ключе. Курсор годен, пока транзакция открыта и не меняет данные.

```
Пред: транзакция открыта — 20
```

`tx.Commit` фиксирует и закрывает транзакцию; у читающей — то же, что `Abort`. `tx.Abort` закрывает
транзакцию без следа; повторный `Abort` ничего не делает.

```
Пред: транзакция открыта — 20 (Commit)
Пост: res = ok — изменения на носителе и видны новым транзакциям; иначе транзакция откачена
```

`tx.Check` проверяет снимок транзакции (инварианты `KvTree` 100–103).

```
Пред: транзакция открыта — 20
Пред: пишущая транзакция ещё ничего не меняла — 21
Пост: TRUE — снимок цел; FALSE — msg называет нарушение
```

Курсор (`KvTree.Cursor`): `Valid`, `Next`, `Prev`, `Key`, `Val`; `Key` и `Val` возвращают копии.

```
Пред: Valid() — 20 (Next, Prev, Key, Val)
Пред: дерево не менялось после создания курсора — 22
```

`Str` переводит строку в UTF-8 без нуля, `ToStr` — обратно, обрезая по `LEN(s)`.


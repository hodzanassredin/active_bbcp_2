# DevLinker1: план поддержки AMD64

Дата: 2026-11-07.

Статус: анализ исходников и предложение архитектуры. Реализация, компиляция и проверки не выполнялись. Документ сохранён для продолжения работы; перед реализацией нужно сверить упомянутые ограничения с актуальными исходниками.

> Обновление 2026-11-07: реализован отдельный путь Windows x64 — см. [LinkPeExe64](Linker1-Win64.md). Ниже сохранён исходный план для Linux ELF64; он остаётся отдельной задачей.

## Цель и рекомендуемый первый этап

Научить DevLinker1 собирать исполняемые файлы Linux AMD64 из OCF нового бэкенда. Начать с ELF executable с фиксированным размещением и действующими ограничениями низкой адресной арены. PIE, DLL, другие ОС и снятие ограничений адресного пространства оставить отдельными этапами.

DevLinker1 — управляющий модуль. Основная работа относится к DevLnkLoad, DevLnkBase, новому ELF64-writer и коду старта runtime. Замены ELF-заголовка недостаточно.

## 1. Отделить архитектуру цели от архитектуры линкера

Линкер должен иметь возможность собирать AMD64-файл, работая внутри 32-битного BlackBox. Поэтому адрес целевого образа нельзя представлять через SYSTEM.ADDRESS: этот тип зависит от платформы самого процесса линкера.

Предлагаемый тип:

```componentpascal
TYPE TargetAddress* = LONGINT;
```

| Значение | Представление |
|---|---|
| Виртуальный адрес секции, символа, база образа | TargetAddress |
| Индекс, количество, смещение в небольшом буфере | INTEGER |
| Адрес памяти процесса линкера | SYSTEM.ADDRESS |
| Fingerprint, код операции | INTEGER |

Пересмотреть Section.addr, ImageBase, opt.imageBase, SetAddr и GetBases. У Symbol.addr сейчас меняется смысл: сначала смещение, затем окончательный адрес. Лучше разделить эти значения явно. Размеры файлов и секций можно пока ограничить существующим Files API, но ограничение должно проверяться.

## 2. Добавить явный выбор AMD64

Возможный новый интерфейс (ещё не реализован):

```text
DevLinker1.LinkElfExe64 Linux BlackBox64 := ...
```

Выбор должен определять processor=12, pointerSize=8, ELF64-writer и AMD64-startup независимо от хостовой платформы.

DevLnkLoad.ReadHeader сейчас читает magic и processor без полноценной проверки. Проверять magic/поддерживаемый формат и архитектуру каждого OCF; запрещать смешение i386 и AMD64.

## 3. Читать целевую раскладку метаданных

DevLnkLoad содержит фиксированные смещения 32-битного Module и шаг 16 для ObjDesc. По текущим DevCPE, ядру и bbrun64 нужны следующие различия:

| Поле | i386 | AMD64 |
|---|---:|---:|
| Module.opts | 4 | 8 |
| Module.refcnt | 8 | 12 |
| Module.term | 40 | 48 |
| Module.names | 84 | 120 |
| Module.imports | 92 | 136 |
| Module.export | 96 | 144 |
| Размер ObjDesc | 16 | 24 |

Добавить Get8/Put8 и операции чтения/записи целевого адресного поля. Заголовок OCF, размеры секций и многие скалярные поля остаются четырёхбайтовыми: механическая замена Read4 на Read8 недопустима.

Зашитые в DevLnkLoad fingerprints NewRec/NewArr нужно согласовать с сигнатурами выбранного целевого ядра. Не переносить старые значения без проверки, особенно после изменения ADDRESS/eltyp.

## 4. Расширить модель fixup

DevLnkBase.DoFixups сейчас записывает результаты через Put4. Нужна явная информация о ширине записи, виде вычисления, целевой секции, addend и длине immediate после disp32. Например:

```componentpascal
FixRec = RECORD
    kind: INTEGER;
    offs: INTEGER;
    width: INTEGER;
    immLen: INTEGER;
    target: Section;
    addend: LONGINT
END;
```

Это эскиз, не готовая замена существующей структуры.

| OCF fixup | Действие в AMD64 |
|---|---|
| absolute | Запись полного адреса, 8 байт |
| relative | Относительное смещение, 4 байта |
| copy | Копирование 8-байтового значения из целевого места |
| table / tableend | Запись адреса, 8 байт; шаг таблицы 8 |
| ripBased + immLen | disp32 с учётом следующих байтов immediate |

Формула RIP-relative:

```text
disp = target + addend - (patchAddress + 4 + immLen)
```

Вычислять в LONGINT, проверять диапазон MIN(INTEGER)..MAX(INTEGER), только затем записывать четыре байта. Для absolute/copy проверять границы восьмибайтовой записи, а не только четырёхбайтового заголовка цепочки.

bbrun64.c содержит работающую модель декодирования формата, но не является безусловным эталоном проверок: там некоторые преобразования в int не проверяют переполнение. Отдельно установить, какие fixup реально выдаёт текущий DevCPLamd64; неизвестные виды отклонять явно.

## 5. Реализовать DevLnkWriteElf64

Существующий writer явно использует ELF32, EM_386 и R_386_*.

Новому writer нужны ELF64-заголовок, program/section headers, symbols, dynamic entries, AMD64 GOT/PLT, целевые релокации и Linux AMD64 interpreter. Изменяется не только ширина, но и раскладка некоторых структур. Для записей с явным addend используется Elf64_Rela; описание общего формата: [ELF relocation](https://osr600doc.sco.com/en/SDK_cprog/OF_Relocation.html). Перед реализацией сверить детали с актуальной AMD64 psABI.

Импорт функций и переменных разделить. Дальний адрес функции можно обслужить через PLT/trampoline. Подмена адреса внешней переменной адресом trampoline неверна: для переменных нужна согласованная с генератором кода схема адресации и релокаций.

## 6. AMD64-startup и завершение

DevLnkBase.GenInitCode сейчас генерирует i386-код, в частности передаёт modlist через EBX. Нужен отдельный AMD64 путь:

* передача списка модулей;
* подготовка bootInfo, argc, argv;
* соблюдение соглашения вызовов и выравнивания стека;
* порядок инициализации ядра и тел модулей;
* завершение и вызовы терминаторов.

В bbrun64 уже есть установка modList и bootInfo. Нужно зафиксировать роли Kernel64, Kernel и главного модуля: текущий загрузчик использует оба ядра, а интерфейс DevLinker1 исторически имеет один KernelName. Нельзя свести перенос к замене EBX на RBX без согласования контракта старта.

## 7. Ограничения размещения первого варианта

TYP и некоторые операции с дескрипторами на момент анализа ещё зависят от низкой адресной арены. Код и метаданные следует размещать в совместимом диапазоне, пока эти ограничения не сняты согласованно во всём runtime.

Все ссылки disp32 должны проходить проверку дальности. Выбранная база образа сама по себе этого не гарантирует, особенно для импортов из системных библиотек.

## Рекомендуемый порядок работы

1. Описание целевой архитектуры и TargetAddress.
2. Чтение OCF AMD64 и метаданных.
3. Fixup на 4/8 байт с проверкой диапазонов.
4. Минимальный ELF64 executable и AMD64-startup.
5. Импорты libc, затем GTK и остальные библиотеки.
6. Динамическая загрузка дополнительных модулей через StdLoader.
7. PIE/DLL, другие ОС и расширение адресных диапазонов.

Для будущих проверок: простой модуль без внешних импортов, NEW записи и массива, межмодульные вызовы/переменные, наследование и copy-fixup таблиц методов, RIP-relative с immediate, импорт функции и внешней переменной, запуск без внешних OCF для полностью включённых модулей, загрузка дополнительного OCF, запуск с аргументами и корректное завершение. Отдельно проверить сборку на 32-битном хосте.

## Более короткий промежуточный путь

Можно добавить в DevLinker1 режим упаковки AMD64-загрузчика и выбранных OCF в один executable. Это позволит получить единый запускаемый файл раньше, но fixup будут выполняться при старте.

Текущий bbrun64 ещё не читает такой пакет: main сканирует внешние каталоги `*/Code` и открывает отдельные OCF. Требуется добавить каталог встроенных модулей, их смещения/размеры, выбор kernel/main и чтение из собственного executable. Просто дописать OCF к существующему bbrun64 недостаточно.

Этот режим не равнозначен полноценному DevLnkWriteElf64. Выбор между ним и полноценной линковкой пока не сделан пользователем.

# DevLinker1: сборка Windows x64

Реализована команда:

```text
DevLinker1.LinkPeExe64 Program.exe := Kernel64+ Library Program$ ~
```

Она собирает PE32+ из **Dev OCF AMD64**, созданных `DevCompiler64`. Формат Hr
отличается, поэтому `HrPeFmt` и `HrCompiler` здесь не используются.
Существующие `LinkPeExe`, `LinkPe`, `LinkPeDll` остаются 32-битными.

Основная документация на английском с устройством загрузчика, fixup, ABI и
командами воспроизведения: [Linker1-Win64](../Linker1-Win64.md).

## Интерфейс

* `+` выбирает и загружает ядро, предоставляющее `NewRec`/`NewArr`. Оно нужно при
  наличии соответствующих fixup; без выделения памяти ядро можно не указывать.
* `$` выбирает главный модуль; по умолчанию — последний в списке.
* Остальные имена добавляют корни зависимостей. Импорты включаются рекурсивно,
  каждый модуль один раз. Порядок инициализации определяется зависимостями.
* Все маркеры разбираются до загрузки, поэтому ядро можно указать в конце команды.
* Объектные файлы ищутся через текущий `Librarian.lib`. Путь результата можно
  заключить в кавычки; каталог должен существовать.

## Сборка инструментов

Запускать из корня проекта, двумя отдельными процессами:

```sh
echo "DevCompiler.CompileThis DevCPM DevLibrarian" | ./dev0Linux
echo "DevCompiler.CompileThis DevCPCamd64 DevCPVamd64 DevCompiler64 DevLnkBase DevLnkLoad DevLnkLoad64 DevLnkWritePe DevLinker1" | ./dev0Linux
```

Приложение компилируется уже через `DevCompiler64`. Его Code/Sym следует держать
отдельно от 32-битных файлов инструментов.

## Проверенный пример

```sh
mkdir -p /tmp/dev-pe64-test/Check/Code /tmp/dev-pe64-test/Check/Sym
mkdir -p /tmp/dev-pe64-test/System/Code /tmp/dev-pe64-test/System/Sym

echo "DevLibrarian.EnableDevLib('/tmp/dev-pe64-test', 'Mod64');
DevCompiler64.CompileThis Kernel64 CheckPe64Api CheckPe64Dep CheckPe64Main
DevLinker1.LinkPeExe64 '/tmp/dev-pe64-test/hello.exe' := Kernel64+ CheckPe64Dep CheckPe64Main$ ~" | ./dev0Linux

python3 Dev/Test/check_pe64.py /tmp/dev-pe64-test/hello.exe
WINEDEBUG=-all wine64 /tmp/dev-pe64-test/hello.exe
```

`Kernel64` — имя исходника; имя модуля внутри него — `Kernel64`.
Программа выводит `DevLinker1 Windows x64 OK` и завершается кодом 0.

Проверены: инициализация зависимости, импорт процедуры и переменной, виртуальный
вызов унаследованного метода, `NEW` записи и массива, таблица `CASE`, вызов
`WriteFile` с пятью параметрами, повторная сборка и повторное включение модуля.
Структурная проверка подтвердила 6 секций, 8 отсортированных экспортов и 181
релокацию `DIR64`. Перенос образа по таблице релокаций с базы 0x400000 на 0x14000000
также проверен запуском через Wine. На настоящей Windows запуск не выполнялся.

Проверены отказы для отсутствующего модуля, повторного `$`, i386/Hr OCF,
обрезанного заголовка и циклического импорта. После отказа следующая сборка в том
же процессе проходит. Старая команда `LinkPeExe` по-прежнему создаёт PE32/i386.

## Windows ABI и ограничения

Для прямых вызовов Windows API в DevCompiler64 добавлен `[ms64]`, например:

```componentpascal
PROCEDURE [ms64] ExitProcess* (code: INTEGER);
```

Поддерживаются целочисленные параметры/результаты, указатели, `SYSTEM.ADDRESS`
и VAR-параметры, представимые одним адресом. Первые четыре слота передаются через
RCX/RDX/R8/R9, остальные — через стек; выделяются 32 байта shadow space,
обеспечивается 16-байтное выравнивание. Адреса имеют 64 бита, DWORD/BOOL — 32 бита.

Параметры и результаты с плавающей точкой, структуры по значению, tagged VAR
записи/массивы и вложенные callbacks пока
отклоняются ошибкой компилятора 200. `[ccall]` остаётся SysV; он не заменяет
`[ms64]`. Линкер не может исправить неправильное соглашение вызова в готовом коде.

Адреса самого образа пока ограничены нижними 2 ГиБ, база по умолчанию — 0x400000.
Указатели в образе и IAT записываются восемью байтами. Используются релокации
DIR64; ASLR/LARGE_ADDRESS_AWARE не заявлены. Windows callbacks, косвенные вызовы `[ms64]` и unwind-таблицы PE64 реализованы;
см. [Windows ABI компилятора](Compiler64-Windows-ABI.md). Сборка x64 DLL, TLS,
языковые SEH handlers и полный Windows runtime остаются отдельной работой.

Тест использует существующий минимальный `Kernel64` со статической кучей. Это
проверка выделения памяти, а не перенос GC, UI, динамического загрузчика и
обнаружения модулей. Linux-модули каркаса нельзя просто включить в Windows EXE.
Для запуска полноценного каркаса потребуется отдельный перенос runtime. Текущий результат — работающая сборка самостоятельных
Windows x64 программ в описанных пределах.

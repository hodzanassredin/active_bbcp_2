# Один HTTP-клиент тремя способами

Задача одна: `GET http://узел:порт/путь`, разобрать строку состояния и заголовки, принять тело по
`Content-Length` или `Transfer-Encoding: chunked`, сделать один шаг переадресации по `Location`,
вернуть код и тело. Один и тот же клиент написан трижды. Рядом — `PaketHttp.Reader.Do` из исходной
системы: так сетевой клиент выглядел до задач.

| Модуль | Где | Кто двигает разбор |
|---|---|---|
| `ObxHttpTask` | `Obx/Mod64/HttpTask.cp` | задача, код последовательный |
| `ObxHttpCodec` | `Obx/Mod/HttpCodec.cp` | `Services.Action`, слои-кодеки |
| `ObxHttpCodecTask` | `Obx/Mod64/HttpCodecTask.cp` | задача кормит те же кодеки |
| `PaketHttp` | `Paket/Mod/Http.cp` | `Services.Action`, один автомат |

Интерфейс слоя лежит отдельно, в `Obx/Mod/Codec.cp`:

```
CONST
	done* = 0; more* = 1; error* = 2;

TYPE
	Decoder* = ABSTRACT RECORD END;

PROCEDURE (VAR d: Decoder) Decode* (IN buf: ARRAY OF BYTE;
		beg, len: INTEGER; OUT used, res: INTEGER), NEW, ABSTRACT;
```

`more` значит «единица не целая, ничего не съедено»; `used = 0`. `done` значит «единица разобрана,
съедено `used` байт»; описание единицы — смещение и длина среза того же буфера — лежит в полях
разборщика. `error` значит «поток испорчен». Разборщик помнит, докуда уже искал разделитель, и
повторный вызов с большим окном не начинает поиск заново.

## Три ключевых места

Задача читает ответ обычными вложенными процедурами. `ReadChunk` зовёт `ReadLine` и `ReadExact`,
те зовут `ReadByte`, `ReadByte` зовёт `Fill`, и только внизу стоит ожидание:

```
PROCEDURE (VAR r: Reader) Fill (): BOOLEAN;
BEGIN
	AsyncIO.Read(r.s, r.buf, 0, LEN(r.buf), r.end);
	IF r.end <= 0 THEN r.beg := 0; r.end := 0; RETURN FALSE END;
	r.beg := 0;
	RETURN TRUE
END Fill;

PROCEDURE ReadChunk (VAR r: Reader; VAR body: ARRAY OF BYTE; at: INTEGER;
		OUT n: INTEGER; OUT last: BOOLEAN; OUT err: INTEGER): BOOLEAN;
	VAR line: ARRAY 64 OF CHAR;
BEGIN
	n := 0; last := FALSE;
	IF ~r.ReadLine(line) THEN err := errClosed; RETURN FALSE END;
	IF ~ParseHex(line, n) THEN err := errChunk; RETURN FALSE END;
	IF n = 0 THEN
		IF ~r.ReadExact(junk, 0, 2) THEN err := errClosed; RETURN FALSE END;
		last := TRUE; RETURN TRUE
	END;
	IF at + n > LEN(body) THEN err := errBuffer; RETURN FALSE END;
	IF ~r.ReadExact(body, at, n) THEN err := errClosed; RETURN FALSE END;
	IF ~r.ReadExact(junk, 0, 2) THEN err := errClosed; RETURN FALSE END;
	RETURN TRUE
END ReadChunk;
```

Состояние разбора — локальные переменные задачи: `kind`, `length`, `loc`, позиция в буфере
`Reader`. Номера шага нет. Пока данных нет, задача спит в `AsyncIO.Read`; главный цикл опрашивает
дескриптор.

Кодек не знает, кто его кормит. Его водитель хранит буфер, поля трёх разборщиков и одно поле
порядка слоёв `phase`. `Drive` вызывает слой, смотрит на `used` и `res`, сдвигает окно и повторяет:

```
CASE p.phase OF
	phaseHeader:
		p.hd.Decode(p.buf, p.beg, p.end - p.beg, used, res);
		IF res = ObxCodec.more THEN
			IF used # 0 THEN p.Fail(errContract) END;
			RETURN
		ELSIF res # ObxCodec.done THEN
			IF p.hd.badStatus THEN p.Fail(errStatus) ELSE p.Fail(errHeader) END;
			RETURN
		END;
		...
		CASE p.hd.kind OF
			kindNone: p.finished := TRUE; RETURN
		| kindLength: p.bd.Reset(p.hd.length); p.phase := phaseLength
		| kindChunked: p.cd.Reset; p.phase := phaseChunk
		END
| phaseLength: ...
| phaseChunk: ...
END
```

Слои: заголовок ответа до пустой строки, тело по длине, кусок `chunked`. Между вызовами живут
буфер и поля разборщиков; порядок слоёв — маленькое поле `phase` водителя. Водитель —
`Services.Action`: пока данных нет, действие переставляется в очередь главного цикла.

Третий модуль берёт те же `ObxHttpCodec.Parser` и `ObxHttpCodec.HeaderDecoder`, а кормит их задача:

```
LOOP
	IF j.p.err # errNone THEN EXIT END;
	IF j.p.redirect OR j.p.finished THEN EXIT END;
	AsyncIO.Read(s, x, 0, LEN(x), n);
	IF n > 0 THEN j.p.Feed(x, n); j.p.Drive
	ELSIF ~s.IsConnected() THEN j.p.Eof
	END
END;
```

Разбор не зависит от того, кто его кормит. Задача ждёт сокет; действие крутится в главном цикле.

`PaketHttp.Reader.Do` устроен иначе. Это одна процедура с явными состояниями `firstHeader`,
`completingNormal`, `completingChunked`, `startingChunked`, `error`, `redirected`; вложенная
`MultyPack` разбирает остаток пакета. Заголовок, длина, кусок и запись в файл переплетены в одном
теле, а буфер — 1 МиБ на соединение.

## Сравнение структуры

Строки разбора посчитаны без пустых строк и комментариев. У `PaketHttp` взят текст
`Reader.Do`; у `ObxHttpTask` — `ReadByte`, `ReadLine`, `ReadExact`, разбор строки состояния и
заголовков, `ReadHead`, `ReadChunk`, `ReadBody`; у `ObxHttpCodec` — `HeaderDecoder`, `BodyDecoder`,
`ChunkDecoder`, `Drive` и вспомогательные разборы; `ObxHttpCodecTask` нового разбора не содержит.

| Вариант | Строк разбора | Явные состояния | Зависимости | Стек на соединение | Буфер |
|---|---|---|---|---|---|
| `PaketHttp.Reader.Do` | 286 (подсчитано) | 6 констант, 3 поля (подсчитано) | `Services.Action`, `CommStreams`, `Views`, `Files` | нет | 1 МиБ на соединение (подсчитано) |
| `ObxHttpTask` | 208 (подсчитано) | 0 констант, 2 поля позиции (подсчитано) | задачи, `AsyncIO`, amd64 | 64 КиБ в примере; по умолчанию 256 КиБ; минимум 9 КиБ (измерено) | 4 КиБ чтения на стеке, 8 КиБ тела |
| `ObxHttpCodec` | 292 (подсчитано) | 6 именованных: 4 фазы и 2 состояния куска; 9 полей (подсчитано) | `Services.Action`; задач, `Async*`, `Monitors`, `ACTIVE` нет | нет | 8 КиБ входа и 8 КиБ тела в записи |
| `ObxHttpCodecTask` | 0 новых (подсчитано) | 0 новых (подсчитано) | задачи, `AsyncIO`, `ObxHttpCodec` | 64 КиБ; минимум 6 КиБ (измерено) | 2 КиБ окна, 16 КиБ `Parser` в записи |

`ObxHttpCodec` не импортирует `Tasks`, `Async*`, `Monitors` и не использует `ACTIVE`, `[exclusive]`
и `AWAIT`; это проверено по списку импортов. Водитель опирается на `Services.Action` — механизм
исходного BlackBox. Ни один из трёх модулей не пишет `ACTIVE.AWAIT`, `[exclusive]` и `^`: расширение
языка им не нужно. Задача берётся из библиотеки `Tasks`, кодек — из `Services.Action`.

Минимум стека измерен на пути «соединиться, отправить запрос, дождаться первого байта»: задача
`ObxHttpTask` работает при 9 КиБ, `ObxHttpCodecTask` — при 6 КиБ. Меньший стек трапает до
увеличения счётчика соединений. Это минимум данного примера и данного пути, не общее обещание
`Tasks`.

## Сравнение замеров

Условия: локальный сервер на 127.0.0.1, 1000 одновременных соединений, которые держат ответ;
и 1000 последовательных запросов по `Content-Length`. Одна машина, один процесс, пять прогонов,
load average 0.9–2.0. Команда:

```sh
tools/iso.sh tools/test-http-examples.sh --measure
```

| Вариант | RSS на соединение | Виртуальная память | Задач на 1000 | Выделений на запрос | Куча за запрос | 1000 послед. запросов |
|---|---|---|---|---|---|---|
| `ObxHttpTask` | 21 КиБ (измерено) | 77 КиБ при стеке 64 КиБ; 270 КиБ при 256 КиБ (измерено) | 1000 (измерено) | 6 (измерено) | 737 байт (измерено) | 1160 мс (измерено) |
| `ObxHttpCodec` | 19 КиБ (измерено) | 19 КиБ (измерено) | 0; 1004 действия (измерено) | 4 (измерено) | 1744 байта (измерено) | 72 мс (измерено) |
| `ObxHttpCodecTask` | 27 КиБ (измерено) | 87 КиБ (измерено) | 1000 (измерено) | 6 (измерено) | 1833 байта (измерено) | 1170 мс (измерено) |
| `PaketHttp` | не измерено | не измерено | 0 задач, действие на загрузку | не измерено | не измерено | не измерено |

Выделения посчитаны по `Kernel.AllocCount` до и после 1000 запросов; куча — по `Kernel.Allocated`
сразу после цикла. Полная сборка после цикла не даёт прироста: счётчик уменьшается на 60 КиБ
служебных блоков, утечки нет.

`PaketHttp` не измерен: его единственный вход `Download` пишет результат в `Files.File` и для
прогресса трогает `Views`. В консоли без рабочего локатора файла наблюдаемого результата нет.
Число строк и буфер 1 МиБ посчитаны по исходнику.

Время `ObxHttpTask` и `ObxHttpCodecTask` включает ожидание главного цикла: `Get` крутит
`Services.actionHook` и `AsyncIO.Poll(1)`, поэтому последовательный запрос платит миллисекундой
опроса. `ObxHttpCodec` в том же опыте не ждёт, а переставляет действие без паузы, и 1000
последовательных запросов проходят быстрее. Это свойство способа ожидания, не разбора: при сотнях
одновременных соединений паузы задач перекрываются.

## Что теряется и что приобретается

Задача даёт обычный последовательный код: `ReadLine`, `ReadExact`, `ReadChunk` читаются сверху
вниз, состояние лежит в локальных переменных, место ожидания видно внизу. Цена — стек на
соединение и планировщик: 64 КиБ виртуальной памяти в примере, 256 КиБ по умолчанию, 1000 записей
задач в куче на 1000 соединений. Одновременные соединения даются без переписывания кода.

Кодек не заводит ни задачи, ни стека: 19 КиБ на простаивающее соединение и 4 выделения на запрос.
Он работает на исходном BlackBox и не требует ни задач, ни их планировщика. Цена — явный автомат:
слои, поле `phase`, договор `more/done/error`, проверка `used` и больше строк разбора, чем у задачи.
Пока ответ не пришёл, действие занимает главный цикл; блокирующий вызов вроде `CommTCP.NewStream`
останавливает цикл на всё время соединения.

`ObxHttpCodecTask` соединяет оба: разбор тот же, что у кодека, ожидание — как у задачи. Плата —
стек задачи плюс запись `Parser` в куче; выигрыш — привычный последовательный код водителя.

`PaketHttp` держит один буфер 1 МиБ и пишет тело в файл; его автомат разбирает заголовок и кусок
в одном проходе и потому короче слоёного, но состояние шага, позиция и длина лежат полями, а
ошибки видит только владелец `Downloading`.

## Где кодек неудобен

Тело неизвестной длины. Наш слой длины объявляет `more`, пока не собрал всё тело, и по договору
`more` ничего не съедает. Значит, буфер соединения должен вмещать тело целиком. Для тела в 1 МиБ
нужен буфер в 1 МиБ на соединение; это возвращает память, которую кодек сэкономил на стеке.

Потоковая отдача большого тела. Чтобы отдавать тело кусками, слой должен съедать часть единицы и
возвращать срез на каждый вызов. Договор `more` с `used = 0` этого не разрешает. Нужен другой
договор (частичное потребление) или задача с буфером на стеке. `chunked` в нашем виде ограничен
размером одного куска, а не всего тела.

Ожидание в коде зовёт `CommTCP.NewStream` прямо на главном стеке. На локальном узле это
незаметно; разрешение имени или соединение с далёким узлом остановит главный цикл. Задача эту
работу уводит в `AsyncWork`, кодек — нет.

## Как проверить

```sh
tools/iso.sh tools/test-http-examples.sh            # 39 проверок трёх клиентов
tools/iso.sh tools/test-http-examples.sh --mutate   # три мутации обязаны ловиться
tools/iso.sh tools/test-http-examples.sh --measure  # память и время
tools/iso.sh tools/unit.sh Obx_devHttpCodec --compile "ObxCodec ObxHttpCodec"
```

Сценарий поднимает локальный сервер на 127.0.0.1 и прогоняет `Content-Length`, `chunked` из трёх
кусков, переадресацию, ответ по одному байту с паузами, обрыв посреди заголовка, посреди длины
куска и посреди тела, мусор вместо строки состояния и нешестнадцатеричную длину куска. Каждый
путь проходит через все три клиента, результаты сверяются между собой и с эталоном.

Мутации: заголовок съедает лишний байт; слой тела возвращает `more` с `used = 1`; `ReadExact` не
дочитывает при коротком чтении. Первая ловится на `/len`, вторая на `/slow`, третья на `/cutbody`.

Модульный тест `Obx_devHttpCodec` не ходит в сеть: он подаёт один и тот же буфер двумя кусками во
всех возможных позициях разреза и сверяет итог с разбором целого буфера. Отдельно каждая позиция
обрыва обязана дать `errClosed`. Тест зарегистрирован в `tools/tests.txt`.

# Монитор-объект и пропуск в модуле Tasks

## Вывод

В `Tasks` собраны три вещи: пропуск `Ctx`, задача с пропуском `Job` и объект-монитор
`Object` с очередями входа, флагов и условий. Пропуск нельзя завести вне `Tasks` —
это проверяет компилятор, а не соглашение. Вход в монитор, выход и ожидание написаны
один раз в `Tasks`; наследник объекта пишет только тело операции.

Свободный `Do` стоит 30 нс. Буфер 64 на флагах по умолчанию будит без передачи
монитора: 72 нс на предмет и 31 переключение на 1000; передача из рук в руки даёт
213 нс и 2030 переключений. Выделений памяти на операцию после прогрева нет.

С пропуском можно спать (`ParkCtx`) и запускать детей (`Spawn`, `JoinAll`). Завершённую
задачу можно запустить тем же объектом: 10 тыс. прогонов после прогрева не выделяют
памяти, 196–207 нс на прогон против 507–523 нс при `NEW` каждый раз. Стек возвращается
в пул и берётся оттуда; запись реестра стека привязывается заново.

Масштаб: 524 217 задач со своими мониторами стоят 2,4 ГБ RSS; потолок — карты памяти,
а не память.

## 1. Что собрано

`Ctx` — пропуск задачи. Это `LIMITED RECORD`: создать его, расширить или скопировать
вне `Tasks` нельзя. Поля `task`, `group`, `cancelled` и `expired` экспортированы только
для чтения; вершина цепочки взятых мониторов лежит в задаче, её длину показывает
`HeldCount`. Пропуск создаёт `Job.Run` на своём стеке и передаёт телу по `VAR`.

`Job` — наследник `Task`. `Run` реализован в `Tasks` и дальше не переопределяется;
наследник пишет `Body- (VAR ctx: Ctx)`. Запуск — обычный `Tasks.Start`; завершённую
или отменённую задачу можно запустить снова тем же объектом.

`Object` — объект-монитор. `Do` входит в монитор, зовёт `Exclusive-` и выходит.
Операция — запись-наследник `Op` на стеке вызывающего, передаётся по `VAR`; служебных
полей в `Op` нет. `Exclusive` разбирает вид операции через `WITH`. `Ready` возвращает
множество флагов состояния; `Await` ждёт, пока `need * Ready() # {}`. `Cond` — условие-объект
для `AwaitCond`: его `Ready(o)` читает состояние монитора `o`.

С подписями:

```
TYPE
	Ctx* = LIMITED RECORD
		task-: Task;
		group-: Group;
		cancelled-, expired-: BOOLEAN
	END;

	Job* = POINTER TO ABSTRACT RECORD (Task) END;
	PROCEDURE (t: Job) Run* ();
	PROCEDURE (t: Job) Body- (VAR ctx: Ctx), NEW, ABSTRACT;

	Op* = ABSTRACT RECORD END;
	Object* = POINTER TO ABSTRACT RECORD END;
	PROCEDURE (o: Object) Do* (VAR ctx: Ctx; VAR op: Op), NEW;
	PROCEDURE (o: Object) Exclusive- (VAR ctx: Ctx; VAR op: Op), NEW, ABSTRACT;
	PROCEDURE (o: Object) Ready* (): SET, NEW, EXTENSIBLE;
	PROCEDURE (o: Object) Await* (VAR ctx: Ctx; need: SET): BOOLEAN, NEW;
	PROCEDURE (o: Object) AwaitCond* (VAR ctx: Ctx; c: Cond): BOOLEAN, NEW;
	PROCEDURE (o: Object) HoldsWhileWaiting* (): BOOLEAN, NEW, EXTENSIBLE;
	PROCEDURE (o: Object) TransferOnRelease* (): BOOLEAN, NEW, EXTENSIBLE;

	Cond* = POINTER TO ABSTRACT RECORD END;
	PROCEDURE (c: Cond) Ready* (o: Object): BOOLEAN, NEW, ABSTRACT;

	PROCEDURE (VAR c: Ctx) Stopped* (): BOOLEAN;
	PROCEDURE (VAR c: Ctx) TaskOf* (): Task;
	PROCEDURE (VAR c: Ctx) GroupOf* (): Group;
	PROCEDURE (VAR c: Ctx) HeldCount* (): INTEGER;

	PROCEDURE ParkCtx* (VAR ctx: Ctx; external: BOOLEAN): BOOLEAN;
	PROCEDURE Spawn* (VAR ctx: Ctx; t: Task);
	PROCEDURE JoinAll* (VAR ctx: Ctx);
	PROCEDURE SetDeadline* (VAR ctx: Ctx; ms: LONGINT);

	PROCEDURE Held* (o: Object): BOOLEAN;
	PROCEDURE Depth* (o: Object): INTEGER;
	PROCEDURE Queued* (o: Object): INTEGER;
```

`ParkCtx` — общая точка сна для библиотек с пропуском: `TRUE` — задача проснулась по
`Unpark`, `FALSE` — пропуск остановлен (отмена или срок, причина в `ctx`), и тогда
вызов возвращается сразу. Срок будит спящего через кучу спящих, отмена — через
`MakeReady`. `Held`, `Depth` и `Queued` — диагностика для тестов; форма ими не
пользуется.

## 2. Как устроен монитор

Состояние объекта — поле владельца, счётчик повторного входа и три очереди задач:
входа, флагов и условий. Очередь — поля самой задачи (`qnext`, `qkind`, `qneed`, `qcond`),
а не запись операции: задача стоит не больше чем в одной очереди монитора.

На выходе и при засыпании в `Await` монитор освобождается. Сначала, если есть ждущие
по флагам, один раз вызывается `o.Ready()` и выбирается первый, у которого
`need * ready # {}`. Иначе, если есть ждущие по условиям, выбирается первый, у которого
`c.Ready(o)` истинно. Иначе берётся первый из очереди входа. Пустая очередь метода не
вызывает. Что делать с выбранной задачей, решает `o.TransferOnRelease`: по умолчанию
монитор остаётся свободным, а задача только будится; она сама снова берёт монитор в
`Await` и перепроверяет условие. Объект, переопределивший метод и вернувший `TRUE`,
передаёт монитор из рук в руки: разбуженный сразу становится владельцем и с входящими
не соревнуется. Первый способ дешевле на буфере, второй — на ёмкости 1 и там, где важен
порядок между ждущими и входящими (раздел 5).

Внутри очереди порядок FIFO. Проверка «первый готовый» идёт по очереди, поэтому ждущий,
условие которого ещё ложно, не задерживает следующего. Разбуженный без передачи, найдя
условие ложным, возвращается в голову очереди: место он уже отстоял.

`Await` и `AwaitCond` — обёртки над одной процедурой `AwaitCommon`; различаются условием
(флаги `need` или объект `Cond`) и видом очереди. Они отпускают монитор, спят и снова
берут его. Возвращают `TRUE`, когда условие истинно и монитор у задачи, и `FALSE`,
когда задача остановлена отменой или сроком. В обоих случаях монитор остаётся у
задачи: `Exclusive` выходит обычным путём. Номер трапа и признак причины — в `ctx`.

Записи вызовов `Do` лежат в куче и берутся из списка свободных пропуска. После прогрева
вход, выход и ожидание не выделяют памяти; список свободных переживает запуск `Job`,
поэтому и повторный запуск не выделяет. У каждой записи есть две отметки: адрес
локальной переменной кадра `Do` (`mark`) и кадра ожидания (`wmark`).

## 3. Правила

**Повторный вход.** Та же задача может войти в `Do` того же объекта ещё раз: глубина
растёт, монитор освобождается на выходе с глубины 1. `Await` и `AwaitCond` на глубине
больше 1 своего объекта трапуют 23: ждать, держа собственный монитор дважды, нельзя.

**Сон с мониторами в руках.** Задача может спать, держа мониторы-объекты, только с их
разрешения. Решает каждый удерживаемый объект методом `HoldsWhileWaiting`; по умолчанию
он возвращает `FALSE`, и сон трапует 26. Объект, который разрешает такое ожидание,
переопределяет метод и возвращает `TRUE`.

Проверка стоит в общих точках засыпания, а не только в `Await`: в `Sleep`, `Join`, `Park`,
`ParkExternal`, в ожидании входа в занятый монитор и в `JoinAll`. Монитор, в чьём `Await`
задача спит на глубине 1, не проверяется: он отпущен на время сна и вернётся к задаче.
Ожидание входа в другой объект — тоже сон с монитором в руках, поэтому оно подчиняется
тому же правилу. Быстрый путь — одно сравнение: задача без взятых мониторов проверок не
делает.

`Yield` и `Sleep(0)` правила не нарушают: задача не ждёт условия, не отпускает монитор и
никому его не передаёт, а только встаёт в конец очереди готовых. Другая задача может
исполниться, но монитор остаётся у уступившей, и взаимное исключение не теряется. Трап
здесь запретил бы законную уступку и ничего не защитил бы.

**Трап.** Уборщик у задачи один на весь `Job`, а не на операцию. Он не отпускает
мониторы сам, а ставит отметку `trapped`. Отпускает `Heal`: на входе в `Do`, `Await`,
`AwaitCond`, `Stopped`, `HeldCount`, `Spawn`, `JoinAll` и `SetDeadline`, в конце
`Job.Run` и в `TaskBoot`, а также перед каждым сном — в `Sleep`, `Join`, `Park`,
`ParkExternal` и в ожидании входа в занятый монитор. Без отметки `Heal` стоит две
проверки флага и цепочку не трогает.

`Reconcile` отпускает запись, если снят её кадр: отметка `mark` ниже указателя стека.
Ожидание снимается только тогда, когда снят кадр самого ожидания (`wmark`): живой
`Await`, который только что встал в очередь перед сном, остаётся. Поэтому непойманный
трап отпускает все мониторы задачи, а трап, пойманный `Kernel.Try` внутри внешнего
`Exclusive`, — только внутренние.

Между трапом и сном задача не уступает процессор, а перед сном `Heal` уже снял
брошенные записи. Другая задача не увидит монитор, которого на стеке уже нет.

Номера трапов:

| Номер | Когда |
|---:|---|
| 20 | `Do`, `Await`, `AwaitCond`: объект `NIL`; `Spawn`: задача `NIL` |
| 21 | `Await`, `AwaitCond`: монитор не у вызывающей задачи |
| 22 | `Do`, `Await`, `AwaitCond` вне задачи |
| 23 | `Await`, `AwaitCond` на глубине больше 1 своего объекта |
| 25 | пропуск принадлежит другой задаче; `AwaitCond`: условие `NIL` |
| 26 | сон, держа монитор, который не разрешает ожидание |
| 100 | нарушен инвариант очереди или нет записи `Do` |

**Остановка.** `Tasks.Cancel` и срок в `SetDeadline` не трапуют в `Await`: задача получает
`FALSE` и сама решает, что делать. `Do` на остановленном пропуске не выполняет операцию
и возвращается без результата; `Spawn` после остановки не запускает задачу. Если задача
отменена, `TaskBoot` всё равно помечает её `Cancelled`, даже когда `Body` вернулось само.

**Дети.** `Spawn` кладёт задачу в группу пропуска, `JoinAll` ждёт её опустошения.
`Job.Run` в конце сам зовёт `JoinAll`: дети не переживают тело. При остановке
`JoinAll` отменяет группу и ждёт, пока задачи завершатся.

## 4. Примеры

Буфер на флагах: запросы `PutOp` и `GetOp`, `Ready` возвращает флаги «есть место» и
«есть предмет», `Await` ждёт нужного флага.

```
TYPE
	PutOp = RECORD (Tasks.Op) x: INTEGER END;
	GetOp = RECORD (Tasks.Op) x: INTEGER END;
	Buf = POINTER TO RECORD (Tasks.Object)
		ring: ARRAY 64 OF INTEGER; head, tail, count: INTEGER
	END;

PROCEDURE (b: Buf) Ready (): SET;
	VAR s: SET;
BEGIN
	s := {};
	IF b.count < LEN(b.ring) THEN INCL(s, 0) END;
	IF b.count > 0 THEN INCL(s, 1) END;
	RETURN s
END Ready;

PROCEDURE (b: Buf) Exclusive- (VAR ctx: Tasks.Ctx; VAR op: Tasks.Op);
BEGIN
	WITH op: PutOp DO
		WHILE b.count = LEN(b.ring) DO
			IF ~b.Await(ctx, {0}) THEN RETURN END
		END;
		b.ring[b.tail] := op.x; b.tail := (b.tail + 1) MOD LEN(b.ring); INC(b.count)
	| op: GetOp DO
		WHILE b.count = 0 DO
			IF ~b.Await(ctx, {1}) THEN RETURN END
		END;
		op.x := b.ring[b.head]; b.head := (b.head + 1) MOD LEN(b.ring); DEC(b.count)
	END
END Exclusive;
```

Сценарии тестов `System_devTasksObj`: взаимное исключение и FIFO очередей, буфер на флагах
и на `Cond`, повторный вход, трап `Await` на глубине 2, чужие мониторы в руках, отмена и
срок при ожидании входа и в `Await`, `Spawn`/`JoinAll`, повторный запуск задачи и `Job`,
выделения на операцию. Замеры — `System_devBench`.

## 6. Что не сделано и что вызывает сомнение

- Монитор-объект не взаимодействует с другими формами исключения: у него своё поле
  владельца, и один объект, взятый двумя разными способами, взаимно не исключается.
  В `main` других форм исключения нет.
- Ожидание в `Await` на глубине больше 1 трапует; вложенное ожидание по разным объектам
  разрешено.
- Сборка мусора при сотнях тысяч стоящих задач дорожает быстрее линейно; причина не
  установлена, поэтому замер масштаба останавливается на 100 тыс.
- Ожидание `Cond` проверяет условие под монитором на каждом пробуждении; на длинных
  очередях цена растёт линейно по числу ждущих.

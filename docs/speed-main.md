# Скорость задач в основной ветке

Документ описывает, из чего складывается скорость задач в `main`: поставщики стеков, прямое
переключение, один `Kernel.Try` на проход планировщика и правило запуска сборки. Числа сняты на
Linux amd64, одна нить ОС; они зависят от нагрузки машины.

## 1. Что входит в горячий путь

| Приём | Где | Что даёт |
|---|---|---|
| Прямое переключение задача → задача | `Tasks.Leave`, `directMax = 64` | при готовой очереди одно переключение вместо двух; `Yield` около 30 нс |
| Первый запуск задачи через `Step` | `Tasks.Step` | общий путь для холодного и тёплого стека |
| Переключение встроено в `Leave` | `Tasks.Leave` | меньше кадров над `Taskarch.Switch` |
| `jmp` вместо `ret` в переключателе | `Taskarch.Switch` | не снимает чужую запись буфера адресов возврата |
| Один `Kernel.Try` на проход планировщика | `Kernel.TryTasks`, `Tasks.Step` | `sigsetjmp` не на каждую задачу |
| Правило сборки по росту кучи (`gcGoal`) | `Kernel.NewBlock` | первая нехватка блока не запускает сборку при малом росте |
| Пул стеков в поставщике | `Tasks.NewGuardDir`, `Tasks.NewSlabDir` | стек завершённой задачи берётся без `mmap` |

## 2. Поставщики стеков

Стек задачи выдаёт поставщик — объект `Tasks.StackDir`. Пул свободных стеков лежит в поставщике;
из пула задача берёт стек без вызова поставщика, а поставщика зовёт только промах пула, возврат
лишнего ядру и опустошение. Задача помнит поставщика (`Task.dir`) и возвращает стек ему, поэтому
смена поставщика при живых задачах корректна.

Поставщиков два. `Tasks.NewGuardDir` — отдельный `mmap` со сторожевой страницей на задачу.
`Tasks.NewSlabDir` — плита на 64 стека одним отображением, сторожевая страница под каждым стеком.
Безопасность у плиты та же: переполнение упирается в свою страницу и даёт трап в своей задаче.
По умолчанию стоит плита; `Tasks.UseGuardStacks` и `Tasks.UseSlabStacks` выбирают поставщика,
`Tasks.SetStackDir` принимает любой объект-поставщик.

Пул держит до 1024 свободных стеков; лишнее `TrimPool` возвращает ядру не больше 16 стеков за шаг,
чтобы массовое завершение задач не стоило массы системных вызовов разом.

## 4. Что не входит

- Плотные стеки и проверка границы в прологе: нужен ключ компилятора, которого в `main` нет.
  Плотный стек без проверки безопасен только с запасом, а запас съедает выигрыш по памяти.
- Мониторы-объекты строятся на `Tasks.Object`; отдельного быстрого пути в компиляторе нет.
- Пул рабочих нитей и вынос блокирующих вызовов ОС: задачи остаются в одной нити.

## 5. Остаток

- Потолок 524 тыс. задач со сторожем; выше нужен другой поставщик стеков.
- Создание из пула в `System_devTasks` шумит на загруженной машине; для точного числа нужен
  отдельный стенд с прогревом и счётчиком сборок.
- Цена проверки границы стека в прологе не измерена: варианта нет в коде.

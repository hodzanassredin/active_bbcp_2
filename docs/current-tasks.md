## Направление: меньше выделений и копирований (владелец, 25.11.2026)

- Цель: подсистемы и примеры по возможности не выделяют память в куче на каждое сообщение или операцию.
  Данные лежат на стеке задачи или в переменных модуля, передаются параметрами `IN`/`OUT`/`VAR`, разные
  типы сообщений разбираются через `WITH`; куча — для долгоживущего и большого.
- Порядок: опись мест, где сейчас выделяется память на операцию (с числами), правила стиля, перечень
  изменений интерфейсов «было/стало» — на согласование владельцу; переписывание — после согласования.
- Связанные работы: диагноз распределителя и пробы пула, массива с индексом и канала значений (ветка `alloc`).

## 25.11.2026 — форма «монитор в базовом классе + пропуск» (владелец: «мне нравится»)

- Основной метод: задача со своим стеком (`Tasks.Task`, `Run`), компилятор исходный; монитор — базовый тип с `Do` (вход, `Exclusive`, выход) и `Wait`; `[exclusive]`/`AWAIT` — необязательная короткая запись.
- Пропуск `Tasks.Ctx = LIMITED RECORD` передаётся `VAR ctx` в `Run`, `Do`, `Wait`, `Join` и вниз по цепочке: ждать без пропуска нельзя (проверяет компилятор).
- В пропуске: задача, группа, `cancelled`, `expired`; `Wait` возвращает BOOLEAN; причина — из `ctx`; после остановки ждущие операции возвращаются сразу, ничего не делая; ошибки самой операции возвращает операция. `Start` — откуда угодно, `Spawn(ctx, t)` — дочерняя в группе родителя, `SetDeadline(ctx, ms)`.
- Не решено (владелец: «насчёт интерфейсов потом подумать»): менять ли подписи существующих `Tasks`/`Async`; взятые мониторы и счётчик уступки в пропуске; объединённый тип «активный объект».
- Пробы: `objform` (форма без пропуска, DeepSeek), `copystack` (участок стека в кучу — исследование), `httpex` (HTTP тремя способами), `pool` (растущий пул), `hooks-study` (опись крючков: минимум ~330 строк ядра на Linux amd64, оценка), `crypto` (перенос принят локально).

## AsyncObject: повторный вход (решено с владельцем 25.11.2026)

- Повторный вход той же задачи в `Do` разрешён, считается глубина (как у Негеле, C.14).
- `Wait` на глубине больше 1 своего объекта — всегда трап (монитор нельзя отпускать посреди внешней операции).
- `Wait`, когда задача держит ещё и другие мониторы, — трап, если хоть один из них не разрешил это:
  метод `(o: Object) HoldsWhileWaiting* (): BOOLEAN, NEW, EXTENSIBLE`, по умолчанию FALSE.
- Удерживаемые мониторы — цепочкой в `ctx` (`ctx.top`, `o.outer`); её же использует уборщик при трапе.
- Режим при запуске задачи не вводим. Встречная блокировка двух задач остаётся на программисте.
- Дальше по разбору оговорок: пункт 2 (одна операция — один вызов), 3–6.

## Монитор-объект: решения по оговоркам 2–4, 6 (владелец 25.11.2026)

- Всё в одном модуле `Tasks`: задача, пропуск `Ctx`, объект-монитор (`Do`, `Exclusive-`, `Wait`,
  `HoldsWhileWaiting`), операция (`Ready`). `Park`/`ParkHard`/`Unpark` наружу не экспортируются.
- Операция — только метка, `Ready` и параметры; служебных полей в ней нет. Поля очереди (сосед, условие) —
  неэкспортируемые поля задачи. Проверка «операция занята» не нужна. Операция с параметрами — своя у задачи,
  операция-метка — общая.
- Уборщик при трапе — один на задачу, операция не расширяет `Kernel.TrapCleaner`.
- Трап, пойманный через `Kernel.Try` внутри `Exclusive`: мониторы из цепочки `ctx.top` отпускаются до уровня
  `Try` (отметка стека при входе в `Do`), остальные остаются. Объект после трапа не помечается испорченным.
- Осталось: пункт 5 (условия всех ждущих на каждом выходе), затем сборка и замеры.

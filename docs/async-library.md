# Библиотека ожиданий, рабочие нити и компутоны (этапы 7–9)

Подсистема `Async` — необязательная надстройка над этапами 1–6. Она не
меняет каркас: каркасные модули (System, Std, Text, Form, Dev, Lin, Win)
по-прежнему не компилируются с ключом `^` и не ждут.

```
Async/Mod/       Select.cp  Chan.cp  Once.cp  IO.cp  Proto.cp
Async/Mod64/     Work.cp    WorkLin.cp  WorkWin.cp  WinSock.cp
                 Computon.cp  Mpi.cp
Robust/Mod64/    Parallel.cp      (* фасад RobustParallel *)
System/Mod/      Poller.cp
Lin/Mod64/       Threads.cp Native.cp
```

`Async/Mod64` компилируется только для AMD64; 32-битная цель эту
библиотеку не собирает. При этом ядро расширения на i386 работает:
`System/Mod/Kernel.cp` получил реестр стеков, мониторы, `Poll` и
`CallCond`, `System/Mod/Tasks.cp` — переключатель x86, `CPC486` —
пролог/эпилог `[exclusive]`; `tools/test32.sh` гоняет Unit, Files,
Tasks, Monitors, Active и Yield на ELF32-консоли. Поэтому каналы,
рабочие нити и компутоны доступны только на amd64, а задачи, мониторы,
`ACTIVE.AWAIT` и ключ `^` — на обеих целях. `LinThreads` и `LinNative`
— отдельные модули объявлений:
`LinLibc` загружен в хост-процесс (`dev0Linux`, `blackbox-console`), и его
символьный файл нельзя расширить новыми процедурами, не пересобрав мир.

## Этап 7: ожидания и ввод-вывод

### Однократная переменная

```
o := AsyncOnce.New();
o.FillInt(42);          (* ровно один раз; повтор — трап 21 *)
x := o.ReadInt();       (* ждёт заполнения *)
```

Есть варианты `FillMsg`/`ReadMsg` для `AsyncSelect.Msg`. Объект — монитор:
методы `[exclusive]`, ожидание — `ACTIVE.AWAIT(done)`.

### Каналы

```
c := AsyncChan.NewChan();                 (* встреча *)
b := AsyncChan.NewBuffer(8);              (* ограниченная очередь *)
m := AsyncChan.NewMailbox();              (* неограниченный ящик *)
c.Send(msg); c.Recv(msg);
b.Send(msg); b.Recv(msg);
m.Send(msg); m.Recv(msg);
```

Все три — мониторы с методами `[exclusive]` и `ACTIVE.AWAIT`; встреча
двухфазовая: `Send` кладёт вклад и ждёт, пока получатель его заберёт
(`taken`). Сообщение — `AsyncSelect.Msg` (расширяемая запись-указатель);
после отправки оно не меняется (дисциплина Clojure/Erlang). Приём через
`WITH`:

```
TYPE NumMsg = POINTER TO RECORD (AsyncSelect.Msg) n: INTEGER END;
VAR m: AsyncSelect.Msg;
...
WITH m: NumMsg DO ... END
```

### Select/Alt

```
VAR ops: ARRAY 3 OF AsyncSelect.Op;
AsyncChan.RecvAlt(a, ops[0]);
AsyncChan.RecvAlt(b, ops[1]);
AsyncChan.TimeoutAlt(100, ops[2]);
i := AsyncChan.Select(ops);      (* индекс сработавшей; 2 — тайм-аут *)
m := ops[i].got;
```

Устройство — по образцу Hopac/CML: каждое предложение (offer) несёт общий
`Ctx` с флагом решения. Первый канал, готовый исполнить предложение, под
своим монитором ставит флаг, забирает/отдаёт сообщение и будит задачу
через `Tasks.Unpark`; остальные предложения снимает владелец после
пробуждения (nack). Активный вклад отправителя откатывается, если решение
принял другой канал: любая операция, наткнувшаяся на offer с решённым
`Ctx`, очищает вклад (`Prune`). Тайм-аут — обычная альтернатива; ждущая
задача спит на `Tasks.Park`, таймер — действие `Services`.

`Select` можно звать только из задачи. Альтернативой может быть и
готовность `Pull` компутона (`AsyncComputon.AltPull`) — сигнал
будит `Select` там же, где канал. Отмена задачи во время ожидания
оставляет предложения; они снимаются при следующем обращении к каналу
(проверка `Tasks.State`), отдельного trap-cleaner нет.

### Ожидание готовности дескрипторов

`System/Mod/Poller.cp` — реестр «дескриптор + событие + Waiter»;
платформенный хук ставит `LinConsole.Init`. `Console.WaitInput` опрашивает
stdin и зарегистрированные дескрипторы одним `poll`, поэтому главный цикл
просыпается от сетевого события, а в покое спит.

```
AsyncIO.Read(s, buf, beg, len, read);    (* читать хотя бы байт *)
AsyncIO.Write(s, buf, beg, len, written);(* записать хотя бы байт *)
AsyncIO.Accept(l, s, timeout);           (* принять соединение *)
```

`CommStreams.Stream/Listener` получили `Handle()`; у `CommTCP__Lin` это
сокет. Если `Handle() = -1`, ожидание вырождается в `Tasks.Sleep(1)`.

`CommTCP__Lin` переведён с `select` на `poll`: `fd_set` ограничен 1024
дескрипторами, а тысяча соединений требует больше. Заодно поднята очередь
`listen` (128).

### Замеры

`Test64IO.TestEcho1000` (localhost): 1000 одновременных соединений,
эхо-обмен, соединения остаются открытыми. Прогон занимает 2.8–3.1 с.
Пока 1000 соединений молчат, процессорное время процесса за 1 с —
7–50 мс (0.7–5 %; зависит от периода опроса).

`Test64Channels` — 9 тестов: Once, встреча (100 сообщений с проверкой
порядка), ограниченный буфер, почтовый ящик с `WITH`, Select по двум
каналам, тайм-аут, отсутствие «протухших» предложений после тайм-аута,
отправка в полный буфер, повторный `Fill`.

### Чего нет

- Протокол канала — в этапе 10 (ниже).
- `AsyncTask` из фреймворка Ивана в снимке отсутствует. Роль автоматов
  играют `Tasks.Task`; мост — общий планировщик и `Select`/`Park`, так
  что ожидание задачи из «автомата» и наоборот выражается каналами и
  `Join`, отдельного класса-моста нет.

## Этап 8: рабочие нити ОС

```
id := AsyncWork.Execute(S.ADR(SomeJob), S.ADDRESS(arg));   (* из задачи *)
status := AsyncWork.Result(id);
AsyncWork.Submit(procAdr, arg);    (* без ожидания *)
AsyncWork.Release(id);
```

`AsyncWork` (`Async/Mod64/Work.cp`) — фасад, клиентский код от платформы
не зависит. Форматы `FileReq`/`AddrReq` и `[ccall]`-процедуры заданий
объявлены в фасаде; реализацию ставит делегат `AsyncWork.Impl`:

- `AsyncWorkLin` (`Async/Mod64/WorkLin.cp`) — 4 нити pthread, статические
  слоты под pthread-мьютексом, готовность — байт в pipe, `Poller` будит
  задачу. Сигналы SIGINT/SIGTERM в нитях закрыты.
- `AsyncWorkWin` (`Async/Mod64/WorkWin.cp`) — 4 нити `CreateThread`,
  статические слоты в `[untagged]`-памяти под `CRITICAL_SECTION`,
  очередь ждёт manual-reset событие, готовность — счётчик `done` и
  auto-reset событие. Главный цикл забирает результат действием
  `Services` (переставляется через 5 мс, пока есть занятые слоты) —
  окна и цикл сообщений не блокируются. Файлы — `CreateFileA`/
  `ReadFile`/`WriteFile`, имена — `getaddrinfo` из `AsyncWinSock`
  (`Async/Mod64/WinSock.cp`, interface-модуль WS2_32). При запуске
  `WSAStartup(2.2)`; динамическая загрузка WS2_32 идёт через
  `LoadLibraryW` в `WinKernel.WkResolve`.

Регистрация делегата ленивая: первый `AsyncWork.Execute` зовёт
`Dialog.Call("<Модуль>.Install", ...)` из `AsyncWork.Ensure`; базовые
init (`LinIntInit`, `WinIntInit`, `WinInit`) пул не заводят.
Клиентский код (`Execute`, `ReadFileJob`, `WriteFileJob`, `ResolveJob`)
не меняется.

Выбор исходников под платформу. `DevLibrarian` умеет один каталог поверх
`Mod` (`Mod64`), а `CompileSubs` обходит только `<Sub>/Mod`; поэтому
файлы `WorkLin.cp`/`WorkWin.cp` вне списка и собираются явным
`CompileThis` в своём стенде: `tools/build64.sh` — `AsyncWork` и
`AsyncWorkLin`, `tools/test-win64.sh` — `AsyncWinSock`, `AsyncWork` и
`AsyncWorkWin`. Фасад при этом общий, а платформенный модуль попадает
только в свою сборку.

Готовые задания: `ReadFileJob`, `WriteFileJob`, `ResolveJob`
(`getaddrinfo`). Тела заданий не выделяют память из кучи. Отладочный
счётчик `Kernel.WorkerAllocs`/`EnterWorker` удалён: он был общим флагом
без атомарности и проверял дисциплину только косвенно; тест
`Test64Workers` оставляет медленный вызов, файл и `getaddrinfo`.

Замер (Linux): `SlowJob` (usleep 300 мс) в рабочей нити; задача ждёт
`Execute`, главный цикл за это время сделал 285 шагов, тест занял
301 мс. Значит, заморозки нет. Разрешение `localhost` и файловый обмен —
1–2 мс. Windows (`Test64WinWorkers` под wine): `Sleep(300)` — 304 мс,
главный цикл делает шаги; файл и `getaddrinfo("localhost")` — 2 мс;
`AsyncWork.Workers() = 4`.

`tools/test-resolver.sh` проверяет худший случай: `unshare -rmn` с
dummy-интерфейсом и своим resolv.conf, где сервер имён недоступен
(пакеты молча теряются, тайм-аут/попытки по умолчанию). `ResolveJob`
для несуществующего имени ждёт `getaddrinfo` 10 010 мс, главный цикл
за это время делает 9 449 шагов (`Services.actionHook.Step` +
`AsyncIO.Poll`). Без `unshare`/`ip`/`mount` сценарий печатает `SKIP` с
причиной. Обычный прогон `tools/test.sh` включает его отдельным этапом.

Ограничения: пул — Linux AMD64 и Windows x64. Рабочая нить не имеет
права трогать кучу, `Kernel.Try`, журнал и каркас; это правило ревью и
отладочного счётчика, а не барьера. Вызовы ОС, которые могут
блокироваться, уводятся целиком в нить. Примитивы синхронизации лежат в
куче (`Sync`), а не в глобальных записях модуля: глобальные записи не
получают гарантированного выравнивания, а futex/`CRITICAL_SECTION` его
требуют. На Windows готовность забирает действие `Services`, поэтому в
чисто консольном вводе с блокирующим `ReadLn` пул работает только пока
крутится цикл (`UnitRunner`, `ConsInterp` с `WaitInput`, GUI).

## Этап 9: компутоны

Интерфейс повторяет `RobustParallel` И. Денисова:

```
TYPE Computon* = POINTER TO ABSTRACT RECORD (Stores.Store) END;
     PROCEDURE (c: Computon) Do*, NEW, ABSTRACT;

AsyncComputon.Start(n);                       (* n локальных процессов *)
AsyncComputon.Push(c, rank, tag);
r := AsyncComputon.Pull(rank, tag);           (* точка ожидания *)
AsyncComputon.Try(rank, tag, r);
AsyncComputon.Stop;
AsyncComputon.Size(); AsyncComputon.Rank();   (* rank управляющего = 0 *)
AsyncComputon.LastError(); AsyncComputon.WorkerPid(rank);
```

`Do` — обычный код CP с кучей, поэтому исполняется в отдельном процессе
BlackBox (свой сборщик), а не в рабочей нити этапа 8. Компутон
сериализуется через `Stores` во временный файл; тип должен реализовать
`Externalize`/`Internalize`.

Транспорт: `fork` + `exec` того же `blackbox-console` (`/proc/self/exe`),
три pipe на исполнителя — команда на stdin, запросы, ответы. Заголовок
кадра: длина, tag, вид (работа/остановка); ответ: длина, tag, код ошибки.
Ошибка `Do` ловится `Services.Try` (в исполнителе ставится пустой
trapViewer, иначе консольный x64 считает трап фатальным) и возвращается
кодом; `Pull` даёт `NIL`, `LastError()` — код.

Ожидание `Pull` — `Tasks.Sleep(10)` с проверкой срока: у задачи есть
дедлайн, ложный журнал тупика не печатается. Гибель исполнителя видна
`Poller` по EOF; запрос повторяется на живом исполнителе, при отсутствии
живых — ошибка `-2`. Тайм-аут — ошибка `-4`.

Замеры: 12 квадратов на 1, 4 и 16 процессах дают одинаковый результат
(тест 12–19 мс после запуска). Убитый `SIGKILL` исполнитель: результат
получен повторно на живом за 414 мс. `AltPull` вместе с каналом и
тайм-аутом проверяет `TestAltPull` (205 мс).

MPI: инструменты ставятся в пользовательское пространство —
`uv pip install mpich` в `.work/venv` (MPICH 5.0.2 даёт `mpicc`,
`mpiexec`, `libmpi.so.12`). Обёртка `tools/bbmpi.c` (собирается mpicc)
скрывает структуры MPI за семью функциями, `AsyncMpi` привязывает их
через `LinDl` только при выборе транспорта — обычные прогоны
MPI-библиотеки не требуют.

### Фасад `RobustParallel`

`Robust/Mod64/Parallel.cp` — тонкий модуль поверх `AsyncComputon` с
опубликованным определением из доклада И. Денисова (2017, с. 19):

```
CONST tag* = 1;
TYPE Computon* = AsyncComputon.Computon;      (* Do, NEW, ABSTRACT *)
     Hook* = AsyncComputon.Hook;              (* Failed(rank, tag, err) *)
VAR rank-, size-: INTEGER;
PROCEDURE LogMsg / Push / Pull / Try / SetHook / Wait / Stop / Unload
```

`Hook` на слайде не приведён; взят `AsyncComputon.Hook`. Ранги как в
MPI: 0 — управляющий (клиент), 1..size−1 — процессы-исполнители;
`Push`/`Pull`/`Try` сдвигают ранг на −1. Размер мира задаёт внешняя
переменная `ROBUST_SIZE` (по умолчанию 1 — только управляющий); в
процессе-исполнителе (`ASYNC_IN`/`ASYNC_OUT`/`ASYNC_TCP`) фасад свой пул
не запускает. `Unload` в определении без результата — отказ только в
журнале.

Клиент `Test64RobustClient` написан только против этого определения в
стиле MPI: `rank = 0` режет работу на части, раздаёт `Push`, собирает
`Pull`; `Do` компутона — ветвь «остальные считают» в процессе
BlackBox. Формула доклада «инициализация → [[отправка/приём]n,
ожидание и расчёт]n → финализация» выражена телом модуля, циклом
Push/Pull и `Stop`. Результат — сумма 1..1000 = 500500 на 1, 4 и 16
процессах (`tools/test-robust.sh`, 1/11/13 мс). Совместимость доказана
по опубликованному интерфейсу; прогон настоящего кода Ивана — когда он
его предоставит.

### MPI-транспорт

Раскладка мира: ранг 0 — управляющий процесс BlackBox с тестом, ранги
1..n — процессы с командой `AsyncMpi.WorkerLoop`. Кадры те же
(12-байтовый заголовок + тело), но через `MPI_Send`/`MPI_Recv`;
готовность ответов главный цикл проверяет `MPI_Iprobe` в действии
`AsyncComputon` (`Services.DoLater` каждые 5 мс), задача ждёт `Pull` как
обычно. `SetTransport("mpi")` включается после `AsyncMpi.Install` (тот
ставит объект `AsyncComputon.Transport`); `Start(n)` требует мира из
n+1 ранга. Ограничения: гибель ранга не повторяется (mpiexec обычно
гасит мир), `Unload` по MPI возвращает отказ, `WorkerPid` неизвестен.
Тест `tools/test-mpi.sh`: 12 квадратов на 4 исполнителях под
`mpiexec -n 5`, 252 мс.

## Этап 10: протокол канала, TCP и обновление кода

### Протокол диалога

`Async/Mod/Proto.cp` (модуль `AsyncProto`) строит детерминированный
автомат из текстового описания:

```
start: RequestMsg > wait; wait: ResponseMsg > wait;
wait: EndMsg > done; done:
```

Пункт — `состояние: Сообщение > состояние`; `>` и `->` равнозначны,
разделитель пунктов — `;` или перевод строки, `состояние:` без
стрелки — конечное состояние (исходящих переходов нет). Имя
сообщения — имя динамического типа записи (`Kernel.GetTypeName` от
`Kernel.TypeOf(m^)`); BlackBox хранит имя типа-указателя с суффиксом
`^`, он срезается.

У канала появились поля `proto`/`protoState` (`AsyncSelect.Core`).
`AsyncChan.SetProtocol(c, p)` включает отладочную проверку; прямые
`Send` у `Chan`/`Buffer`/`Mailbox` зовут `AsyncSelect.CheckSend`.
Нарушение печатает текст в консоль и трапует (ASSERT 21); текст
остаётся в `AsyncProto.LastViolation`, ожидаемые сообщения — в
описании нарушения. Без протокола `CheckSend` выходит после одного
теста `NIL`. Отправки через `Select` (`SendAlt`) проверяются в момент,
когда предложение действительно исполняется: сразу в `Register` или при
снятии отложенного предложения в `TakeRendezvous`/`CompleteSend`.
Проигравшее предложение состояние протокола не меняет; нарушение
трапует задачу, исполняющую операцию.

Тесты — `Test64Protocol`: корректный диалог «Запрос → Ответ* → Конец»
(состояние `done`, `IsFinal`), нарушение порядка (`UnitAssert.Traps`),
канал без протокола, отказ разбора описания.

### TCP-транспорт

`AsyncComputon.SetTransport("pipe"|"tcp")` до `Start`; то же задаёт
внешняя переменная `ASYNC_TRANSPORT`. Программа (`Push/Pull/Try`,
`AltPull`, тесты) не меняется. Управляющий создаёт
`CommTCP.NewListener("127.0.0.1:0")`, передаёт исполнителю
`--ASYNC_TCP=127.0.0.1:PORT` и принимает одно соединение
(`AcceptOne`, ожидание вне задачи). Кадры те же: длина, tag, вид;
в TCP режиме `inFd = outFd = сокет`. Команда `WorkerLoop` по-прежнему
идёт на stdin через pipe.

Сокет из `CommTCP` неблокирующий: в исполнителе `O_NONBLOCK`
снимается — кадры там читает только он; в управляющем остаётся
неблокирующим для `Poller`, а `WriteAll` при `EAGAIN` повторяет
запись (до 1 с). Гибель исполнителя видна по EOF, `MarkDead`/`Resend`
работают как на pipe.

Тесты: `TestSquaresTcp4` — те же 12 квадратов на 4 исполнителях,
`TestKillRetryTcp` — `SIGKILL` и повтор, `TestTransportSetting` —
неизвестное имя отвергается.

### Обновление кода: `Unload`

`AsyncComputon.Unload(module): BOOLEAN` шлёт `kindUnload` всем живым
исполнителям и ждёт ответов через `Poller` (можно звать вне задачи).
Исполнитель зовёт `Kernel.UnloadMod`; следующий `Push` загружает
обновлённый `.ocf`. Отказ — `FALSE`, `LastError() = 20`: модуль
импортирован (ненулевой `refcnt`) или его кадр есть на стеке.
Отдельного отказа для своего транспортного модуля нет: кадр
`WorkerLoop` ядро видит в `StackUsesModule` так же, как любой другой.
Незагруженный модуль — успех. После выгрузки `WorkerLoop` очищает
указатель на объект выгруженного модуля, иначе следующий `Collect`
разыменует его таблицу методов.

Тест — `Test64Unload`: модуль `Test64UnloadCode` (y = x*x) собирается
в мир, затем тест перекомпилирует его в y = x*x + 1000 через
`DevCompiler64.CompileText`, зовёт `Unload("Test64UnloadCode")` и
проверяет, что следующий `Push` даёт 1009; после теста исходный `.ocf`
собирается обратно. Отдельно проверяются отказы для `AsyncComputon` и
`Kernel`.

### Детерминированная метка времени

`DevCPE` читает внешний параметр `BB_COMPILE_TIME` в формате
`ГГГГ-ММ-ДД ЧЧ:ММ:СС` и пишет его в описатель модуля вместо текущего
времени (иначе поведение прежнее). `tools/bootstrap.sh` теперь делает
три прохода: A — упакованным компилятором, B и C — собранным, оба с
фиксированной меткой; `tools/bootstrap-compare.py` сравнивает `.ocf` и
`.osf` проходов B и C побайтно, без маскирования (49 модулей,
различий 0).

## Решения без владельца (этапы 7–10)

| Вопрос | Решение | Отмена |
|---|---|---|
| Где живёт библиотека | новая подсистема `Async`, Mod (переносимое) и Mod64 (нити, процессы) | разложить по System/Comm |
| Сообщение канала | указатель на расширяемую запись `AsyncSelect.Msg`; после отправки не меняется | копирование значения или неизменяемые записи |
| Отправитель встречи | двухфазный вклад + `taken`; `Select`-предложения лежат в очередях ядра | свести прямые операции к одноальтернативному `Select` |
| Отмена в `Select` | предложения снимаются лениво по `Tasks.State` | trap-cleaner, снимающий всё сразу |
| Тайм-аут `Select` | альтернатива + действие `Services` | отдельный `Tasks.ParkTimeout` в ядре |
| Реестр fd | `System.Poller` + хук в `LinConsole` | отдельный модуль LinPoller |
| `select` в TCP | заменён на `poll` (fd_set < 1024) | оставить select и ограничить соединения |
| Очередь accept | 128 вместо 5 | брать `SOMAXCONN` из Net |
| Новые POSIX-вызовы | `LinNative` (объявления), не `LinLibc`: символы хоста не обновить | пересобрать хост-мир целиком |
| Сигналы в рабочих нитях | блокируются в теле нити | блокировать в главной перед созданием |
| Счётчик кучи | `inWorker` — глобальный флаг, а не TLS: возможны ложные срабатывания при параллельном выделении | TLS через `pthread_getspecific` |
| Остановка исполнителей | SIGKILL + закрытие pipe; `waitpid` не зовётся (SIGCHLD игнорируется, в x64 небезопасен) | ждать `waitpid` и мягко останавливать |
| Ожидание `Pull` | `Sleep(10)` с дедлайном | таймер `Services` |
| Описание протокола | автомат состояний текстом (`state: Msg > state`), не регулярное выражение | EBNF-парсер с `*`, `+`, `?`, `\|` |
| Вид сообщения | имя динамического типа записи, суффикс `^` срезается | явный целочисленный вид у `Msg` |
| Где проверяется протокол | прямые `Send` и `SendAlt` в точке исполнения предложения | проверка в `Select` через явный вид `Msg` |
| Выбор транспорта компутонов | `SetTransport` + `ASYNC_TRANSPORT`, до `Start` | поле в `Start`/отдельный модуль транспорта |
| Сокет исполнителя | блокирующий (кадры читает только он); управляющий — неблокирующий, `EAGAIN` повторяется | ожидание готовности записи через `Poller` |
| Отказ `Unload` | по `refcnt` и кадрам ядра, включая свой транспортный модуль (кадр `WorkerLoop`) | экспортировать из ядра «модуль на стеке» |
| Метка времени компиляции | внешний `BB_COMPILE_TIME` в `DevCPE`; проходы B и C бутстрапа сравниваются побайтно | нулевая метка либо маска в сравнении |

## Открыто

- Windows x64: пул рабочих нитей `CreateThread` и опрос готовности
  сделаны — фасад `AsyncWork` с делегатами `AsyncWorkLin`/`AsyncWorkWin`,
  регистрация ленивая из `AsyncWork.Ensure`; под wine идут
  `Test64WinWorkers` 4/4. GUI-прогон Windows (`WinInit`) собирается, но
  отдельного теста под wine нет.
- MPI: нет повтора при гибели ранга и `Unload` (mpiexec гасит мир).
- Перемещение `Reliable`-повторов на уровень транспорта (сейчас повтор
  один: при смерти исполнителя).
- Точные карты стека от компилятора — по-прежнему за пределами.
- GUI проверен автоматически под `gtk4-broadwayd`; меню и мышь — нет
  (эмуляция мыши запрещена).

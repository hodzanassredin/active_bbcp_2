# Библиотека ожиданий, рабочие нити и компутоны (этапы 7–9)

Подсистема `Async` — необязательная надстройка над этапами 1–6. Она не
меняет каркас: каркасные модули (System, Std, Text, Form, Dev, Lin, Win)
по-прежнему не компилируются с ключом `^` и не ждут.

```
Async/Mod/       Select.cp  Chan.cp  Once.cp  IO.cp
Async/Mod64/     Work.cp    Computon.cp
System/Mod/      Poller.cp
Lin/Mod64/       Threads.cp Native.cp
```

`Async/Mod64` компилируется только для AMD64; 32-битная цель библиотеку
не собирает. `LinThreads` и `LinNative` — отдельные модули объявлений:
`LinLibc` загружен в хост-процесс (`dev0Linux`, `blackbox-console`), и его
символьный файл нельзя расширить новыми процедурами, не пересобрав мир.

## Этап 7: ожидания и ввод-вывод

### Однократная переменная

```
o := AsyncOnce.New();
o.FillInt(42);          (* ровно один раз; повтор — трап 21 *)
x := o.ReadInt();       (* ждёт заполнения *)
```

Есть варианты `FillMsg`/`ReadMsg` для `AsyncSelect.Msg`. Объект — монитор:
методы `[exclusive]`, ожидание — `ACTIVE.AWAIT(done)`.

### Каналы

```
c := AsyncChan.NewChan();                 (* встреча *)
b := AsyncChan.NewBuffer(8);              (* ограниченная очередь *)
m := AsyncChan.NewMailbox();              (* неограниченный ящик *)
c.Send(msg); c.Recv(msg);
b.Send(msg); b.Recv(msg);
m.Send(msg); m.Recv(msg);
```

Все три — мониторы с методами `[exclusive]` и `ACTIVE.AWAIT`; встреча
двухфазовая: `Send` кладёт вклад и ждёт, пока получатель его заберёт
(`taken`). Сообщение — `AsyncSelect.Msg` (расширяемая запись-указатель);
после отправки оно не меняется (дисциплина Clojure/Erlang). Приём через
`WITH`:

```
TYPE NumMsg = POINTER TO RECORD (AsyncSelect.Msg) n: INTEGER END;
VAR m: AsyncSelect.Msg;
...
WITH m: NumMsg DO ... END
```

### Select/Alt

```
VAR ops: ARRAY 3 OF AsyncSelect.Op;
AsyncChan.RecvAlt(a, ops[0]);
AsyncChan.RecvAlt(b, ops[1]);
AsyncChan.TimeoutAlt(100, ops[2]);
i := AsyncChan.Select(ops);      (* индекс сработавшей; 2 — тайм-аут *)
m := ops[i].got;
```

Устройство — по образцу Hopac/CML: каждое предложение (offer) несёт общий
`Ctx` с флагом решения. Первый канал, готовый исполнить предложение, под
своим монитором ставит флаг, забирает/отдаёт сообщение и будит задачу
через `Tasks.Unpark`; остальные предложения снимает владелец после
пробуждения (nack). Активный вклад отправителя откатывается, если решение
принял другой канал: любая операция, наткнувшаяся на offer с решённым
`Ctx`, очищает вклад (`Prune`). Тайм-аут — обычная альтернатива; ждущая
задача спит на `Tasks.Park`, таймер — действие `Services`.

`Select` можно звать только из задачи. Альтернативой может быть и
готовность `Pull` компутона (`AsyncComputon.AltPull`) — сигнал
будит `Select` там же, где канал. Отмена задачи во время ожидания
оставляет предложения; они снимаются при следующем обращении к каналу
(проверка `Tasks.State`), отдельного trap-cleaner нет.

### Ожидание готовности дескрипторов

`System/Mod/Poller.cp` — реестр «дескриптор + событие + Waiter»;
платформенный хук ставит `LinConsole.Init`. `Console.WaitInput` опрашивает
stdin и зарегистрированные дескрипторы одним `poll`, поэтому главный цикл
просыпается от сетевого события, а в покое спит.

```
AsyncIO.Read(s, buf, beg, len, read);    (* читать хотя бы байт *)
AsyncIO.Write(s, buf, beg, len, written);(* записать хотя бы байт *)
AsyncIO.Accept(l, s, timeout);           (* принять соединение *)
```

`CommStreams.Stream/Listener` получили `Handle()`; у `CommTCP__Lin` это
сокет. Если `Handle() = -1`, ожидание вырождается в `Tasks.Sleep(1)`.

`CommTCP__Lin` переведён с `select` на `poll`: `fd_set` ограничен 1024
дескрипторами, а тысяча соединений требует больше. Заодно поднята очередь
`listen` (128).

### Замеры

`Test64IO.TestEcho1000` (localhost): 1000 одновременных соединений,
эхо-обмен, соединения остаются открытыми. Прогон занимает 2.8–3.1 с.
Пока 1000 соединений молчат, процессорное время процесса за 1 с —
7–50 мс (0.7–5 %; зависит от периода опроса).

`Test64Channels` — 9 тестов: Once, встреча (100 сообщений с проверкой
порядка), ограниченный буфер, почтовый ящик с `WITH`, Select по двум
каналам, тайм-аут, отсутствие «протухших» предложений после тайм-аута,
отправка в полный буфер, повторный `Fill`.

### Чего нет

- Протокол канала по образцу Zonnon (грамматика сообщений и отладочная
  проверка последовательности) не сделан; задел описан в плане.
- `AsyncTask` из фреймворка Ивана в снимке отсутствует. Роль автоматов
  играют `Tasks.Task`; мост — общий планировщик и `Select`/`Park`, так
  что ожидание задачи из «автомата» и наоборот выражается каналами и
  `Join`, отдельного класса-моста нет.

## Этап 8: рабочие нити ОС

```
id := AsyncWork.Execute(S.ADR(SomeJob), S.ADDRESS(arg));   (* из задачи *)
status := AsyncWork.Result(id);
AsyncWork.Submit(procAdr, arg);    (* без ожидания *)
AsyncWork.Release(id);
```

Пул — 4 нити pthread. Тело — `[ccall]`-процедура над `[untagged]`-памятью:
задания и результаты лежат в статических слотах, очередь под
pthread-мьютексом, о готовности нить пишет байт в pipe. Главный цикл
видит его через `Poller` и в `Scan` будит задачу. В рабочих нитях
закрыты SIGINT/SIGTERM.

Готовые задания: `ReadFileJob`, `WriteFileJob`, `ResolveJob`
(`getaddrinfo`). `Kernel.EnterWorker/LeaveWorker` и
`Kernel.WorkerAllocs()` — отладочный счётчик: `NEW` из рабочей нити
увеличивает его. Это именно счётчик (не запрет): `NEW` по-прежнему
выделяет, поэтому тест дисциплины гоняют при почти пустом главном цикле.

Замер: `SlowJob` (usleep 300 мс) в рабочей нити; задача ждёт `Execute`,
главный цикл за это время сделал 285 шагов, тест занял 301 мс. Значит,
заморозки нет. Разрешение `localhost` и файловый обмен — 1–2 мс.

Ограничения: пул — Linux AMD64; Windows x64 не сделан. Рабочая нить не
имеет права трогать кучу, `Kernel.Try`, журнал и каркас; это правило
ревью и отладочного счётчика, а не барьера. Вызовы ОС, которые могут
блокироваться, уводятся целиком в нить.

## Этап 9: компутоны

Интерфейс повторяет `RobustParallel` И. Денисова:

```
TYPE Computon* = POINTER TO ABSTRACT RECORD (Stores.Store) END;
     PROCEDURE (c: Computon) Do*, NEW, ABSTRACT;

AsyncComputon.Start(n);                       (* n локальных процессов *)
AsyncComputon.Push(c, rank, tag);
r := AsyncComputon.Pull(rank, tag);           (* точка ожидания *)
AsyncComputon.Try(rank, tag, r);
AsyncComputon.Stop;
AsyncComputon.Size(); AsyncComputon.Rank();   (* rank управляющего = 0 *)
AsyncComputon.LastError(); AsyncComputon.WorkerPid(rank);
```

`Do` — обычный код CP с кучей, поэтому исполняется в отдельном процессе
BlackBox (свой сборщик), а не в рабочей нити этапа 8. Компутон
сериализуется через `Stores` во временный файл; тип должен реализовать
`Externalize`/`Internalize`.

Транспорт: `fork` + `exec` того же `blackbox-console` (`/proc/self/exe`),
три pipe на исполнителя — команда на stdin, запросы, ответы. Заголовок
кадра: длина, tag, вид (работа/остановка); ответ: длина, tag, код ошибки.
Ошибка `Do` ловится `Services.Try` (в исполнителе ставится пустой
trapViewer, иначе консольный x64 считает трап фатальным) и возвращается
кодом; `Pull` даёт `NIL`, `LastError()` — код.

Ожидание `Pull` — `Tasks.Sleep(10)` с проверкой срока: у задачи есть
дедлайн, ложный журнал тупика не печатается. Гибель исполнителя видна
`Poller` по EOF; запрос повторяется на живом исполнителе, при отсутствии
живых — ошибка `-2`. Тайм-аут — ошибка `-4`.

Замеры: 12 квадратов на 1, 4 и 16 процессах дают одинаковый результат
(тест 12–19 мс после запуска). Убитый `SIGKILL` исполнитель: результат
получен повторно на живом за 414 мс. `AltPull` вместе с каналом и
тайм-аутом проверяет `TestAltPull` (205 мс).

MPI: в системе нет `mpicc`/`mpirun`/`libmpi`, поэтому транспорт MPI не
делался. Интерфейс от транспорта не зависит; при появлении MPI его
можно добавить за `Push/Pull`, не меняя программы. TCP-транспорт тоже не
сделан.

## Решения без владельца (этапы 7–9)

| Вопрос | Решение | Отмена |
|---|---|---|
| Где живёт библиотека | новая подсистема `Async`, Mod (переносимое) и Mod64 (нити, процессы) | разложить по System/Comm |
| Сообщение канала | указатель на расширяемую запись `AsyncSelect.Msg`; после отправки не меняется | копирование значения или неизменяемые записи |
| Отправитель встречи | двухфазный вклад + `taken`; `Select`-предложения лежат в очередях ядра | свести прямые операции к одноальтернативному `Select` |
| Отмена в `Select` | предложения снимаются лениво по `Tasks.State` | trap-cleaner, снимающий всё сразу |
| Тайм-аут `Select` | альтернатива + действие `Services` | отдельный `Tasks.ParkTimeout` в ядре |
| Реестр fd | `System.Poller` + хук в `LinConsole` | отдельный модуль LinPoller |
| `select` в TCP | заменён на `poll` (fd_set < 1024) | оставить select и ограничить соединения |
| Очередь accept | 128 вместо 5 | брать `SOMAXCONN` из Net |
| Новые POSIX-вызовы | `LinNative` (объявления), не `LinLibc`: символы хоста не обновить | пересобрать хост-мир целиком |
| Сигналы в рабочих нитях | блокируются в теле нити | блокировать в главной перед созданием |
| Счётчик кучи | `inWorker` — глобальный флаг, а не TLS: возможны ложные срабатывания при параллельном выделении | TLS через `pthread_getspecific` |
| Остановка исполнителей | SIGKILL + закрытие pipe; `waitpid` не зовётся (SIGCHLD игнорируется, в x64 небезопасен) | ждать `waitpid` и мягко останавливать |
| Ожидание `Pull` | `Sleep(10)` с дедлайном | таймер `Services` |

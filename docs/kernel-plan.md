# План правок ядра

Документ перечисляет, что в ядре (`System/Mod64/Kernel.cp`, `System/Mod/Kernel.cp`) следует
исправить или упростить, почему и как проверить. Правки компилятора и библиотеки упомянуты
только там, где без них правка ядра не имеет смысла.

Пометки достоверности:

- **проверено** — подтверждено прогоном или чтением кода;
- **по коду** — вывод из чтения кода, прогоном не подтверждён;
- **не проверено** — предположение, перед работой нужно подтвердить.

Порядок разделов — по приоритету: сначала возможное неверное поведение, затем упрощение, затем
скорость, затем подготовка к нитям. Последний раздел — находки в исходном коде снимка, не
относящиеся к расширению.

## 1. Корректность

### 1.1. Сборка мусора на незнакомом стеке

**Сейчас (проверено, тест `System_devGcStack`).** `MarkLocals` обходит реестр стеков. Если
текущий указатель стека не принадлежит ни одной записи реестра, сборка отменяется целиком:
ядро не знает, где на этом стеке лежат указатели, и не имеет права освобождать память.

**Почему плохо.** Отмена безопасна, но молчалива. Если код постоянно работает на
незарегистрированном стеке (обратный вызов из библиотеки C, сопрограмма сторонней библиотеки),
мусор не собирается вовсе, и процесс растёт до исчерпания памяти без сообщения.

**Что сделать.**

1. Считать отменённые сборки (`skippedCollections`) и при первом случае и далее на каждой
   степени двойки печатать строку через `platform.String`: адрес SP и число пропусков.
2. Для обратных вызовов из C (`[ccall]`-пролог в `DevCPCamd64.Enter`) регистрировать стек
   автоматически: при входе на незнакомом стеке спросить у платформы границы текущего стека нити
   (`pthread_getattr_np` в Linux, `VirtualQuery` в Windows) и завести временную запись реестра;
   снять при выходе. Это новый метод платформы `CurrentStackBounds(OUT lo, hi)`.
3. Если границы получить нельзя — оставить отмену, но с сообщением из пункта 1.

**Проверка.** Функция C вызывает процедуру CP на стеке, выделенном `mmap` без регистрации;
процедура порождает мусор и зовёт `Kernel.Collect`. С пунктом 2 мусор собран; без границ
напечатано предупреждение. `System_devGcStack` остаётся зелёным.

### 1.2. Граница скана спящего стека

**Сейчас (проверено чтением).** `SwitchSave` записывает `s.sp := SP - switchSaveSlack`, где
запас — 256 байт на amd64 и 64 на i386, с зажимом по нижней границе стека. Переключатель в
`Tasks` кладёт регистры ниже SP; запас нужен, чтобы они попали в скан.

**Почему плохо.** Число подобрано под текущий переключатель. Если переключатель начнёт сохранять
больше, указатель в сохранённом регистре окажется вне скана, и объект будет освобождён живым.

**Что сделать.** Точную границу знает только переключатель. Варианты:

- переключатель сам пишет итоговый SP в запись стека после всех `push` (поле `sp` экспортировать
  для записи владельцу стека или дать процедуру `Kernel.SetSavedSP(s, sp)`); `SwitchSave`
  сохраняет только состояние `Try`;
- либо оставить запас, но связать его с переключателем константой в одном месте и проверять в
  тесте: размер области сохранения не больше запаса.

Первый вариант правильнее; второй — правка в две строки.

**Проверка.** Задача держит единственную ссылку на объект в регистре, который сохраняет
переключатель, уступает, другая задача зовёт `Kernel.Collect`; объект жив. Близкий тест —
`System_devRegs`; его следует расширить.

### 1.3. Индексы стеков и кластеров

**Сейчас (проверено чтением).** `clusterIndex` и `stackIndex` — статические массивы по 16 384
записи. При переполнении ставится флаг `clusterIndexFull` / `stackIndexFull`, поиск уходит в
линейный обход списка. Флаг сбрасывается только при инициализации ядра: вернуться к двоичному
поиску после того, как число записей упало, нельзя. Индекс стека есть только на amd64; на i386
поиск всегда линейный.

**Почему плохо.** Один всплеск (20 тыс. задач на секунду) навсегда замедляет `StackOf`, а он
вызывается на каждом переключении задач и на каждом трапе. Для кластеров то же относится к
`InHeap` в сборщике.

**Что сделать.** Массив переменной длины, память под него берётся у платформы (не из кучи: индекс
нужен самому сборщику). При заполнении — выделить вдвое больший, скопировать, старый вернуть.
Флаг «переполнен» и линейный путь остаются только на случай отказа платформы в памяти; после
освобождения записей индекс перестраивается из списка. Индекс стека добавить и на i386.

**Проверка.** Зарегистрировать 20 тыс. стеков, снять все, зарегистрировать один; `StackOf`
находит его через индекс (счётчик линейных обходов равен нулю). Для кластеров — чёрный ящик
`System_devInHeap`: куча растёт на сотни кластеров, живые объекты держатся глобалами, после
`Collect` живые целы, мусор собран (`Kernel.Allocated`). Внутренний инвариант индекса проверяет
`ASSERT` в `IndexInsert`/`IndexRemove` при `debug`.

### 1.4. Диапазон главного стека

**Сейчас (проверено чтением).** Запись главного стека: `hi` — самый старший виденный SP,
`lo := hi - maxStackScan`, то есть условные 64 МБ. Настоящий стек процесса обычно 8 МБ. Диапазон
может пересекаться со стеками задач, выделенными `mmap`; `StackOf` выбирает самый узкий
подходящий диапазон.

**Почему плохо.** Правило «самый узкий» работает, но держится на допущении. Адрес в чужой
памяти, попавший в условные 64 МБ, считается адресом главного стека.

**Что сделать.** Взять настоящие границы у платформы тем же методом `CurrentStackBounds` из 1.1
при старте ядра. `UpdateMainStack` и правило «самый узкий» после этого убрать.

**Проверка.** Адрес на 16 МБ ниже вершины главного стека не принадлежит ни одному стеку реестра.

### 1.5. Запрет выгрузки занятого модуля

**Сейчас (проверено чтением).** `UnloadMod` отказывает, если `StackUsesModule` находит код
модуля на любом стеке. `FrameInModule` идёт по цепочке сохранённых указателей кадра; если
цепочка обрывается (кадр функции C между кадрами CP), выше обрыва делается консервативный скан
слов (`WordsInModule`).

**Почему плохо.** Два разных способа с разной точностью. Обход по цепочке точен, но зависит от
проверки выравнивания кадра (см. 5.1). Скан слов надёжен, но даёт ложные запреты: старый адрес
возврата в мёртвой области стека мешает выгрузке.

**Что сделать.** После решения 5.1 вернуть строгую проверку выравнивания. Отдельно — подсчитать
на тестах GUI, как часто срабатывает запасной скан; если редко, оставить как есть.

**Проверка.** `System_devUnloadGuard` (кадр на главном стеке и на стеке спящей задачи) плюс
случай с обратным вызовом из C между кадрами.

### 1.6. Рабочие нити и куча

**Сейчас (проверено чтением).** Выделение памяти и сборщик рассчитаны на одну нить. Рабочие
нити (`AsyncWork`) по соглашению не трогают кучу. `NewBlock` не проверяет, на каком стеке
происходит выделение.

**Почему плохо.** Соглашение ничем не защищено. `NEW` из рабочей нити даст порчу кучи, которая
проявится позже и в другом месте.

**Что сделать.** Вернуть проверку в дешёвом виде: при входе в `NewBlock` сравнить текущий SP с
реестром стеков — стек рабочей нити в реестре не числится, и выделение на нём даёт трап с
понятным номером. Реестр уже есть, отдельный флаг не нужен. Цена — один `StackOf` на выделение;
замерить и, если заметно, включать только в отладочной сборке ядра.

**Проверка.** Тест «рабочая нить не трогает кучу»: `NEW` в теле работы даёт трап, а не порчу.

## 2. Упрощение

### 2.1. Экспорты

Ядро экспортирует процедуры, которые нужны расширению и тестам. Часть из них можно убрать или
слить:

| Экспорт | Пользователи | Что сделать |
|---|---|---|
| `AllocStack`, `FreeStack` | `Tasks` | обёртки над `platform.AllocateStackMem`; убрать вместе с переносом `Tasks` |
| `RegisterSignalStack` | `LinKernel.InitSignalStack` | слить с `RegisterStack` параметром |
| `Wait` | тесты, `Docu/ru/Async.md` | оставить: документированное ручное ожидание |
| `RequestPoll` | `Tasks` (планировщик), `Dev_devYield` | перенести в `Scheduler` |
| `AllocCount` | `System/Mod/Loop` | оставить: пропуск сборки без выделений |
| `platform-`, `sched-` | `Monitors` | обходятся только сменой API крючков |

Диагностика `Monitors`: `IsLocked`, `WaitersCount`, `DumpMonitors`, `LockDepth` — документированный
API; `IsLocked` и `WaitersCount` используют тесты мониторов. `Tasks`: `List`, `ListSize`,
`Switches`, `ResetStats` — документированная диагностика и замеры.

Каждое удаление меняет отпечаток `Kernel`, поэтому делать одной правкой с пересборкой мира и
самосборкой компилятора.

### 2.2. Остатки мониторов в ядре

- `CallCond` — процедура `[code]` на 9 байт, вызывает условие ожидания с чужим кадром. Ядру она
  не нужна, её зовёт только `Monitors`. Перенести в `Monitors` (для двух разрядностей — два
  варианта или условный код).
- `SetQuiet` и счётчик `quietCleanup` — «трап в чужом условии не запускает уборку стека». Это
  знание о мониторах внутри обработчика трапов. Заменить общим механизмом: `Monitors` вычисляет
  условие под `Kernel.Try`, а переадресацию трапа ждущей задаче делает его обработчик.
- Тип `CondProc` остаётся в ядре: его отпечаток включён в сигнатуру `Kernel.Await`, которую зовёт
  компилятор.

### 2.3. Дублирование

`System/Mod/Kernel.cp` и `System/Mod64/Kernel.cp` — два отдельных файла; каждая правка
расширения вносится дважды. `System/Mod/Tasks.cp` и `System/Mod64/Tasks.cp` различаются
переключателем регистров и размерами слов.

**Что сделать.**

1. `Tasks`: общий модуль в `System/Mod/Tasks.cp`, платформенная часть — отдельный маленький
   модуль (`TasksSwitch` в `Mod` и `Mod64`): переключатель `[code]`, раскладка начального кадра,
   константы.
2. Реестр стеков в ядре: код одинаков для двух разрядностей, кроме размера слова. Ядро не
   импортирует ничего, поэтому общий модуль невозможен; держать блок текстуально одинаковым и
   сверять сценарием `tools/`, как сверяется самосборка.
3. Слияние двух `Kernel.cp` в один — решение автора ядра (см. 5.4).

## 3. Скорость

### 3.1. Сборка мусора при тысячах стеков

**Сейчас (по коду).** `MarkLocals` сканирует каждый стек реестра от сохранённого SP до вершины с
шагом 4 и для каждого слова проверяет попадание в кучу. Границы кучи считаются один раз на
сборку. Кандидаты каждого стека проверяются отдельным вызовом `CheckCandidates`.

**Что сделать.** Сначала замер: `tools/bench-gc.sh` при 1, 1000 и 10 000 спящих задачах, время
одной сборки и доля скана стеков. Если доля заметна:

- собирать кандидатов со всех стеков в один массив и проверять одним проходом;
- для спящей задачи скан начинается от сохранённого SP — пустая часть стека уже не читается;
  проверить, что это так и для только что созданных задач.

Без замера ничего не менять.

### 3.2. Статические индексы

Два массива по 16 384 указателя — 256 КБ статических данных ядра у любого процесса, включая не
использующий задачи. Уходит вместе с правкой 1.3: начальный размер индекса — одна страница.

## 4. Подготовка к нитям

Сейчас задачи кооперативные и живут в одной нити ОС. Если код CP будет исполняться в нескольких
нитях, в ядре придётся изменить следующее (по коду):

- **Состояние `Try`.** `trapStack`, `tryCount` и контекст платформы — глобальные переменные,
  которые `SwitchSave`/`SwitchRestore` перекладывают в запись стека и обратно. Для нитей
  источником должна стать сама запись текущего стека (или область данных нити), без глобальных
  копий.
- **Состояние трапа.** Глобальные `sp`, `fp`, `pc` прерванного кода заполняются обработчиком
  сигнала — одна копия на процесс.
- **Выделение памяти.** `NewBlock` и списки свободных блоков не защищены. Нужен либо общий замок,
  либо буфер выделения на нить.
- **Сборщик.** Обходит стеки, считая, что все остальные спят. Для нитей нужна остановка мира:
  точки безопасности (их роль может сыграть `Kernel.Poll` при компиляции с ключом уступок).
- **Реестр стеков и индексы.** Вставка и удаление без защиты.
- **Раскладка данных.** Восьмибайтные поля со сдвигом 4 (см. 5.2) не дают атомарной записи
  указателя, если он пересекает границу кеш-строки.

Это не задачи на сейчас. Раздел нужен, чтобы новые правки не добавляли глобального состояния:
всё новое, что относится к исполнению, кладётся в запись стека.

## 5. Находки в исходном коде снимка

Эти места не относятся к расширению. Менять их — решение автора 64-битного ядра и генератора.

### 5.1. Стек выровнен на 4, а не на 8

**Проверено замером.** Пробный модуль печатал остаток указателя кадра от деления на 8 в
вызванной процедуре: при одной локальной `INTEGER` у вызывающей — 0, при одной `LONGINT` — 4,
при трёх `INTEGER` — 0. Область локальных переменных 64-битный генератор выделяет кратной 4;
после `sub rsp, размер` указатель стека получает сдвиг 4, и кадры ниже наследуют его.

**Почему работает.** Процессору выравнивание стека не нужно; перед вызовом функции C генератор
выравнивает стек на 16 сам (`PreCcall16`/`PostCcall16`); вещественная арифметика идёт через x87,
инструкций, требующих выровненной памяти, нет.

**Чем плохо.**

- Сборщик обязан сканировать стек с шагом 4. Скан с шагом 8 уже был ошибкой в исходном коде:
  комментарий в `ScanStack` описывает объект, освобождённый живым, потому что единственная
  ссылка лежала в слоте со сдвигом 4.
- Проверка кадра «кратен 8» в обходе кадров обрывала обход; она заменена на «кратен 4» в
  `FrameInModule` и `GetRefFrame` — это ослабление защиты от мусора.
- Восьмибайтное значение со сдвигом 4 иногда пересекает границу кеш-строки (влияние на скорость
  не измерялось).
- Системная раскрутка исключений Windows может требовать выровненных кадров (не проверено; под
  wine тесты с трапами проходят).

**Что сделать.** В `DevCPCamd64` выделять область локальных переменных кратной 8 (лучше держать
RSP кратным 16 на всём теле процедуры — тогда выравнивание перед вызовами C сводится к
константе). После этого вернуть скан по 8 байт и строгую проверку кадра. Правка меняет код
каждой процедуры: пересборка мира, самосборка компилятора с побайтным сравнением, полный прогон
тестов на трёх платформах.

### 5.2. Восьмибайтные поля упакованы по 4

Тот же комментарий в `ScanStack` говорит, что компилятор пакует 8-байтные поля записей на
границу 4. Для кучи это значит: указатель в объекте может лежать со сдвигом 4. Сейчас безвредно
(метки сборщика идут по описателям типов, а не сканом), но мешает разделу 4. Правка раскладки
полей меняет размеры записей и формат символьных файлов — отдельное большое решение.

### 5.3. Адреса модулей ниже 4 ГБ

`AllocModMem` выделяет память модуля с флагом `MAP_32BIT`, адреса кода и данных хранятся в
`INTEGER` (`SHORT(base)`). Описатель, метаданные, код и переменные лежат в одном куске, каждый
блок округлён до страницы — это нужно для 32-битных смещений из кода. Но `MAP_32BIT` в Linux
ограничивает область первыми 2 ГБ адресов: суммарный объём загруженных модулей ограничен, а при
исчерпании загрузка модуля откажет. Что сделать: хранить адреса модулей в `ADDRESS`, снять
`MAP_32BIT`, выделять память модулей одним зарезервированным диапазоном (чтобы смещения между
модулями помещались в 32 бита). Объём правки не оценивался.

### 5.4. Два файла ядра

32-битное и 64-битное ядро — отдельные файлы, расходящиеся примерно на 400 строк по объёму и
неизвестно насколько по содержанию. Любая правка вносится дважды и проверяется дважды. Слияние в
один файл с платформенными вставками — на усмотрение автора.

### 5.5. Строгий отбор кандидатов

`strictStackSweep = TRUE` (`System/Mod64/Kernel.cp`): слово со стека считается ссылкой, только
если оно кратно 16 и указывает на начало блока. Указатель внутрь объекта (например, адрес поля,
оставшийся в регистре или на стеке после `VAR`-параметра) объект не удерживает. По коду исходного
ядра это намеренное решение; записано как место, которое надо помнить при добавлении любого кода,
держащего внутренние адреса через точку уступки.

## 6. Порядок работ

1. 1.6 (куча из рабочей нити) — малая правка, закрывает молчаливый отказ.
2. 1.1 и 1.4 вместе — оба требуют метода платформы `CurrentStackBounds`.
3. 1.3 с 3.2 — растущие индексы.
4. 1.2 — точная граница скана.
5. 2.1 и 2.2 одной правкой — отпечаток `Kernel` меняется один раз.

# 0001. Задачи со своим стеком в одной нити ОС

Статус: принято. Дата: 23.11.2026.

## Задача

BlackBox исполняет код Component Pascal в одной нити ОС, а каркас (окна, модели, журнал) написан в
расчёте на это. Нужно было дать программисту ожидание посреди алгоритма: сетевой диалог, производитель
и потребитель, сон по сроку. Ограничения: сборщик мусора консервативно сканирует стек и не знает
точной раскладки кадров; компилятор не выдаёт карт указателей; каркас нельзя переписывать целиком;
ожидание должно быть возможно из любой глубины вызовов.

## Решение

Задача — запись с методом `Run` и собственным стеком. Все задачи исполняет одна нить ОС, переключение
кооперативное: задача отдаёт процессор сама, в точках переключения. Стек выделяется сразу на всю длину
(`mmap` со сторожевой страницей, физическая память по касанию) и не растёт. Переключатель — процедура
`[code]` `Taskarch.Switch`, без внешней библиотеки. Итоговое устройство — `docs/implementation.md`,
разделы 1–3; правила — `Docu/ru/Tasks.md`.

## Рассмотренные варианты

**Нити ОС с общей кучей.** Настоящая многоядерность. Отвергнут: пометка сборщика по алгоритму
Deutsch–Schorr–Waite временно портит живые объекты, трапы и списки ядра — по одному на процесс,
каркас однонитевый. Active BlackBox Ермакова (2006) шёл этим путём: замки понадобились примерно в
60 местах каркаса, автор снял проект как неперспективный и сам оставил интерфейс однонитевым с очередью
в главный цикл. Правила «задела на многопоточность» в плане держат этот путь открытым.

**Вытеснение по сигналу (как Go 1.14).** Цикл без вызовов не замораживает планировщик. Отвергнут:
нужны точные карты стека и правки всего каркаса, ведь переключение посреди `WriteChar` ломает
инварианты моделей. Вместо него — точки уступки по ключу компилятора (запись 0006).

**Автоматы без стека (async/await в C# и Rust, protothreads, QP, продолжения Hopac).** Задача стоит
байты, а не килобайты. Отвергнут для основного механизма: локальные переменные не переживают
ожидание, ждать можно только в верхней функции, а для `async` нужна большая правка компилятора и
«раскраска» всего кода. Многошаговый протокол автоматом пишется тяжело. Бесстековый `AsyncTask`
из сборки Денисова оставался для случаев с миллионами задач.

**Растущий стек (Go — копированием, ранний Go и Rust — сегментами).** Стек начинается с 2 КБ.
Отвергнут: копирование требует точной карты указателей каждого кадра, а в Component Pascal адреса
внутри стека лежат в параметрах `VAR`, статической связи и временных значениях. Указатели на стек
не перемещаемы. Сегменты бросили и в Go, и в Rust из-за «hot split».

**Волокна ОС и `ucontext`.** Сопрограммы Темпла в линии BlackBox Center сделаны на волокнах Windows
и работают только на Windows x86-32. Временный переключатель на `ucontext` в `libtest64.so` жил
один шаг работ и был заменён процедурой `[code]` на 71 байт: внешняя `.so` не нужна.

## Следствия

- Две задачи между точками переключения не мешают друг другу: общий счётчик обходится без монитора.
- Задача стоит резерва адресов на весь стек; число задач упирается в память, а не в число отображений
  ОС. Свежий стек стоит 5,4–5,9 мкс системных вызовов (`docs/measurements.md`, раздел 2.1).
- Цикл без точек переключения замораживает все задачи и главный цикл.
- Блокирующий вызов ОС в задаче останавливает всех: такие вызовы уходят в рабочие нити (запись 0007).
- Долг: многоядерность на общей куче и растущие стеки требуют точных карт стека от компилятора.

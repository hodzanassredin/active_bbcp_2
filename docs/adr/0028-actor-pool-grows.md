# 0028. Пул исполнителей акторов растёт под ожидание в обработчике

Статус: принято, в работе. Дата: 25.11.2026.

## Задача

Ожидание в обработчике актора (канал, `AWAIT`, сон, ввод-вывод, `Ask` с ожиданием) занимает
исполнителя пула `ActorRun` на всё время ожидания. Пул фиксирован: не больше `maxExec = 64` задач,
массив `execs`. Когда все исполнители ждут, ящики с готовыми письмами стоят, хотя работа в них есть.
Владелец принял правило «масштаб — акторы, глубина ожиданий — задачи»: ожидание в обработчике —
разрешённый приём, ценой одного стека на каждого одновременно ждущего. Значит, пул должен расти под
число ждущих и возвращаться к исходному числу, когда ожидания кончились. Горячий путь (ни один
обработчик не ждёт) подорожать не должен: ни выделений, ни поиска на письмо.

## Решение (план до кода)

1. Единственная точка роста — `Pool.Schedule`, когда ящик впервые получает работу: кооперативная
   модель, других задач в этот момент нет, гонок не будет. Расти в момент ухода исполнителя в
   ожидание не нужно: уход сам по себе работы не создаёт.
2. `Schedule` кладёт ящик в кольцо `run`, затем берёт свободного исполнителя из списка `idle`
   (вход в `Tasks.ParkExternal`), иначе из списка `sleep` (лишний исполнитель спит `shrinkMs`),
   иначе — если `n < limit` — запускает нового исполнителя. Нет предела — `limitHits` плюс один,
   ящик ждёт, как раньше.
3. Массив `execs` фиксированного размера заменяется динамическим массивом указателей с запасом;
   он растёт удвоением только при росте пула, на письмо выделений нет.
4. Свободные исполнители — врезной двусвязный список с `idleCount`: взять и вернуть за O(1),
   без обхода массива. Это дешевле прежнего поиска `WHILE ~execs[i].idle`.
5. Лишний исполнитель, не найдя работы, спит `shrinkMs`; проснувшись по сроку и не найдя работы,
   завершается, пока `n > base` (`base` — число из `Start`). Пришедшая работа будит его раньше,
   и он работает; усадка идёт только после настоящего простоя.
6. Предел — `limit`, по умолчанию 1024, меняется `SetLimit`. Память: стек задачи 256 КиБ, 1024
   стека — 256 МиБ виртуального пространства со сторожевой страницей; физическая память — только
   затронутые страницы. Достижение предела не трап.
7. `ActorSim` не трогаем: рост живёт только в реализации `Dispatcher.Schedule` пула; общий
   `Dispatcher.Process` не меняется, трассы по зёрнам остаются прежними.

## Рассмотренные варианты

**Расти при уходе исполнителя в ожидание.** Исполнитель не знает, есть ли готовые ящики: уход в
ожидание сам работы не создаёт, а проверка очереди на каждом ожидании — лишняя работа. Точка
`Schedule` дешевле и точнее: она вызывается ровно тогда, когда появился готовый ящик.

**Оставить поиск свободного исполнителя по массиву.** На письмо приходится обход до 64 записей;
при пределе 1024 это уже заметно. Список свободных снимает поиск и заодно даёт признак «свободных
нет» за O(1).

**Своя задача каждому актору.** Отвергнут владельцем в записи 0018: тысяча акторов — тысяча
стеков. Растущий пул даёт стек только одновременно ждущим, а не всем акторам.

## Следствия

- Пул растёт под число одновременно ждущих обработчиков и усаживается к числу из `Start`.
- Горячий путь: `Schedule` — O(1) без выделений; память под массив исполнителей выделяется
  только при росте.
- По достижении предела поведение прежнее: готовые ящики ждут, `limitHits` считает случаи.
- `ActorSim` и прогоны по зёрнам не меняются.

## Не установлено

- Точная физическая память ждущего исполнителя не измерена отдельно; приводится RSS замера пула.
- Цена роста пула на 1000 ожиданий не сравнивалась с ценой тысячи задач `dedicated`.

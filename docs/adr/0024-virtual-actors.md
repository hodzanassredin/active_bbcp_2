# 0024. Виртуальные акторы

Статус: принято, сделано. Дата: 24.11.2026.

## Задача

Этап 4 по решению владельца. Счёт номер 42 должен быть доступен по номеру, где бы он ни жил: актор
адресуется видом и ключом, а не узлом и именем. Он поднимается при первом письме на каком-то узле,
состояние берёт из журнала (`ActorPersist`), после простоя уходит (снимок и выгрузка). Активное
воплощение ключа в кластере одно; узел пропал — ключ поднимается на другом. Ограничения: без
согласования (Raft — этап 5), на том, что уже есть: `ActorNet`, `ActorPersist`, детерминированная
проверка `ActorNetMem`/`ActorSim`.

## Решение

- **Модуль `ActorGrain`.** Кластер узла (`Cluster`) знает свой узел `ActorNet`, статический список
  членов с пропусками их хозяев и общий журнал. Вид регистрируется фабрикой: `Register(cl, kind, f)`.
  Адрес ключа — `Ref(cl, kind, key)`, наследник `ActorCore.Ref`: `Tell`, `Ask` и `Respond` работают
  с ним как с любым адресом.
- **Размещение — рандеву-хеш** (наибольший вес): владелец ключа — живой член с наибольшим
  `хеш(член + вид + ключ)`. Как `disthash`/`Rendezvous` в protoactor-go: при уходе члена переезжают
  только его ключи, при возврате — возвращаются. Владелец считается при каждой отправке, кеша
  размещения нет.
- **Хозяин.** Корневой актор узла (имя узла) — хозяин воплощений. Письмо ключу идёт хозяину
  владельца конвертом (`вид`, `ключ`, письмо); хозяин находит или поднимает ребёнка `вид.ключ` и
  передаёт ему письмо с исходным отправителем — ответ идёт прямо отправителю.
- **Состояние.** Воплощение — `ActorGrain.Actor`, персистентный актор. Его поток журнала — `вид.ключ`
  без имени узла (новое поле `ActorPersist.Actor.stream`), поэтому на другом узле поднимается то же
  состояние. Журнал общий для кластера (как общая база): узлы делят хранилище, а не память.
- **Пассивация.** Хозяин считает тики простоя каждого воплощения; после `idle` тиков без писем
  воплощение сохраняет снимок и останавливается. Тик — письмо хозяину (`Tick`): в
  детерминированном прогоне — шаг водителя, на живом узле — таймер.
- **Членство.** Статический список плюс потеря: хозяин наблюдает хозяев других членов
  (`Watch` удалённого адреса), `Terminated` с причиной `byNodeLoss` помечает член мёртвым, и его
  ключи переезжают. Возврат члена — `Rejoin`.
- **Одно воплощение.** Без согласования при разделении сети два узла могут считать владельцем
  каждый себя и поднять два воплощения. Запись защищает проверка версии журнала: второе
  воплощение, записывая событие, получает `conflict` (трап `conflictTrap`), надзор останавливает
  его, следующее письмо поднимает его заново уже с чужим событием.
- **Повтор.** Как в саге: команда несёт номер операции, воплощение помнит итоги (событиями) и на
  повтор отвечает тем же итогом.

## Рассмотренные варианты

**Кольцо согласованного хеша с виртуальными точками.** Даёт то же свойство «уходит мало ключей», но
требует таблицы точек; рандеву-хеш при десятках узлов дешевле и без состояния. protoactor-go
использует рандеву (`cluster/identitylookup/disthash`, `rendezvous.go`).

**Реестр активаций (каталог «ключ → узел»), как `partition`-поиск protoactor-go.** Точнее при
разделении, но сам требует согласования или владельца реестра; это этап 5.

**Пассивация по `ReceiveTimeout` воплощения**, как в protoactor-go (`SetReceiveTimeout` в контексте
зерна). Тайм-аут простоя живёт в реальном времени и ломает повтор прогона по зерну; тик хозяина
работает и в `ActorSim`, и на живом узле.

**Поток журнала по имени ящика.** Имя содержит узел (`B/acct.42`), и на другом узле состояние не
нашлось бы. Отдельный поток `вид.ключ` требует поля в `ActorPersist.Actor`; поле необязательно,
пустое — прежнее поведение.

**Обобщённые зёрна с кодогенерацией** (protoactor-go `protoc-gen-go-grain`). Здесь письма — те же
`ActorNet.Msg`, генератора нет.

## Следствия

- В `ActorPersist.Actor` поле `stream`; в `ActorNet` — `WriteMsg`/`ReadMsg` для письма внутри
  письма (конверт).
- `Watch` адреса ключа не поддержан: воплощение может уйти и вернуться, его конец — не событие для
  клиента.
- Граница: при разделении сети возможны два воплощения одного ключа одновременно; писать может
  только одно (проверка версии журнала), читать старое состояние может и второе. Журнал общий и
  считается доступным всем узлам; разделение хранилища вне объёма.
- `ActorPersist.Actor.Receive` стал расширяемым (`EXTENSIBLE`): воплощение перехватывает письмо
  пассивации. Интерфейс для пользователя меняется (вопрос владельцу): метод можно переопределить, а
  переопределивший обязан звать базовый.
- Хозяин ищет воплощение перебором списка: обращение дорожает с числом активных ключей узла
  (2000 ключей — 40 мкс на письмо). Таблица по имени — следующий шаг, если понадобится.
- Замеры (`Actor_devGrain.Bench`, 2000 ключей): подъём с первой записью 200–209 мкс, письмо
  активному 39–44 мкс, пассивация 47–51 мкс, подъём из снимка 189–193 мкс, из 20 событий без
  снимка 0,99–1,18 мс.
- Вне объёма: Raft (этап 5), реестр активаций, пересылка писем при переезде (письмо в пути к ушедшему
  владельцу теряется — «не более одного раза»).

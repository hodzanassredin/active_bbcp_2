# 0022. Хранилище «ключ → значение» по образцу LMDB/BoltDB

Статус: принято. Дата: 24.11.2026.

## Задача

Владелец попросил «минимальную имплементацию на ББ, но боеспособную, и чтобы можно было для обучения
использовать»: встроенное упорядоченное хранилище «ключ → значение» с транзакциями. Ограничения:
одна нить ОС и кооперативные задачи, без фоновой работы; файл переживает выключение питания в любой
момент; объём — около 2–2,5 тыс. строк, чтобы код можно было прочитать целиком; правки чужих
модулей — только привязка `fsync` в `LinLibc`.

## Решение

Подсистема `Kv`: B+-дерево с копированием при записи, один писатель, читатели по снимку, две
мета-страницы с CRC32 и номером транзакции, без журнала. Порядок фиксации: страницы → `Sync` → мета
в страницу `txid MOD 2` → `Sync`. Страницы читаются обычным чтением через ограниченный кеш узлов,
`mmap` нет. Большие значения лежат в страницах продолжения узла. Свободные страницы ждут, пока их не
перестанет видеть самый старый читатель. Устройство описано в `Kv/Docu/ru/Kv.md`.

## Рассмотренные варианты

**LMDB/BoltDB (выбран).** Один файл, нет журнала и восстановления: открытие только выбирает целую
мету. Ядро bolt (page, node, freelist, cursor, tx, db) — около 2,9 тыс. строк Go (посчитано
`wc -l`), его можно повторить в пределах цели. Цена — один писатель и файл, который не сжимается.

**LSM-дерево (LevelDB, mini-lsm).** Быстрая запись за счёт журнала, таблиц в памяти и фонового
слияния. Отвергнуто по объёму и по устройству: LevelDB — 11,4 тыс. строк, учебный mini-lsm — 8,8 тыс.;
слиянию нужна фоновая работа, а в однонитевой системе задач она либо блокирует всех, либо требует
`AsyncWork` с запретом на кучу в рабочих нитях.

**Bitcask.** Журнал записей и хеш-таблица ключей в памяти. Отвергнуто: нет порядка ключей и обхода
диапазона, а это требование задачи.

**Привязка готовой библиотеки на C (LMDB, SQLite).** Отвергнуто целью «для обучения»: код хранилища
не читается на Component Pascal, и вызовы C с `mmap` в одной нити ничего не дают задачам.

**`mmap` против своего кеша.** LMDB и bolt читают файл через `mmap`. Отвергнуто: ошибка чтения
становится сигналом, а не `res`; рост файла требует перемаппинга при живых читателях; у i386 мало
адресного пространства. Свой кеш на 1024 узла даёт ограниченную память и обычные коды ошибок.

**Страницы продолжения против предела «четверть страницы» и ссылки в другое хранилище.** Предел
отвергнут: журнал событий хранит значения больше килобайта. Ссылка во внешний файл добавила бы
второй путь записи без атомарности. Страницы продолжения повторяют bolt: узел из одного большого
элемента занимает несколько страниц подряд.

**Вторая пишущая транзакция ждёт (монитор) против трапа.** Выбран трап 21. Внутри операций Kv нет
точек переключения, поэтому ожидание имело бы смысл только между операциями; в той же задаче оно
вечное, а на главном стеке ждать нельзя. Задачам, которые пишут по очереди, монитор ставит
пользователь.

## Следствия

Открытие не восстанавливает ничего и занимает два чтения меты и чтение списка свободных. Тест
обрыва питания проверяет каждую запись и каждый `Sync` фиксации. Файл не сжимается; долгий
читатель держит страницы, и файл растёт. Номера страниц 32-битные: предел — 16 ТБ. Windows не
поддержана: нужен `KvWin` на `WinApi` (`FlushFileBuffers`).

## Не установлено

- Скорость против bolt на той же машине не измерялась.

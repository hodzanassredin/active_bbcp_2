# 0004. Реестр стеков в ядре, сборка по всем стекам, запрет выгрузки занятого модуля

Статус: принято. Дата: 23.11.2026; индекс стеков удалён 24.11.2026.

## Задача

Сборщик BlackBox считал корнями глобальные переменные и один стек — от текущего `FP` до дна главного.
Объект, на который ссылается только локальная переменная спящей задачи, он освободил бы живым. В
исходном коде незнакомый стек молча пропускался (`MarkLocals`), а трап главной нити мог уйти в стек
спящей сопрограммы. Выгрузка модуля проверяла только счётчик ссылок, хотя код модуля может стоять в
кадре спящей задачи. Ограничение: правки ядра минимальны, ядро сразу дублируется для amd64 и i386.

## Решение

Ядро ведёт реестр стеков: запись `Kernel.Stack` хранит границы, сохранённые `sp` и `fp`, контекст
`Kernel.Try` (`tryContext`, `trapStack`, `tryCount`). Реестр — двусвязный список без индекса.
`MarkLocals` сканирует текущий стек от `FP`, спящие — от сохранённого `sp`. Переключатель передаёт
записи стеков в `SwitchSave`/`SwitchRestore` сам, поиск `StackOf` нужен только трапу, сборке и
выгрузке. На незарегистрированном стеке сборка отменяется целиком. `UnloadMod` не выгружает модуль,
код которого есть в кадре любого стека. Устройство — `docs/implementation.md`, раздел 6.

## Рассмотренные варианты

**Список сопрограмм, как у Темпла.** Кольцевой список `Kernel.Coroutine`, скан стека только у уже
помеченного дескриптора. Перенесена идея реестра и скана от сохранённого указателя. Не перенесено:
у Темпла нет контекста `Try` на стек, сторожевой страницы и запрета выгрузки, а его ошибка #197 —
сбой сборщика после выгрузки модуля с живой сопрограммой.

**Трап при незнакомом стеке.** План велел заменить молчаливый пропуск трапом, и `MarkLocals` давал
`HALT(126)`. Ревью нашло, что обратный вызов из C на чужом стеке уронит процесс внутри сборки.
Принята отмена сборки: ядро не знает, где на таком стеке указатели, и не вправе освобождать память
(коммит f6a15b41). Молчаливость отмены записана долгом (`docs/kernel-plan.md`, 1.1).

**Отсортированный индекс стеков.** Введён в коммите 6f081507: на 10 тыс. задач линейный поиск
стека по `SP` стоил десятки микросекунд на переключение. Профиль задания s24 показал
`UnregisterStack` 10,9 %, `StackOf` 10,0 %, вставку в индекс 7,4 %: `mmap` отдаёт адреса по
убыванию, и каждая вставка сдвигала массив. Индекс удалён: планировщик знает обе записи заранее,
и после этого `StackOf` в горячем пути не остался. 1000 задач — 8,0 → 0,9 мс, 10 000 — 163 → 9,5 мс
(коммит 28d71a84). Ядро стало короче, число экспортов не выросло.

**Запрет выгрузки только по цепочке `FP`.** Обход кадров проверял выравнивание по 8, а кадры
Component Pascal выровнены по 4; обход сразу сдавался, и занятый модуль выгружался (коммит
a0706b56). Ревью добавило: кадр C между кадрами CP обрывает цепочку. Принят обход цепочки плюс
консервативный скан слов от точки обрыва (коммит fc56a7f7).

**Индекс кластеров кучи.** Без него `InHeap` перебирал кластеры линейно: сборка 10 млн живых
объектов шла 24 с, 50 млн — 544 с. С отсортированным индексом — 0,31 с и 1,8 с (коммит f5603744).
Индекс статический, на 16 384 записи, чтобы сборка не выделяла память.

## Следствия

- Тысячи задач с объектами только в локальных переменных переживают сборку.
- Сборка сканирует все живые стеки: при тысячах задач и сборке на каждую нехватку блока её цена
  растёт квадратично (`docs/kernel-plan.md`, 3.1; запись 0015).
- Долг: граница скана спящего стека держится на запасе `switchSaveSlack` (kernel-plan 1.2);
  статический индекс кластеров после переполнения навсегда уходит в линейный поиск (1.3).

# 0003. Каркас однонитевый, задачи живут в главном цикле

Статус: принято. Дата: 23.11.2026; поведение трапнувшего действия пересмотрено 24.11.2026.

## Задача

Планировщику задач нужно место, где он получает управление, а главному циклу BlackBox — способ
спать до события вместо опроса таймером раз в 50 мс. Каркас (модели, виды, журнал, рассылка
сообщений) держит общее состояние в глобальных переменных и не рассчитан на то, что его прервут
посреди рассылки. Ограничение: интерфейсы каркаса не меняются.

## Решение

Планировщик — действие `Services.Action`: шаг `Tasks.Step` исполняет готовые задачи не дольше кванта
(5 мс) и возвращает управление циклу. Консольный цикл ждёт ввода, сокетов и ближайшего срока одним
`poll` (`Poller`). Каркас остаётся однонитевым: задача не ждёт внутри обработчика действия и внутри
рассылки по домену, такое ожидание трапует 21. Действие, трапнувшее в `Do`, в очередь не
возвращается — как в исходном BlackBox. Устройство — `docs/implementation.md`, разделы 2 и 3.

## Рассмотренные варианты

**Замки в каркасе, как в Active BlackBox.** Ермаков поставил критические секции в `Log`,
`TextModels`, `Stores`, `Meta` и ещё около 60 мест. Отвергнут: при одной нити ОС замки не нужны, а
сам автор ABB оставил интерфейс однонитевым с очередью в главный цикл. Из ABB взята карта мест
каркаса с глобальным состоянием — по ней выбраны проверки «где ждать нельзя».

**Пять проверок каркаса из плана** (путь сообщения, открытый скрипт, обработчик вида, guard и
notifier, рассылка в домен). Инструментированы две: обработчик действия и рассылка по домену;
остальные три остались не сделанными (отчёт задания s5).

**Трапнувшее действие возвращать в очередь.** План требовал, чтобы действие после трапа не пропадало
молча. Так и было сделано в коммите 8e24ed27. Ревью 24.11 нашло, что в исходном BlackBox действие
теряется намеренно — это способ остановить сломанное действие, а возвращённое трапует на каждом шаге
цикла. Решено вернуть поведение исходной системы (коммит 9bcf5d5d, тест: действие с `HALT`
исполняется ровно один раз).

## Следствия

- Окна и команды обрабатываются между шагами планировщика; задачи не трогают каркас напрямую.
- Задача, которой нужен каркас, идёт через очередь главного цикла.
- `Tasks` использует `Services.now`, а не `immediately`: немедленные действия исполняет только
  `Loop.Loop`.
- Долг: три проверки каркаса из плана не инструментированы.

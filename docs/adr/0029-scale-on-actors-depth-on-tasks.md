# 0029. Масштаб — на акторах, глубина ожиданий — на задачах

Статус: принято.
Дата: 25.11.2026.

## Задача

В системе три способа вести много параллельных сущностей: задачи со своим стеком (`Tasks`, активные
объекты, `AWAIT`), акторы (`Actor`) и отложенные действия (`Services.Action`). Стек задачи со сторожевой
страницей — не меньше 4 КБ и два участка памяти процесса; потолок числа таких задач задаёт
`vm.max_map_count` (замер и расчёт — `docs/stacks-study.md`). Пробовались способы поднять потолок:
плотные стеки без сторожей, растущий стек с переносом, стек из кусков. Нужно правило, чем что делать,
чтобы не требовать от задач миллионов.

## Решение

- **Много сущностей с состоянием** (соединения, заказы, агенты, узлы) — акторы. Сотни байт на штуку,
  состояние между письмами в полях.
- **Отложенные и повторяющиеся действия** — `Services.Action`.
- **Последовательный код с ожиданием в глубине вызовов** — задачи. Стеков нужно столько, сколько
  потоков управления ждёт одновременно, а не сколько всего сущностей.
- Ожидание внутри обработчика актора разрешено, его цена — один стек на каждого одновременно ждущего;
  для этого пул исполнителей растёт (запись 0028).

Стратегии стеков задач:

- **основная** — стек в виртуальной памяти со сторожевой страницей; не требует правок компилятора;
- **запасная** — плотные стеки без сторожей с проверкой границы в прологе (ветка `active2-fast`,
  команда `Tasks.UseDenseStacks`, только Linux/amd64), когда одновременно ждущих больше потолка;
- **кандидат** — стек из кусков (проба в ветке `segs`, не принята и не влита): первый путь, если
  целью станут миллионы сущностей с последовательной логикой.

## Рассмотренные варианты

**Растущий стек с переносом** (проба в ветке `maps`: карты кадров, список доверенных процедур).
Заморожен: большая правка компилятора и ядра ради случая, который закрывают акторы. В A2 от переноса
стека ушли к кускам (исходники `Activities.Mod`, процедура `ExpandStack`); причина не выяснена.

**Задача в один кадр** (ждать только в корневой процедуре, кадр в куче, вызовы на общем стеке). Не
делается. В ETH такой вариант построен (Keller, 2006): размер стека считает компилятор, но ценой запрета
ожидания, методов и вызовов чужих модулей; автор Composita называет результат непрактичным.

**Автомат вместо стека силами компилятора.** В семействе Oberon не найден: в Zonnon протокол-грамматика
превращается в таблицу только для проверки порядка сообщений, активность остаётся потоком.

**Стек из кусков сразу.** Отложен до появления цели. В семействе Oberon миллионы процессов получены
именно так: Aos с доработкой 2006 года, Composita, нынешнее ядро A2 — куски, на новый кусок копируются
только параметры, следующий кусок придерживается.

## Следствия

- Перенос масштаба на акторы переносит туда и цену выделений: письма без `NEW` на операцию становятся
  условием, а не улучшением.
- Сетевые протоколы с известной длиной единицы (запись TLS, сообщение рукопожатия, заголовки HTTP)
  можно разбирать без стека: слой копит целую единицу и зовёт синхронный разбор над буфером. Интерфейс
  такого слоя не принят.
- Абстракция «поток, из которого читают» при наслоении слоёв сохраняется только на задачах: ждёт
  нижний слой, верхние не меняются.

## Не установлено

- Цена перехода через границу куска: в пробе `segs` измерена на разных процедурах, сравнение нечестное.
- Потолок задач со сторожем при `vm.max_map_count` 65 530 — расчёт по измеренному числу участков на
  задачу; при 1 048 576 измерено 524 220.
- Почему A2 заменил перенос стека кусками.

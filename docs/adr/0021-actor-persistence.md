# 0021. Персистентность акторов: журнал событий со снимками

Статус: принято. Дата: 24.11.2026.

## Задача

Состояние актора должно переживать трап, перезапуск супервизором и падение процесса (запись 0018:
`Restart` создаёт экземпляр с начальным состоянием). Решения владельца: журнал событий со снимками;
актор расширяет `Stores.Store`; кадр — двоичный, через `Stores`, кодек сменный; хранилище за
абстракцией (память или база); образец — persistence из protoactor-go. Темы этапа: журнал событий,
оптимистичная проверка версии, происхождение (кто, когда, по какой причине) в каждом событии,
читатель CQRS как пример, повтор команды без второго действия. Ограничения: ядро, компилятор,
`Tasks`, `Async`, `Cas` не меняются; хранилища «ключ — значение» пока нет.

## Решение

Четыре модуля в `Actor/Mod`: `ActorJournal` (абстрактный журнал потоков и реализация в памяти),
`ActorCodec` (кадр `Stores.Store` ↔ байты), `ActorPersist` (персистентный актор, читатель),
`ActorFileJournal` (файл «только дозапись», снимки в `CasStore`). Устройство и правила —
`Actor/Docu/ru/Actors.md`, раздел 8 и разделы 12.4–12.7.

## Рассмотренные варианты

**Всё состояние после каждого письма против журнала событий.** Сохранение всего состояния проще:
одна запись, восстановление — одно чтение. Отвергнуто: цена записи растёт с размером состояния, а
причина изменения теряется, и аудит («кто, когда, почему») пришлось бы вести отдельно. Журнал пишет
только изменение, восстановление — та же свёртка `Apply`, история — готовая.

**Снимки.** Без снимков восстановление проходит весь поток: 100 000 событий — 0,38–0,51 с
(`Actors.md`, раздел 10), и время растёт с историей. Снимок раз в `snapEvery` событий плюс хвост —
6–12 мкс при снимке после последнего события. Снимок хранится один на поток (новый заменяет
старый); события до снимка не удаляются, хотя интерфейс это допускает: аудиту нужна вся история.

**Кодек через `Stores` против своего формата.** Свой формат (поля вручную, номер типа из таблицы)
быстрее и не зависит от имён модулей. Отвергнут решением владельца и тем, что `Stores` уже даёт
поиск типа по имени, загрузку модуля и номер версии в каждом кадре; неизвестный тип `Stores`
превращает в `Alien`, и кодек отвечает `unknown`, а не трапует. Кодек сменный (`ActorCodec.SetDir`).
Первая сборка брала временный файл ОС на каждый кадр, а журнал в памяти держал указатель на каждое
событие; замер 100 000 событий не закончился за 5 минут. Кодек пишет через файл в памяти, тела
событий лежат в одном массиве потока, и запись стала линейной.

**Где проверяется версия (OCC).** Вариант «проверяет актор» (читает `Last`, сравнивает, пишет)
отвергнут: между чтением и записью другой писатель может дописать поток. Проверка — внутри
`Append(stream, expected, …)`: несовпадение даёт `conflict` и ничего не пишет. Для будущего
хранилища «ключ — значение» это одна пишущая транзакция: поиск последнего ключа потока и запись.
`Persist` отвечает на `conflict` трапом 70: актор не знает, как совместить чужое событие со своей
командой, а `Restart` перечитывает поток вместе с чужим событием.

**Временный диск: файл «только дозапись» против ожидания `Kv`.** Без дискового журнала нельзя
показать восстановление после падения процесса. Файл — запись с длиной и контрольной суммой FNV-1a;
при открытии первая оборванная или испорченная запись и всё после неё отбрасываются. Границы
приняты сознательно: `Flush` без `fsync`, один процесс на файл, указатель потоков в памяти, открытие
читает весь файл. Ключи будущего адаптера: `"e" + поток + 0X + seq` (8 байт, старший вперёд) для
событий, `"s" + поток` для снимка.

**Ошибка хранилища и ожидание.** Повтор записи внутри `Persist` отвергнут: повторять или нет —
решение супервизора, у которого есть счёт отказов. Ошибка — трап 71. `Persist` синхронный, без
точек переключения: письма ждут в ящике, медленное хранилище держит исполнителя, актору с медленным
хранилищем дают свою задачу (`Props.dedicated`).

**Причина и автор.** В ядре нет сквозного номера письма, поэтому причину (`cause`) передаёт
обработчик — номер операции из команды; он же служит повтору без второго списания. Автор —
отправитель команды (`c.Sender()`), без отправителя — сам актор.

## Следствия

- Персистентное состояние есть только у наследников `ActorPersist.Actor`; прочие акторы ведут себя
  как в записи 0018.
- Таблица выполненных операций хранит последние N номеров (в примерах и тестах — кольцо); повтор
  операции старше последних N выполняется снова. Правило выбрано как самое простое: отсечка «не
  старше снимка» привязала бы повтор к частоте снимков.
- Тип события нельзя переименовать или удалить, пока в журналах есть его кадры; новое поле — новая
  версия (`ReadVersion(min, max, v)`).
- Журнал растёт без предела; файл открывается чтением целиком.
- Пример `ObxActor2` не изменён: повтор показан в `ObxActor3`.
- Появилась `Kv` (запись 0022), и журнал на диске — `ActorKvJournal`: ключи `"e" + поток + 0X + seq`
  и `"s" + поток`, как задумано выше; последний номер ищет курсор (`Seek` за конец потока и шаг
  назад), а не ключ-счётчик, который мог бы разойтись с ключами событий. Запись — 1,6–1,7 мс на
  событие (два `Sync` на фиксацию). `ObxActor3` переведён на `Kv`; файл
  «только дозапись» остался простой реализацией без `fsync` и транзакций.
- Внутри транзакций `Kv` нет точек переключения, `Sync` держит исполнитель: медленный носитель
  задерживает весь пул акторов.
- Групповая фиксация живёт внутри `ActorKvJournal.Append`: интерфейс `ActorJournal` не изменился.
  Отвергнуты метод «дописать пачку» у `Journal` (пачку собирал бы `ActorPersist`, а писатели — разные
  акторы, у каждого свой обработчик) и обёртка-журнал поверх любого `Journal` (у памяти и файла
  `Sync` нет, выигрывать нечего, а пачке нужна одна транзакция, которой у абстракции нет); в `KvDb` —
  тоже отвергнуто: проверка `expected` по потоку — знание журнала, не базы. `Append` из задачи встаёт
  в очередь; первая задача становится ведущей, уступает один раз и фиксирует очередь одной
  транзакцией; конфликт ожидаемого номера получает только свой запрос. При 8 и 64 писателях запись
  в 4–7 раз дешевле, чем по одной фиксации на событие (`Actors.md`, раздел 10).

## Что взято от `Kv`

Упорядоченные ключи и курсор (`Seek`, `Prev`, `Next`), пишущая транзакция `Update` с проверкой и
записью, фиксация с `Sync`.

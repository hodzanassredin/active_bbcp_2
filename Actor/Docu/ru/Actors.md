# Акторы

Подсистема `Actor` строит программу из объектов, которые обмениваются сообщениями и не делят
состояние. Глава описывает акторы одного процесса, их исполнение общим пулом задач и надзор родителя за
детьми. Задачи, мониторы и точки переключения определены в
`Docu/CP-Lang.md` и `Docu/ru/Tasks.md`, сообщения и каналы — в `Docu/ru/Async.md`.
Подсистема собирается только для AMD64, как и `Async`.

## 1. Счёт, который трогают все

Возьмём банковский счёт, с которого снимают деньги несколько задач. Если остаток лежит в общей
переменной, каждая задача проверяет его и уменьшает, и между проверкой и уменьшением другая задача
успевает сделать то же самое: остаток уходит в минус. Монитор закрывает эту дыру, но приносит
другую: задача, трапнувшая внутри исключающей процедуры, оставляет счёт в том состоянии, в каком
застал её трап, и следующая задача работает с ним дальше.

Актор решает обе задачи одним правилом. *Актор* — объект с собственным состоянием и обработчиком
`Receive`; состояние актора меняет только его обработчик, а другие части программы посылают ему
сообщения. Сообщения ждут обработки в *ящике* — очереди актора. Обработчик получает их по одному,
поэтому между проверкой остатка и его уменьшением чужого вмешательства нет. Трап обработчика
ловится и становится сообщением *супервизору* — родителю актора, который решает, что делать с
отказавшим: продолжить, перезапустить с чистым состоянием или остановить.

Отправитель знает получателя по *адресу* — значению типа `ActorCore.Ref`. Адрес состоит из имени
узла и имени актора. Отправка, наблюдение и остановка идут через абстрактные методы адреса,
поэтому адрес актора на другом узле занимает то же место (разделы 9 и 10).

## 2. Первый актор

Счётчик принимает `Inc` и отвечает на `Get` текущим значением. Модуль ниже (пример `ObxActor0`,
страница `Obx/Docu/ru/Actor0.md`) создаёт его, посылает тысячу `Inc` из задачи-клиента, спрашивает
итог и останавливает всё.

```
MODULE ObxActor0;
	IMPORT Services, Tasks, Console, Strings, ActorCore, ActorRun;

	TYPE
		Inc = POINTER TO RECORD (ActorCore.Msg) END;
		Get = POINTER TO RECORD (ActorCore.Msg) END;
		Num = POINTER TO RECORD (ActorCore.Msg) n: INTEGER END;
		Counter = POINTER TO RECORD (ActorCore.Actor) n: INTEGER END;
		Client = POINTER TO RECORD (Tasks.Job) END;

	VAR counter: ActorCore.Ref;

	PROCEDURE (a: Counter) Receive (c: ActorCore.Context; m: ActorCore.Msg);
		VAR r: Num;
	BEGIN
		WITH m: Inc DO INC(a.n)
		| m: Get DO NEW(r); r.n := a.n; c.Respond(r)
		ELSE	(* Started и прочие сообщения жизненного цикла *)
		END
	END Receive;

	PROCEDURE New (): ActorCore.Actor;
		VAR a: Counter;
	BEGIN
		NEW(a); RETURN a
	END New;

	PROCEDURE (t: Client) Body- (VAR ctx: Tasks.Ctx);
		VAR i: INTEGER; inc: Inc; get: Get; r: ActorCore.Msg; s: ARRAY 16 OF CHAR;
	BEGIN
		NEW(inc); NEW(get);
		FOR i := 1 TO 1000 DO ActorCore.Tell(counter, inc) END;
		IF ActorCore.Ask(counter, get, 1000, r) = ActorCore.ok THEN
			Strings.IntToString(r(Num).n, s); Console.WriteStr("counter: "); Console.WriteStr(s)
		ELSE Console.WriteStr("counter: no answer")
		END;
		Console.WriteLn;
		ActorRun.Shutdown
	END Body;

	PROCEDURE Do*;
		VAR t: Client;
	BEGIN
		IF ActorRun.n = 0 THEN ActorRun.Start(4) END;
		counter := ActorCore.Spawn(NIL, ActorCore.NewProps(New), "counter");
		NEW(t); Tasks.Start(t);
		WHILE Tasks.Count() > 0 DO Services.actionHook.Step END
	END Do;

END ObxActor0.
```

Команда `ObxActor0.Do` печатает `counter: 1000`. Актор описывается записью `Props`: фабрика
экземпляров, предел ящика, признак собственной задачи и стратегия надзора за детьми. `Spawn`
создаёт экземпляр фабрикой, заводит ящик и возвращает адрес; первым сообщением обработчик получает
`Started`. `Tell` кладёт сообщение в ящик и возвращается сразу. `Ask` посылает сообщение с временным
адресом ответа и ждёт первого письма на этот адрес не дольше заданного числа миллисекунд;
обработчик отвечает через `c.Respond`, который адресует письмо отправителю текущего сообщения.
`Ask` ждёт, поэтому клиент — задача: на главном стеке `Ask` трапует с кодом 20. Пропуск
`Tasks.Ctx` для `Ask` не нужен, и клиент написан как `Tasks.Task` с `Run`; это нижний уровень.
Прикладной код, который входит в `Tasks.Object`, пишут через `Tasks.Job` с `Body-`.

Сообщение — расширение `AsyncSelect.Msg` (в подсистеме оно называется `ActorCore.Msg`) и после
отправки не меняется. Счётчик выше посылает тысячу раз один и тот же объект `inc`: это допустимо
именно потому, что объект неизменяем. Если бы клиент менял поле отправленного сообщения, обработчик
увидел бы значение на момент обработки, и порядок отправок перестал бы что-либо значить.

Последним клиент зовёт `ActorRun.Shutdown` (раздел 3), а команда крутит главный цикл, пока есть
задачи. Без общей остановки исполнители ждали бы работы вечно, и цикл команды не кончился бы.

## 3. Исполнители

У актора нет своей задачи. Ящики с работой обслуживает *исполнитель* — задача пула `ActorRun`,
которая берёт ящик из общей очереди, вызывает `Dispatcher.Process` и возвращает ящик в очередь,
если в нём остались письма. `ActorRun.Start(n)` заводит n исполнителей; за один вызов `Process`
актор обрабатывает все системные сообщения и до ста пользовательских. Тысяча акторов поэтому
занимает тысячу ящиков и столько стеков, сколько исполнителей в пуле.

Обработчик актора может ждать: спать, принимать из канала, спрашивать другого актора через `Ask`.
Пока он ждёт, действует правило: один обработчик на актор за раз. Ящик ждущего актора помечен как
занятый, и следующее письмо этому актору не выдаётся ни этому, ни другому исполнителю. Цена правила
— занятый исполнитель. Пусть в пуле четыре исполнителя, а четыре актора одновременно уснули в
`Receive` на секунду: пятый актор, которому пришло письмо, ждёт секунду, хотя работы у него на
микросекунду. Тест `TestBusyActorGetsNoSecondMessage` проверяет обе стороны правила: два письма
`Nap` одному актору обрабатываются друг за другом, а письмо второму актору обрабатывается во время
первого сна.

Актор, которому ожидание нужно постоянно, получает собственную задачу: `Props.dedicated := TRUE`.
Его ящик обслуживает только она, и исполнители пула остаются свободны; в тесте
`TestDedicatedLeavesPoolFree` пул из одного исполнителя отвечает другому актору, пока актор со своей
задачей спит.

Свободный исполнитель ждёт в `Tasks.ParkExternal`, и `Tell` будит его через `Tasks.Unpark`.
`Unpark` вне задачи — из команды или из действия `Services` — сам переносит срок шага планировщика
на ближайший, поэтому письмо с главного стека начинает обрабатываться в следующем шаге главного
цикла. `ParkExternal` — ожидание события извне: письмо может прийти с главного стека, поэтому
свободный пул тупиком не считается (`TestIdlePoolIsNoDeadlock`). Следствие: пока пул жив,
планировщик не объявляет и полный тупик прочих задач.

Спросить самого себя через `Ask` нельзя: вопрос лёг бы в собственный ящик, а ящик занят ждущим
обработчиком, и ответа не было бы никогда. Поэтому `Ask` из обработчика актора к этому же актору
трапует с кодом 23, и отказ уходит супервизору. Тест `TestAskSelfTraps` проверяет, что корень
останавливает такой актор сразу, не дожидаясь срока вопроса.

Общая остановка — `ActorRun.Shutdown`. Она посылает `Stop` каждому актору без родителя, ждёт, пока
остановятся все акторы (дети раньше родителей, раздел 5), затем завершает задачи пула: каждый
исполнитель выходит из своего цикла сам, без отмены, поэтому в журнале нет ни `Tasks: cancelled`, ни
`Tasks: deadlock`. Собственные задачи акторов кончаются вместе со своими акторами. Если актор не
остановился за 5 с (его обработчик ждёт без конца), `Shutdown` отменяет задачи пула, как `Stop`, а
такой актор остаётся. `Shutdown` ждёт в задаче через `Tasks.Sleep`, на главном стеке — крутя
главный цикл; из задачи исполнителя она трапует с кодом 20: исполнитель ждал бы сам себя. Тест
`TestShutdownLeavesNoTasks` проверяет, что после неё не остаётся ни одной задачи и планировщик не
видел взаимной блокировки; примеры `ObxActor0`–`ObxActor2` проверяют чистый журнал.

## 4. Доставка

Доставка идёт по правилу «не более одного раза». Письмо, которое не может быть обработано, не
возвращается отправителю и не повторяется; оно становится *мёртвым письмом*, а счётчик
`ActorCore.deadLetters` увеличивается на единицу. Мёртвым становится письмо остановленному актору,
письмо сверх предела ящика `Props.capacity` (в предел входят и отложенные `Stash` письма; письмо
`ActorCore.Urgent` идёт мимо предела), ответ `Respond` на сообщение без отправителя и всё,
что осталось в ящике при остановке актора. Отправитель при этом не трапует и не ждёт.

Ящик без предела растёт, пока есть память. С пределом `capacity = 5` двадцать писем, посланных
подряд до первой обработки, дают пять обработанных и пятнадцать мёртвых
(`TestCapacityOverflowGoesToDeadLetters`).

Письма одного отправителя одному получателю приходят в порядке отправки: ящик — одна очередь, и
каждый адресат кладёт письмо в её конец. Тест счётчика посылает тысячу пронумерованных `Inc` и
проверяет, что номера идут подряд. Письма разных отправителей перемешиваются в порядке, в котором
отправители получали управление.

`Ask` возвращает один из трёх ответов:

| Результат | Условие |
|---|---|
| `ok` | на адрес ответа пришло письмо, оно в `reply` |
| `timedOut` | за отведённое время ответа нет |
| `dead` | вопрос стал мёртвым письмом или адресат остановился, не ответив |

Ответ `dead` приходит без ожидания срока: в тесте `TestStoppedActorGivesDeadLetters` вопрос
остановленному актору со сроком 1000 мс возвращается быстрее 500 мс. На время вопроса адрес ответа
наблюдает адресата, как `Watch`; адресат, который принял вопрос и остановился без `Respond`,
поэтому тоже даёт `dead` сразу (`TestAskDeadWhenTargetStopsWithoutReply`: актор, молчащий на вопрос
со сроком 2000 мс, останавливают через 50 мс, и `Ask` возвращается быстрее 1000 мс). Ответ,
пришедший после тайм-аута, теряется.

### Маршрутизаторы

У службы часто несколько равноценных работников: три счёта одной валюты, четыре читателя одной
очереди. Клиент хочет послать одно письмо «одному из них», не зная, сколько их. *Маршрутизатор* —
актор, который владеет набором маршрутов и пересылает каждое письмо одному маршруту или всем,
сохраняя исходного отправителя. Получатель пересланного письма видит тот же `Sender`, как если бы
клиент писал маршруту сам.

`ActorRouter.NewGroup(refs, kind, seed)` берёт готовые адреса; `ActorRouter.NewPool(factory, n,
kind, seed, strategy)` рождает `n` детей фабрикой и держит их адреса у себя. В пуле
маршрутизатор — родитель, поэтому трап ребёнка становится отказом маршрутизатора, и судьбу
ребёнка решает `Props.strategy`. Перезапуск оставляет адрес ребёнка тем же, поэтому маршрут не
меняется. Остановленный маршрут — директивой `Stop` или `StopActor` — снимается из набора, когда
маршрутизатор получает `Terminated`; пустой набор теряет письмо: маршрутизатор его обработал, и мёртвым оно не становится. Команда
`ActorRouter.SetGroup(router, refs)` заменяет набор, `SetCount(router, n)` растит или сокращает
пул, `SetKind(router, kind)` меняет правило; все три — обычные письма и действуют в порядке
ящика.

Правило выбирает маршрут:

| Вид | Маршрут |
|---|---|
| `roundRobin` | следующий по кругу |
| `random` | из генератора с зерном `seed`; то же зерно и те же вызовы дают ту же последовательность |
| `broadcast` | все маршруты |
| `consistentHash` | маршрут с наибольшим `ActorHash.Weight(имя, "router", ключ)`; письмо без ключа идёт по пустому ключу |

Вес — тот же рандеву-хеш, которым размещается ключ виртуального актора (`ActorGrain`): для одного
имени маршрута и ключа оба выбирают одно место. При уходе маршрута переезжают только его ключи.
Письмо для рандеву-хеша расширяет `ActorRouter.Keyed` и заполняет поле `key`; расширение — простая
запись, поэтому маршрутизация письма ничего не выделяет. Набор маршрутизатора — массив, созданный
при рождении; пересылка только кладёт письмо в ящик маршрута.

Пример `ObxActor10` посылает шесть писем по кругу, одно всем и четыре с одним ключом по
рандеву-хешу. Тесты: `TestRoundRobinCyclesOverGroup`, `TestBroadcastSendsToEveryRoute`,
`TestRandomIsDeterministicFromSeed`, `TestConsistentHashKeepsKeyOnRoute`,
`TestPoolRestartsFailedRoute`, `TestPoolDropsStoppedRoute`, `TestSetGroupChangesRoutes`.

### Поток событий

Нескольким акторам часто нужна одна и та же новость: новый заказ, остановленный счёт, неудачный
перевод. Рассылать её каждому вручную значит, что отправитель знает всех получателей, а новый
получатель требует правки отправителя. *Поток событий* переворачивает это: акторы подписываются
на поток, а издатель пишет один раз в поток. `ActorEvent.New()` создаёт актор-поток;
`Subscribe(s, r, filter)` подписывает `r` с необязательным предикатом `Filter`,
`Unsubscribe(s, r)` снимает подписку, `Publish(s, m)` посылает письмо потоку. Поток пересылает
письмо каждому подписчику, у которого предиката нет или `Match` вернул `TRUE`, сохраняя
отправителя письма.

`Publish` ничего не выделяет: это `Tell` потоку, а поток только ставит письмо в ящики
подписчиков. Выделяют память `Subscribe`, `Unsubscribe` и событие `DeadLetter`. Поток наблюдает
подписчиков, поэтому остановленный подписчик уходит из списка, когда поток получает `Terminated`;
отписывать его не нужно.

`ActorEvent.SetDefault(s)` делает поток приёмником мёртвых писем: каждое письмо, не дошедшее до
адресата, публикуется в `s` как `ActorEvent.DeadLetter` с полями `m` (исходное письмо), `to`
(адресат; `NIL` — нет) и `sender`. Мёртвое письмо о самом `DeadLetter` не публикуется, а мёртвое
письмо, возникшее во время вызова приёмника, не считается, поэтому остановленный поток не
замыкает круг. `SetDefault(NIL)` снимает приёмник.

Пример `ObxActor11` публикует заказы и сведения двум подписчикам, один с предикатом, и
показывает мёртвое письмо как событие. Тесты: `TestPublishReachesSubscribers`,
`TestFilterSelectsLetters`, `TestUnsubscribeStopsDelivery`, `TestStoppedSubscriberIsRemoved`,
`TestDeadLetterPublished`, `TestDeadLetterIsNotRepublished`, `TestDeadLetterAboutDeadLetterIsNotPublished`.

## 5. Жизненный цикл

Актор проходит состояния «работает», «перезапускается», «останавливается» и «остановлен». О каждом
переходе обработчик узнаёт сообщением:

| Сообщение | Когда |
|---|---|
| `Started` | первым после создания и первым после перезапуска |
| `Restarting` | старому экземпляру перед перезапуском |
| `Stopping` | в начале остановки |
| `Stopped` | последним, после остановки всех детей |
| `Terminated` | наблюдателю, когда наблюдаемый актор остановлен |
| `ReceiveTimeout` | после простоя дольше `SetReceiveTimeout` |

Кроме ящика пользовательских писем у актора есть системная очередь: остановка, наблюдение,
отказ ребёнка, уход ребёнка, директивы супервизора. Перед каждым пользовательским письмом
исполнитель разбирает всю системную очередь. Поэтому `StopActor` останавливает актор, даже если в
его ящике тысяча писем: все они станут мёртвыми.

Остановка идёт сверху вниз и завершается снизу вверх. Родитель получает `Stopping`, посылает
остановку детям и ждёт ухода каждого; `Stopped` родитель получает, только когда детей не осталось.
Если бы порядок был обратным, обработчик родителя в `Stopped` освобождал бы ресурсы, которыми дети
ещё пользуются в своих `Stopping`. Тест `TestStopParentStopsChildrenFirst` проверяет по журналу,
что `Stopping` и `Stopped` обоих детей записаны раньше `Stopped` родителя.

`c.Watch(r)` подписывает актор `c` на остановку `r`: когда `r` остановлен, обработчик `c` получает
`Terminated` с полем `who = r` один раз. Повторный `Watch` того же `r` подписки не добавляет: два
вызова дают одно `Terminated` (`TestWatchTwiceGivesOneTerminated`). Подписка на уже остановленный
актор отвечает `Terminated` сразу (`TestWatchStoppedGetsTerminatedAtOnce`). `c.Unwatch(r)` снимает
подписку; `Terminated`, посланное до `Unwatch`, но ещё не обработанное, обработчик тоже не получит
(`TestUnwatchGivesNoTerminated`). Остановка наблюдателя снимает все его подписки, и список
наблюдателей у `r` не растёт от ушедших.

`c.SetReceiveTimeout(ms)` просит сообщить о простое. После `ms` миллисекунд без пользовательских
писем обработчик получает `ReceiveTimeout` один раз; следующий отсчёт начинает следующее письмо.
В тесте `TestReceiveTimeoutOnceAfterIdle` при сроке 100 мс десять писем с паузой 20 мс не дают ни
одного `ReceiveTimeout`, затем 250 мс тишины дают ровно один, и ещё 250 мс тишины — ни одного.
Сообщения жизненного цикла и сам `ReceiveTimeout` отсчёт не сбрасывают.

Тайм-аут простоя не обгоняет письма и не теряется. Пока обработчик идёт или в ящике ждут письма,
актор не простаивает, и `ReceiveTimeout` не выдаётся: срок проверяется снова позже
(`TestTimeoutDoesNotOvertakeMail`: письмо, ждавшее за долгим обработчиком, обработано раньше
тайм-аута). Приостановленный актор (раздел 6) тайм-аута не получает, а после `Resume` отсчёт
начинается заново (`TestTimeoutNotLostWhileSuspended`).

`c.Become(b)` подменяет обработчик: следующие письма получает `b.Receive(a, c, m)`, где `a` —
экземпляр актора. `Become(NIL)` возвращает `Receive` экземпляра, перезапуск — тоже
(`TestRestartDropsBecome`). `Become` и `SetReceiveTimeout` меняют обработку писем своего актора,
поэтому их зовут только из его обработчика; вызов из другого места трапует с кодом 20
(`TestHandlerOnlyCallsTrapOutside`). Перезапуск снимает и тайм-аут (`TestRestartDropsReceiveTimeout`).

Обработчик, который возвращается к прежнему поведению, пользуется стеком. `c.BecomeStacked(b)`
откладывает текущее поведение и ставит `b`; `c.Unbecome` отбрасывает текущее и восстанавливает
последнее отложенное. На пустом стеке `Unbecome` возвращает `Actor.Receive`, как и `Become(NIL)`.
`Become` заменяет текущее поведение и стек не трогает; перезапуск и остановка очищают и то и
другое (`TestRestartDropsBehStack`). Стек принадлежит одному экземпляру и не разделяется.
Откладывание выделяет один узел, поэтому обработчик, зовущий `BecomeStacked` на каждое письмо,
растит стек; для простой замены служит `Become`. `TestBecomeStackedUnbecomeRestores` откладывает
два поведения и снимает их обратно до `Actor.Receive`.

Новое поведение — полный обработчик: письмо, которого текущее поведение не знает, теряется, а не
передаётся нижнему. Поэтому поведения в тесте сами обрабатывают письма откладывания и снятия.

## 6. Надзор

Каждый актор, созданный `Spawn(c, ...)`, — ребёнок актора `c`; созданный `Spawn(NIL, ...)` —
ребёнок корня. Обработчик исполняется под `Kernel.Try`, и трап в нём не роняет исполнителя:
ящик приостанавливается, а родитель получает системное сообщение об отказе с номером трапа.
Родитель спрашивает стратегию из своего `Props.strategy` и получает *директиву* — решение о судьбе
отказавшего ребёнка:

| Директива | Действие |
|---|---|
| `Resume` | ящик снимается с паузы, состояние сохранено, письмо-виновник пропущено |
| `Restart` | дети ребёнка останавливаются, затем фабрика создаёт новый экземпляр, он получает `Started`; письма ящика сохранены, виновник пропущен |
| `Stop` | ребёнок останавливается, его письма становятся мёртвыми |
| `Escalate` | отказывает сам родитель с тем же номером трапа; ребёнок ждёт его судьбы |

Без стратегии директива — `Stop`. `ActorSup.NewOneForOne(d, max, ms)` отвечает директивой `d` и
применяет её только к отказавшему ребёнку. Для `Restart` она считает перезапуски в окне: окно
открывает первый отказ, отказ после конца окна открывает новое, а отказ с номером `max + 1` в окне
даёт `Stop`. Без предела ребёнок, трапующий на каждом письме, перезапускался бы бесконечно и
занимал исполнителя. Тест `TestTooManyRestartsStopsAndNotifiesWatcher` при `max = 2` посылает три
трапующих письма: ребёнок получает `Started` три раза, затем останавливается, и наблюдатель
получает `Terminated`.

Перезапуск без журнала теряет состояние. Модуль ниже (пример `ObxActor1`) считает письма, трапует
на третьем и перезапускается: после перезапуска счёт начинается заново.

```
MODULE ObxActor1;
	IMPORT Services, Tasks, Console, Strings, ActorCore, ActorSup, ActorRun;

	TYPE
		Inc = POINTER TO RECORD (ActorCore.Msg) END;
		Boom = POINTER TO RECORD (ActorCore.Msg) END;
		Worker = POINTER TO RECORD (ActorCore.Actor) n: INTEGER END;
		Parent = POINTER TO RECORD (ActorCore.Actor) END;
		Client = POINTER TO RECORD (Tasks.Job) END;

	VAR worker: ActorCore.Ref; starts, last: INTEGER;

	PROCEDURE (a: Worker) Receive (c: ActorCore.Context; m: ActorCore.Msg);
	BEGIN
		WITH m: ActorCore.Started DO INC(starts)
		| m: Inc DO INC(a.n); last := a.n
		| m: Boom DO HALT(42)
		ELSE
		END
	END Receive;

	PROCEDURE NewWorker (): ActorCore.Actor;
		VAR a: Worker;
	BEGIN
		NEW(a); RETURN a
	END NewWorker;

	PROCEDURE (a: Parent) Receive (c: ActorCore.Context; m: ActorCore.Msg);
	BEGIN
		IF m IS ActorCore.Started THEN
			worker := ActorCore.Spawn(c, ActorCore.NewProps(NewWorker), "worker")
		END
	END Receive;

	PROCEDURE NewParent (): ActorCore.Actor;
		VAR a: Parent;
	BEGIN
		NEW(a); RETURN a
	END NewParent;

	PROCEDURE (t: Client) Body- (VAR ctx: Tasks.Ctx);
		VAR inc: Inc; boom: Boom; s: ARRAY 16 OF CHAR;
	BEGIN
		WHILE worker = NIL DO Tasks.Sleep(1) END;
		NEW(inc); NEW(boom);
		ActorCore.Tell(worker, inc); ActorCore.Tell(worker, inc);
		ActorCore.Tell(worker, boom);
		ActorCore.Tell(worker, inc);
		Tasks.Sleep(100);
		Strings.IntToString(starts, s); Console.WriteStr("worker: Started "); Console.WriteStr(s);
		Strings.IntToString(last, s); Console.WriteStr(", count after restart "); Console.WriteStr(s);
		Console.WriteLn;
		ActorRun.Shutdown
	END Body;

	PROCEDURE Do*;
		VAR p: ActorCore.Props; t: Client;
	BEGIN
		IF ActorRun.n = 0 THEN ActorRun.Start(4) END;
		starts := 0; last := 0; worker := NIL;
		p := ActorCore.NewProps(NewParent);
		p.strategy := ActorSup.NewOneForOne(ActorCore.Restart, 3, 1000);
		ASSERT(ActorCore.Spawn(NIL, p, "parent") # NIL, 100);
		NEW(t); Tasks.Start(t);
		WHILE Tasks.Count() > 0 DO Services.actionHook.Step END
	END Do;

END ObxActor1.
```

Команда `ObxActor1.Do` печатает `worker: Started 2, count after restart 1`: два письма `Inc` до
трапа пропали вместе со старым экземпляром. Перезапуск сначала останавливает детей ребёнка и только
потом создаёт новый экземпляр (`TestRestartStopsGrandchildrenFirst`: `Stopped` внука записан раньше
`Started` нового экземпляра). Окно перезапусков `OneForOne` сдвигается: отказ после конца окна
снова даёт `Restart`, а не `Stop` (`TestRestartWindowResets`).

Иногда дети супервизора зависят друг от друга: читатель и писатель одного буфера, счёт и журнал
его переводов. Перезапуск только отказавшего ребёнка оставляет у остальных состояние, которое с
ним больше не сходится. `ActorSup.NewAllForOne` после отказа перезапускает всех детей
супервизора, а `ActorSup.NewRestForOne` — отказавшего и рождённых после него; дети, рождённые
раньше, продолжают работу. Стратегия считает отказы всех детей в одном окне, а не у каждого
ребёнка отдельно: окно открывает первый отказ, а отказ с номером `max + 1` останавливает группу.
Директивы те же, что у `OneForOne`; на `Restart` стратегия отвечает `RestartAll` или
`RestartRest`, после предела — `StopAll` или `StopRest`. Директива `Stop` сразу останавливает
группу, `Resume` возобновляет только отказавшего, `Escalate` передаёт отказ вверх как раньше.
Тест `TestAllForOneRestartsAllChildren` отказывает одного из трёх детей и видит `Started` шесть
раз; `TestRestForOneRestartsRestOnly` отказывает среднего и видит `Restarting` только у него и у
рождённого после него (`TestAllForOneTooManyStopsAll`, `TestRestForOneTooManyStopsRest`,
`TestAllForOneWindowResets`).

Порядок детей важен для `RestForOne`. Список детей хранит младшего первым: рождённый позже стоит
ближе к голове. «Рождённые после» — это дети от головы до отказавшего включительно; старшие стоят
дальше и их директива не трогает. `ActorCore` исполняет групповую директиву, посылая `Restart`
или `Stop` каждому ребёнку этого отрезка, поэтому каждый ребёнок проходит обычный жизненный цикл
и сообщает `Restarting` или `Stopping` своему обработчику.

Пример `ObxActor2` показывает, почему для счетов выбран `Resume`. Банк — супервизор счетов и
переводов; каждый сотый перевод несёт нулевую сумму, и счёт трапует на предусловии. При `Resume`
остаток счёта сохраняется, перевод не получает ответа и по `ReceiveTimeout` считается отказанным, а
в конце сумма остатков равна начальной. При `Restart` новый экземпляр счёта начал бы с начального
остатка, и сумма денег изменилась бы на величину всех операций, прошедших через этот счёт.

Фабрика может упасть и при перезапуске. Тогда у ребёнка нет экземпляра, и его ящик снова
приостановлен с отказом перед родителем. `Resume` такому ребёнку означал бы обработку писем
экземпляром `NIL`: каждое письмо трапует, и круг отказов не кончается. Поэтому `Resume` ребёнку без
экземпляра исполняется как `Stop` (`TestFactoryFailAfterRestartStopsOnResume`). Фабрика, которая
вернула `NIL`, отказывает с номером 26.

`Escalate` передаёт отказ вверх: родитель приостанавливается и отказывает перед своим родителем.
Если затем родителя возобновят, вместе с ним возобновятся и его приостановленные дети; если
перезапустят или остановят — дети остановятся. Отказ, дошедший до корня, корень решает одной
директивой: он останавливает своего ребёнка, то есть актор верхнего уровня, через который прошёл
отказ, и печатает в `Console` строку `Actor: root stops <имя> after trap <номер>`. Остановка
уносит всё поддерево. Корень не перезапускает: у него нет фабрики, которой он мог бы доверять
больше, чем фабрике упавшего актора, а бесконечный цикл перезапусков на верхнем уровне некому
прервать. Тест `TestEscalateReachesRootWhichStops` проверяет, что наблюдатель актора верхнего
уровня со стратегией `Escalate` получает `Terminated`, а ребёнок получает `Stopped`.

Приостановленный родитель о детях не решает. Пока его судьбу решает его собственный родитель,
отказ другого ребёнка откладывается и решается после возобновления; если родителя перезапустят или
остановят, дети остановятся вместе с ним, и отложенное решение не понадобится. Иначе стратегия
перезапускала бы детей родителя, которого через миг остановят. Тест
`TestSuspendedParentDefersDecisions` проверяет, что за 100 мс, пока решается судьба родителя,
второй отказавший ребёнок не перезапущен, а после возобновления — перезапущен.

Трап в обработчике `Restarting`, `Stopping` или `Stopped` отказом не считается: актор уже уходит, и
надзор ничего не может к этому добавить. Такой трап отмечается строкой
`Actor: trap in lifecycle of <имя>`. Трап внутри `Strategy.Decide` считается отказом родителя;
решение о ребёнке откладывается, пока родитель не возобновлён.

## 7. Отмена исполнителя

Задачу исполнителя можно отменить: `ActorRun.Stop` отменяет весь пул, а отменённая задача
прерывается трапом 127 в ближайшей точке переключения. Если эта точка внутри `Receive`, трап 127
пролетает через `Kernel.Try` обработчика. Отмена исполнителя не означает отказа актора: актор
ни в чём не виноват, его прервали снаружи. Поэтому трап 127 супервизору не передаётся. Письмо,
которое обрабатывалось, теряется по правилу «не более одного раза», ящик снимается с исполнителя
и, если в нём остались письма, снова ставится в очередь пула, а исполнитель завершается тем же
трапом 127. После следующего `ActorRun.Start` актор продолжает работу с прежним состоянием и
следующего письма (`TestCancelledExecutorIsNotFailure`: `Started` получен один раз, прерванное
письмо не завершено, следующее обработано).

Если бы трап 127 считался отказом, остановка пула при завершении программы превращалась бы в
лавину отказов, перезапусков и сообщений супервизорам, которые к тому же некому исполнять.

Отмена прерывает только пользовательский обработчик. Шаг жизненного цикла и надзора доводится до
конца, иначе актор застрял бы на полпути: остановка без `Stopped` и без ухода из каталога, родитель
без известия об уходе ребёнка, ребёнок, навсегда приостановленный без решения. Прерванный
обработчик `Started`, `Stopping`, `Stopped` или `Restarting` считается выполненным, и переход идёт
дальше в той же задаче (`TestCancelInStoppingFinishesStop`). Прерванные фабрика и `Decide`
повторяются: их системное письмо возвращается в начало очереди, и следующий исполнитель зовёт их
снова (`TestCancelInFactoryRetries`, `TestCancelInDecideKeepsFailure`). Затем задача прерывается
трапом 127.

Для актора со своей задачей правило то же: отмена этой задачи — не отказ и не остановка. Ящик
снимается с задачи, и при следующей работе `ActorRun` заводит актору новую задачу
(`TestCancelledDedicatedTaskStillAnswers`: после отмены задачи, ждавшей внутри `Receive`, актор
отвечает на следующий вопрос). Остановить актор можно только остановкой (`StopActor`): отмена
задачи — средство исполнителя, а не владельца актора.

## 8. Состояние, которое переживает перезапуск

`ActorCore.Actor` расширяет `Stores.Store`, но ядро подсистемы методов хранилища не вызывает: письма
не сериализуются, а `Restart` создаёт экземпляр фабрикой заново (раздел 6, `ObxActor1`). Состояние,
которое должно пережить трап, перезапуск и падение процесса, хранит модуль `ActorPersist`.

**Причина.** Перезапуск лечит отказ тем, что выбрасывает испорченное состояние. Счёт, остаток
которого выброшен вместе с ошибкой, лечить так нельзя, а `Resume` (`ObxActor2`) оставляет
состояние, но не спасает от падения процесса.

**Рассуждение.** Сохранять всё состояние после каждого письма дорого и теряет причину изменения.
Поэтому сохраняется не состояние, а *событие* — запись о том, что уже случилось («списано 30 по
операции 1»). Состояние — свёртка событий одной чистой процедурой `Apply`. Тогда:

- восстановление — та же свёртка: прочитать события и применить их по порядку;
- журнал событий — готовая история изменений: кто, когда и по какой причине;
- чтобы не сворачивать миллион событий, раз в `snapEvery` событий сохраняется *снимок* — кадр
  состояния после события с номером `seq`; восстановление берёт снимок и применяет только хвост.

Обработчик команды персистентного актора делает три шага: проверяет команду по текущему состоянию,
зовёт `Persist(c, e, cause)` и больше состояние не трогает. `Persist` кодирует событие, дописывает
его в поток с именем актора, ожидая номер `seq`, и только после удачной записи зовёт `Apply(e)`.
Восстановление идёт при обработке `Started` — и при создании, и после перезапуска: снимок, затем
события после него, затем обработчик получает `ReplayComplete`. Хранилище синхронное, точек
переключения в восстановлении нет; письма, пришедшие тем временем, ждут в ящике и приходят после
`ReplayComplete` (`TestCommandsWaitForReplay`).

У каждого события метаданные, которые журнал хранит рядом с кадром и отдаёт без разбора тела:
номер `seq`, время записи `time` (UTC, `ГГГГММДДччммсс`), причина `cause` — номер, который передал
обработчик (номер операции, номер команды), и автор `author` — отправитель команды, а без
отправителя — сам актор. Номер операции служит и повтору: если операция уже есть в состоянии,
обработчик событие не пишет, и повторная команда второй раз не списывает. Таблица выполненных
операций — часть состояния, её восстанавливает тот же `Apply`.
Таблица помнит последние N номеров (в `ObxActor3` — 16): новый номер вытесняет самый старый.
Повтор обычно приходит вскоре после первой попытки, а таблица без предела росла бы вместе со
снимком. Цена: повтор операции старше последних N спишет снова (`TestOldOperationsForgotten`);
N выбирают больше числа операций, которые могут быть «в пути» у одного клиента.

**Пример.** Счёт из `ObxActor3` (журнал в базе `Kv`):

```
	PROCEDURE (a: Account) Apply (e: ActorPersist.Event);
	BEGIN
		WITH e: Deposited DO INC(a.balance, e.sum)
		| e: Withdrawn DO DEC(a.balance, e.sum); a.ops[a.nOps MOD 16] := e.op; INC(a.nOps)
		ELSE
		END
	END Apply;

	PROCEDURE (a: Account) Handle (c: ActorCore.Context; m: Msg);
		VAR d: Deposited; w: Withdrawn; b: Balance;
	BEGIN
		WITH m: ActorPersist.ReplayComplete DO INC(starts)
		| m: Deposit DO NEW(d); d.sum := m.sum; a.Persist(c, d, 0)
		| m: Withdraw DO
			IF ~a.Done(m.op) THEN NEW(w); w.sum := m.sum; w.op := m.op; a.Persist(c, w, m.op) END
		| m: Crash DO HALT(42)
		| m: GetBalance DO NEW(b); b.n := a.balance; c.Respond(b)
		ELSE
		END
	END Handle;
```

После трапа, после перезапуска и после повторного открытия базы остаток тот же, а повтор операции 1
ничего не списывает. `ObxActor4` показывает снимки и историю с автором и причиной, `ObxActor5` —
отчёт «обороты по счетам», который читает те же потоки отдельно от счетов (CQRS) и догоняет журнал
по номеру последнего прочитанного события.

**Нарушение.** Обработчик, который меняет состояние сам, мимо `Apply`, теряет изменение при
перезапуске: восстановление его не повторит. `Apply`, который шлёт письма или пишет в журнал,
повторит их при каждом восстановлении. Трап между записью и `Apply` событие не теряет: оно уже в
журнале и применится при восстановлении (`TestTrapAfterPersistKeepsEvent`); трап до `Persist` не
оставляет следа (`TestTrapBeforePersistLosesEvent`).

Правила отказов:

| Случай | Что происходит |
|---|---|
| поток дописан другим писателем (номер не совпал) | `Append` ничего не пишет и отвечает `conflict`; `Persist` трапует `conflictTrap` (70), событие не применено; при `Restart` актор перечитывает поток вместе с чужим событием (`TestConflictFailsActor`) |
| ошибка хранилища при записи или чтении | трап `storeTrap` (71); судьбу решает супервизор — повторить (`Restart`) или остановить |
| кадр не читается (тип не найден, версия вне допустимых) | кодек отвечает `unknown`, не трапует; восстановление трапует `decodeTrap` (72), читатель `ActorPersist.Read` получает `res = corrupt` (`TestUnknownEventType`) |

Ожидание: журналы в памяти, в файле и в `Kv` отвечают сразу, поэтому `Persist` с ними синхронный и
точек переключения не имеет: пока он пишет, исполнитель занят. Медленное хранилище задерживает весь
пул; актор, которому это важно, создаётся с `Props.dedicated` (раздел 3).

Журнал может ответить и позже: `RaftJournal` подтверждает запись, только когда её зафиксировало
большинство узлов Raft, а ждать этого внутри обработчика нельзя — под `ActorSim` ту же задачу ждут и
узлы Raft. Поэтому `Persist` отдаёт событие журналу методом `ActorJournal.Journal.Submit` и не ждёт.
Ответил журнал сразу — событие применено и вызван `Persisted(c, e)` ещё до возврата из `Persist`;
ответит позже — `Persist` возвращается сразу, а применение и `Persisted` случатся, когда ответ придёт
письмом. Пока ответа нет, актор новых писем не обрабатывает: каждое пришедшее откладывается
(`ActorCore.Context.Stash`) и после ответа возвращается в начало ящика в прежнем порядке. Так
обработчик следующей команды всегда видит состояние со всеми записанными событиями. Отвечать на
команду надо в `Persisted`: там состояние уже включает событие, а `c.Sender()` — отправитель команды.
Код после `Persist` видит новое состояние только у журнала, который отвечает сразу:

```
PROCEDURE (a: Counter) Handle (c: ActorCore.Context; m: ActorCore.Msg);
	VAR e: Added;
BEGIN
	IF m IS Inc THEN NEW(e); a.Persist(c, e, 0) END	(* ответ — в Persisted *)
END Handle;

PROCEDURE (a: Counter) Persisted (c: ActorCore.Context; e: ActorPersist.Event);
	VAR r: Value;
BEGIN
	NEW(r); r.v := a.v; c.Respond(r)	(* событие записано и применено *)
END Persisted;
```

Восстановление идёт тем же путём (`ActorJournal.Journal.Replay`): письма до `ReplayComplete` тоже
откладываются. Ответ журнала приходит в ящик служебным письмом `ActorCore.Urgent`, мимо предела
`Props.capacity`: на полном ящике он не теряется. Отложенные письма входят в предел ящика, поэтому
пока актор ждёт ответа, он держит не больше `capacity` писем, а лишние становятся мёртвыми сразу
(`Actor_devBounded`).

**Свежесть перед письмом.** Воплощение виртуального актора (`fresh`, раздел 11) отвечает только по
состоянию не старше подтверждённого журнала. Перед обработкой письма оно спрашивает у журнала
последний номер своего потока (`SubmitLast`) и, если поток ушёл вперёд, читает недостающие события
(`Replay`), пока письмо ждёт в отложенных. У `RaftJournal` этот вопрос идёт через `ReadIndex`,
поэтому воплощение, отрезанное от большинства журнала, останавливается с `storeTrap`, а не отвечает
устаревшим состоянием. Цена — один запрос к журналу на письмо. Правило действует для любого ответа,
включая ответ на повтор команды: клиент не видит состояния старше последней подтверждённой записи
ключа.

Версии событий. Кадр пишет `Stores.Writer.WriteStore`: имя типа, затем поля из `Externalize`. Тип
читает свой номер версии `ReadVersion(min, max, v)` и разбирает поля по `v`. Новое поле — новая
версия: `max` растёт, старые кадры читаются по старой раскладке, а у нового поля — значение по
умолчанию. Кадр из будущей версии и кадр неизвестного типа — `unknown` (`TestVersionRule`). Тип
события нельзя переименовывать и удалять, пока в журналах есть его кадры.

**Цена.** Каждое изменение — кодирование кадра через `Stores` и запись в журнал; восстановление без
снимка проходит все события потока (замеры — раздел 12). Журнал растёт без предела: события до
снимка не удаляются, потому что история нужна аудиту. Журнал в файле (`ActorFileJournal`) —
временное хранилище до упорядоченного «ключ — значение»: один процесс на файл, `Flush` без `fsync`
(сбой питания может унести последние записи — при открытии они отбросятся как оборванный хвост),
указатель потоков в памяти, открытие читает весь файл.

Журнал устроен по образцу `Files.Directory`: абстрактный `ActorJournal.Journal`, переменные `dir`,
`stdDir` и `SetDir`. Кодек (`ActorCodec`) сменный тем же способом. Реализаций журнала три:

| | в памяти (`NewMem`) | файл «только дозапись» (`ActorFileJournal`) | база `Kv` (`ActorKvJournal`) |
|---|---|---|---|
| переживает падение процесса | нет | да, кроме записей, не дошедших до носителя | да |
| долговечность записи | — | `Flush` без `fsync` | фиксация: страницы, `Sync`, мета, `Sync` |
| транзакции | — | нет; оборванный хвост отбрасывается при открытии | да: `Append` — одна пишущая транзакция |
| процессы | один | один на файл | один на базу |
| открытие | — | читает весь файл, указатель в памяти | читает мету; поиск по дереву |
| запись события (раздел 12) | 4,7–4,9 мкс | 6,4–7,0 мкс | 1,6–1,7 мс (два `Sync`) |

Файл «только дозапись» оставлен как простая реализация для примеров и тестов без базы; там, где
событие должно пережить выключение питания, журнал — `ActorKvJournal`.

Журнал в `Kv` хранит событие под ключом `"e" + поток + 0X + номер` (8 байт, старший вперёд), снимок —
под ключом `"s" + поток`. Последний номер потока ищет курсор: `Seek` за последний возможный ключ
потока и шаг назад; отдельный ключ-счётчик не нужен — он повторял бы то, что уже есть в ключах.
Внутри `KvDb.Update` и `View` точек переключения нет, а `Sync` держит исполнитель до конца записи на
носитель: у акторов на общем пуле это ожидание всего пула. `Begin(TRUE)` другой задачи, пока пишущая
открыта, ждёт в `Tasks.Park`; пока транзакции журнала не переключаются, другая задача открытой
пишущей не застаёт. Актору, который пишет часто, дают свою задачу (`Props.dedicated`).

Два `Sync` на событие ограничивают журнал примерно 600 событиями в секунду. Поэтому `Append` из
задачи не фиксирует сам, а встаёт в очередь журнала. Первая задача в пустой очереди становится
ведущей: уступает один раз, чтобы другие писатели успели встать в очередь, и фиксирует всю очередь
одной транзакцией. Каждый запрос сверяет свой ожидаемый номер в этой транзакции: конфликт одного
потока не мешает остальным. Остальные задачи ждут в `Tasks.Park` и получают `ok` только после
фиксации своей пачки; обрыв посреди фиксации оставляет базу без всей пачки
(`TestKvGroupTorn`). Пачка собирается из задач, которые пишут одновременно: восемь акторов на пуле из
четырёх исполнителей дают пачки не больше четырёх, акторы с `Props.dedicated` — по числу акторов.
`Append` вне задачи фиксирует сам.

## 9. Адрес и каталог

Адрес — абстрактная запись `Ref` с полями `node` и `name` и четырьмя абстрактными методами:
`Post(m, sender)` доставляет письмо, `AddWatcher(w)` и `RemoveWatcher(w)` подписывают и отписывают
наблюдателя, `Stop` останавливает адресата. Локальный адрес — сам ящик (`Context` расширяет `Ref`).
`Tell` зовёт `Post`, `c.Watch` и `c.Unwatch` — `AddWatcher` и `RemoveWatcher`, `StopActor` —
`Stop`; ни одна из них не знает, где получатель. Транспорт между узлами расширяет `Ref` своим типом
(`ActorNet`, раздел 10), а `ActorCore.InitRef` заполняет его узел и имя.

Адрес ответа `Ask` — тоже `Ref`. Пока `Ask` ждёт, адрес стоит в реестре под именем `"$ask/номер"`, и
каталог находит его по этому имени, как актор; после возврата `Ask` и после отмены ждущей в нём задачи имя из каталога уходит
(`TestCancelledAskLeavesNoReplyAddress`).

Адрес по имени ищет каталог `ActorCore.dir` — по образцу `Files.dir`: абстрактный тип
`Directory` с методом `Lookup(node, name)`, переменные `dir` и `stdDir` и процедура `SetDir`.
Стандартный каталог знает только свой узел (`ActorCore.node = "local"`) и отвечает `NIL` на чужой.

Имя актора — строка из `Spawn`: `"counter"` у актора верхнего уровня, `"parent/worker"` у ребёнка,
`"$7"` у актора без имени. Два актора с одним именем трапуют в `Spawn` с кодом 24. Остановленный
актор уходит из каталога, и имя освобождается.

## 10. Акторы на разных узлах

Магазин и банк работают в разных экземплярах BlackBox. Магазину нужен остаток, банку — чтобы чужой
процесс не списал деньги, угадав имя счёта. Узел — экземпляр с корневым актором; имя узла — имя
этого корня, акторы узла — его потомки (`"bank/acct"`). Узлы связывает транспорт
`ActorNet.Transport`: «послать кадр узлу». Реализаций две: `ActorNetMem` — сеть в памяти с планом
сбоев для тестов и примеров, `ActorNetTcp` — TCP на `CommTCP` и `AsyncIO`, тех же модулях, на которых
стоит транспорт компутонов. Несколько узлов могут жить в одном процессе: письма между ними всё равно
идут через транспорт, кодируются и раскодируются, поэтому ведут себя так же, как между процессами.

```
net := ActorNetMem.NewAuto();
shop := ActorNet.New("shop", net, 1234); ActorNetMem.Add(net, shop);
bank := ActorNet.New("bank", net, 5678); ActorNetMem.Add(net, bank);
teller := ActorCore.Spawn(NIL, ActorCore.NewProps(NewTeller), "bank");
ActorNet.Export(bank, teller, cap);	(* "bank|bank|5f0c…" *)
r := ActorNet.Import(shop, cap);
res := ActorCore.Ask(r, q, 1000, reply)
```

**Адрес-пропуск.** Удалённый адрес — узел, имя и метка: первые 16 байт хеша от секрета узла-владельца
и имени. Метку выдаёт только владелец: в адресе отправителя кадра, в адресе внутри письма
(`ActorNet.WriteRef`) и явно (`Export`). Кадр с неверной меткой узел отбрасывает и считает в
`refused`; угадать имя мало — метка другого имени не подходит (`TestForgedAddressRefused`). Метка не
хранится, а вычисляется, поэтому узел, перезапущенный с тем же секретом, принимает прежние адреса.
Кадры не шифруются: метка защищает от угадывания, а не от перехвата.

**Письмо.** Отправитель пишет `Tell(r, m)` или `Ask(r, m, …)`, как локально. Письмо, которое уходит на
другой узел, наследует `ActorNet.Msg` и умеет `Write` и `Read` поверх `Stores.Writer` и `Reader`; тип
ищется по имени модуля и типа только среди загруженных модулей: кадр не загружает модулей, письмо
незагруженного типа отклоняется. Получатель сам загружает модули своих писем (например, импортом). Письмо другого типа удалённому адресу — трап
`ActorNet.notNetMsg`.

**Доставка «не более одного раза».** Кадр несёт имя узла-отправителя, номер его воплощения и
порядковый номер; получатель помнит окно последних номеров и отбрасывает повтор. Дубль сети не
исполняется дважды (`TestDuplicatesExecuteOnce`), а потерянный кадр не повторяется: `Ask` тогда
кончается тайм-аутом (`TestAskTimeout`). Повтор команды — дело приложения: команда несёт номер
операции, получатель записывает итог событием и на повтор того же номера отвечает тем же итогом, не
исполняя второй раз. `TestRetryAfterLostReply` теряет ответ, повторяет команду и проверяет, что
событие в журнале одно.

**Наблюдение и потеря узла.** `c.Watch(r)` удалённого адреса посылает узлу-владельцу просьбу; тот
наблюдает за актором сам и при остановке шлёт кадр «кончился». Если узел пропал (транспорт сообщил
`ActorNet.Lost`: в памяти — `ActorNetMem.Crash`, на TCP — обрыв соединения), каждый наблюдатель
адреса этого узла получает `Terminated` (`TestNodeLost`, `TestTcpLost`). Поле `reason` в `Terminated`
различает причины: `byStop` — актор остановлен, `byFailure` — остановлен надзором после отказа,
`byNodeLoss` — узел потерян (`TestReasonLocal`, `TestReasonRemoteStop`, `TestReasonRemoteFailure`,
`TestReasonNodeLoss`). Код, который поле не читает, не обязан его разбирать.

**Процессы.** Узел может жить в своём процессе: несколько процессов `blackbox-console`, каждый —
узел `ActorNetTcp`, обмениваются теми же кадрами, что узлы одного процесса. Адрес узла — строка
`хост:порт`; адреса всех узлов лежат в файле `nodes` каталога прогона, по строке `имя адрес`, а
свойственное роли и каталог узел получает внешними переменными. Пропуск, выданный `Export`,
доходит до соседа тоже файлом (`<роль>.cap`), поэтому узел узнаёт адреса остальных раньше, чем
пошлёт первый кадр. Сценарий `tools/test-cluster.sh` поднимает это на loopback; те же файлы и
неподвижные порты служат двум машинам.

Перезапуск процесса — новое воплощение узла. `ActorNet.New` всегда даёт ему номер 1, а окно
повторов соседа помнит номера кадров прежнего воплощения; кадры нового процесса были бы отброшены
как дубли. Поэтому узел, живущий в процессе, хранит счётчик запусков в файле и до первого кадра
зовёт `ActorNet.SetIncarnation` со следующим номером. Секрет узла не меняется, поэтому пропуски,
выданные до перезапуска, остаются верными. Убитый процесс сосед замечает как обрыв соединения:
читатель `ActorNetTcp` сообщает `ActorNet.Lost`, наблюдатели получают `Terminated` с `byNodeLoss`.
Сценарий проверяет окно напрямую: узел шлёт пачку кадров, его убивают, он поднимается снова, и
первый кадр нового воплощения должен дойти до соседа.

**Защищённый канал.** Кадры `ActorNetTcp` идут открытым текстом, и поле «от кого» не связано с
отправителем. `ActorNetTls` несёт те же кадры по TLS 1.3 со взаимной проверкой. У узла сертификат
корня кластера: ECDSA P-256, имя узла — в SAN. Доверенный — только корень; сервер требует
клиентский сертификат, поэтому узел без него рукопожатие не завершает. `Configure` загружает
корень, сертификат узла и ключ, `Attach` открывает слушатель, `SetMembers` отдаёт транспорту список
участников: имя узла и SHA-256 его сертификата.

Принимающий берёт имя узла из SAN соединения и сверяет с составом. Поле «от кого» каждого кадра
сравнивается с этим именем: верного сертификата мало, чтобы слать от чужого имени. Расхождение
рвёт соединение, считается в `forged` и уходит в журнал через процедуру `ActorNetTls.audit`;
владелец направляет её в свой файл.

**Отзыв.** Служба состава хранит отпечаток узла ключом вступления (`RaftMembership.JoinCmd`).
Имя, убранное из состава вызовом `SetMembers`, теряет входящие и исходящие соединения, наблюдатели
адресов этого узла получают `Terminated`, а новое рукопожатие отвергается. Сам `ActorNetTls` службу
не читает: список применяет владелец, поэтому транспорт не зависит от `Raft`.

**Выдача сертификатов.** `tools/cluster-certs.sh` создаёт корень и сертификаты узлов через
`openssl` (ECDSA P-256, SAN) в каталоге прогона. `tools/test-cluster.sh --tls` прогоняет все
сценарии на этих сертификатах и добавляет отрицательные случаи: сертификат чужого корня, верный
сертификат с подделанным «от кого» и узел, удалённый из состава, не принимаются. Тот же сценарий
пропускает один `Ask` через `tools/tls-proxy.py`, сохраняет байты и ищет в них известную строку
письма: в захвате только шифртекст. Цена канала — в `docs/measurements.md`.

Сценарий прогоняет в трёх процессах и сагу `ObxActor7`, и виртуальных акторов `ObxActor8`. Сага и
виртуальные акторы берут те же письма и журналы, что и примеры; виртуальные акторы получают общий
журнал из `RaftJournal`, поэтому состояние ключа переезжает на узел, принявший ключ после гибели
владельца.

**Сага.** Перевод денег между счетами на узлах A и B ведёт координатор на узле C — персистентный
актор. Шаги перевода: списать с A, зачислить на B, при отказе зачисления — вернуть на A. Каждый шаг
координатор сначала записывает событием, потом посылает команду; по тику он повторяет команду
текущего шага, а счета отвечают на повтор прежним итогом. Падение любого узла в любой точке не
меняет суммы: координатор после перезапуска читает свой журнал и продолжает с записанного шага,
счёт — свой. `ObxActor7` показывает перевод с падением координатора посреди саги.

**Проверка от зерна.** Сеть `ActorNetMem.New(seed)` теряет, задерживает, дублирует и переставляет
кадры по плану `Plan`, а жребий берёт от зерна. Исполнитель `ActorSim` обрабатывает ящики в одной
задаче по порядку прихода, без реального времени. Вместе они делают прогон функцией зерна:
`TestSagaSeeds` прогоняет сагу на 200 зёрнах с падениями узлов, проверяет, что все переводы
закончены и сумма сохранена, и прогоняет каждое зерно второй раз, сверяя число шагов, кадров и
остатки. Провал печатает зерно; `Actor_devNet.Rerun` повторяет последнее.

Случайные падения дополняет перебор. Точка саги — обработанное ящиком письмо (приём команды или
ответа, запись в журнал, отправка) или доставленный кадр; в прогоне без сбоев сети их 187.
`TestSagaEveryPoint` для каждой третьей точки роняет каждый из трёх узлов — с потерей всех кадров в
пути и без неё, — поднимает его через пять шагов и доводит сагу до конца; полный перебор (1122
прогона) входит в `Actor_devNet.Long`. Долгий прогон на 3000
зёрнах — команда `Actor_devNet.Long`.

```sh
echo 'Actor_devNet.Long' | tools/run64.sh
```

В этом прогоне нет `Ask` и тайм-аута простоя: они живут в реальном времени, и повтор шага идёт по
тику водителя.

Примеры: `ObxActor6` — два узла в одном процессе, `Ask`, отказ поддельному адресу и потеря узла;
`ObxActor7` — сага с падением узла.

## 11. Виртуальные акторы

Счёт номер 42 нужен клиенту по номеру, а не по месту: на каком узле он сейчас живёт, клиенту знать
незачем, а узел может пропасть. Виртуальный актор адресуется видом и ключом — `("acct", "42")`.
Он поднимается при первом письме на одном из узлов, состояние берёт из журнала, после простоя
уходит, а при потере узла поднимается на другом.

```
ca := ActorGrain.New(a, j); ActorGrain.Register(ca, "acct", NewAccount);
cb := ActorGrain.New(b, j); ActorGrain.Register(cb, "acct", NewAccount);
ActorGrain.HostCap(ca, cap); ActorGrain.Member(cb, cap);
ActorGrain.HostCap(cb, cap); ActorGrain.Member(ca, cap);
acct := ActorGrain.Ref(cb, "acct", "42");
c.Tell(acct, deposit)
```

**Кластер и хозяин.** `ActorGrain.New` создаёт на узле хозяина — корневой актор с именем узла — и
кластер со списком членов. Члены задаются явно: пропуск хозяина одного узла (`HostCap`) передаётся
другому (`Member`). Журнал `j` общий для всех узлов: узлы делят хранилище, как общую базу, а не
память.

**Состав из службы.** Список членов не обязательно собирать вручную. В кластере, чьи узлы входят в
службу состава Raft (руководство `Raft`, раздел «Служба состава»), `RaftGrainMembership` вступает в
неё с пропуском хозяина, продлевает аренду и читает список; каждый ответ передаётся в
`ActorGrain.ApplyMembers`. Этот вызов добавляет нового члена, оживляет вернувшегося и помечает
мёртвым пропавшего из списка; ключ из списка хранится в записи члена (`Key`). Размещение считается
по живым членам при каждой отправке, поэтому смена списка меняет владельцев без отдельного
переразмещения. Член, чья аренда не продлена, для остальных умирает так же, как узел, потерянный
через `Terminated`; ключи после этого переезжают к оставшимся.

`Member` остаётся для постоянного состава и для тестов.

**Размещение.** Владелец ключа — живой член с наибольшим весом `хеш(член, вид, ключ)`. Это
рандеву-хеш, как в protoactor-go: когда член уходит, переезжают только его ключи. Владелец
считается при каждой отправке. Письмо адресу ключа уходит хозяину владельца конвертом; хозяин
находит воплощение (ребёнка `вид.ключ`) или поднимает его и передаёт письмо с исходным отправителем,
поэтому `Respond` отвечает прямо клиенту (`TestActivateOnFirstMessage`).

**Состояние.** Воплощение — наследник `ActorGrain.Actor`, персистентный актор (раздел 8). Его поток
журнала — `вид.ключ` без имени узла (поле `stream`), поэтому на другом узле поднимается то же
состояние. Повтор команды защищает, как в саге, номер операции (`TestRetryIdempotent`).

**Пассивация.** Хозяин считает тики простоя каждого воплощения: `ActorGrain.Tick(cl)`; после `idle`
тиков без писем воплощение сохраняет снимок и останавливается. Следующее письмо поднимает его из
снимка (`TestPassivateAndReactivate`). Письмо, пришедшее хозяину после просьбы о пассивации, но до
конца воплощения, хозяин не отдаёт уходящему воплощению, а держит и после `Terminated` передаёт
новому по порядку (`TestLetterDuringPassivation`). Письма, пришедшие воплощению между трапом
конфликта журнала и его остановкой, хозяин заранее не видит: они становятся мёртвыми письмами, и
клиент повторяет их с тем же номером операции. Тик — письмо, а не таймер: в детерминированном прогоне его
даёт водитель, на живом узле — действие `Services`.

**Потеря узла.** Хозяин наблюдает хозяев других членов. `Terminated` с причиной `byNodeLoss` делает
член мёртвым, и его ключи размещаются среди живых (`TestMoveOnNodeLoss`); вернувшийся член
объявляет `Rejoin`. Письмо, которое шло к пропавшему узлу, теряется — клиент повторяет его с тем же
номером операции.

**Одно воплощение — без согласования.** Если сеть разделилась, каждый узел может считать владельцем
себя и поднять своё воплощение ключа. Перед записью воплощение виртуального актора сверяет своё
состояние с последним событием потока (`SubmitLast`) и догоняет его (`Replay`), поэтому две копии
пишут по очереди, а не мимо друг друга. Запись, пришедшая со старым номером, получает `conflict`: она
не применена, воплощение останавливается (`ActorPersist.conflictTrap`), а следующее письмо поднимает
его уже с чужим событием (`TestSplitBrainOneWriter`). Согласованный журнал — подсистема `Raft`
(`Raft/Docu/ru/Raft.md`, запись решения 0025); журнал `ActorPersist` поверх неё — `RaftJournal`
(пример `ObxRaft1`). `Raft_devGrainJournal` прогоняет виртуальные акторы на `RaftJournal` под
`ActorSim`: кластер журнала из трёх узлов, служба состава из трёх узлов, разрывы сети, падения узлов
обоих кластеров и смена списка участников. Проверки каждого шага и итога: каждая операция исполнена
один раз, подтверждённые записи ключа — одна цепь (`prev` равен предыдущему номеру), ни один ответ не
старше последней подтверждённой записи, сумма сохраняется. Барьер чтения — запись решения 0035.

`TestSeeds` прогоняет 100 зёрен: три узла, пять ключей, двадцать операций; сеть теряет и дублирует
кадры, узлы падают и поднимаются, клиент повторяет неподтверждённые операции. Каждая операция
исполнена ровно один раз, повтор зерна совпадает шаг в шаг; 2000 зёрен — `Actor_devGrain.Long`. Те же
свойства на `RaftJournal` — `Raft_devGrainJournal.TestSeeds` (100 зёрен, три ключа, четыре вклада и
четыре чтения на ключ); длинный прогон — `Raft_devGrainJournal.Long` (2000 зёрен).

Пример: `ObxActor8` — счёт на двух узлах: обращение по номеру, падение узла, продолжение на другом.

## 12. Замеры

`Actor_devBench` печатает строки `BENCH` того же вида, что `Async_devBench`. Замеры 25.11.2026
на машине разработки (Linux x86-64, три прогона подряд, `tools/test.sh Actor_devBench`) два актора, отвечающих друг
другу через `Respond`, тратят 78–82 нс на письмо, то есть 156–164 нс на обмен туда и обратно, при
одном исполнителе и при четырёх; обмен через две встречи `AsyncChan` в `docs/measurements.md`
стоит 389–483 нс. Разница объясняется переключениями: обмен задач через каналы переключает стек
четыре раза, а исполнитель обрабатывает оба ящика подряд и переключается 62 раза на тысячу писем
при одном исполнителе и 39 раз при четырёх. Выделений памяти в обмене нет.

Создание 10 000 акторов на четырёх исполнителях вместе с обработкой `Started` занимает
10,9–11,0 мкс на актор, доставка каждому по одному письму — 2,8–4,3 мкс на письмо. Профиль
(`tools/prof.sh`) отдаёт сборщику мусора больше 70 % выборок: у каждого ящика свои кольца очередей,
а адрес хранит два имени по 128 знаков.

Персистентность (`TestSlowPersist`, один исполнитель, 100 000 событий по 4 байта полезных данных,
три прогона): `Persist` в журнал в памяти — 4,7–4,9 мкс на событие (около 200 000 событий в
секунду), в файл — 6,4–7,0 мкс (около 150 000 в секунду; `Flush` после каждой записи, без `fsync`).
Журнал `Kv` в файле на диске (`TestSlowPersist`, 2000 событий): 1,6–1,7 мс на событие (около 600 в
секунду) — цена двух `Sync` на фиксацию; восстановление 2000 событий без снимка — 7 мс. Групповая
фиксация (`TestSlowKvGroupCommit`, 2048 событий, три прогона) при одном писателе ничего не меняет —
1,8–4,7 мс на событие, при 8 писателях-задачах даёт 0,25–1,4 мс, при 64 — 0,44–0,52 мс; без неё
все три случая стоили 1,8–4,0 мс. Разброс — от диска: время `Sync` на нём не постоянно.
Восстановление 100 000 событий без снимка — 0,38–0,51 с из памяти и 0,38–0,41 с из файла; со
снимком после последнего события — 6–12 мкс. Строки `BENCH persist-*` и `recover-*`.

Узлы (`Actor_devNet`, сеть в памяти, `ActorSim`): прогон саги из 8 переводов с потерями 10 %,
дублями 10 %, задержкой до 3 шагов, перестановкой и падениями узлов занимает около 3,5 мс на зерно
(`TestSagaSeeds`: 200 зёрен, каждое дважды, — 1,4 с). Долгий прогон `Actor_devNet.Long` на 3000
зёрнах — 4,5 с (1,5 мс на зерно). Список созданных узлов не хранится: он рос бы вместе с их сетями и
кадрами, и сборщик работал бы всё дольше (`TestSagaRunsFreeMemory`).

Виртуальные акторы (`Actor_devGrain.Bench`, один узел, журнал в памяти, 2000 ключей, три прогона):
первое письмо ключу с подъёмом и записью события — 200–209 мкс, письмо активному воплощению —
39–44 мкс, пассивация со снимком — 47–51 мкс на воплощение, подъём из снимка — 189–193 мкс, подъём
без снимка из 20 событий — 0,99–1,18 мс. Подъём без снимка растёт с длиной потока; снимок при
пассивации делает цену подъёма постоянной. Воплощение ищется в хеш-таблице: при 1000 ключах
письмо стоит 4 мкс, при 100000 — 5–10 мкс, а перебор списка при 100000 стоил 1,1–1,5 мс
(`docs/measurements.md`, раздел 15).

## 13. Ограничения

- Одна нить ОС: акторы исполняются по очереди, вычислительная работа одного актора задерживает
  остальных до точки переключения исполнителя (исполнитель уступает каждые 64 ящика).
- Персистентность — только у `ActorPersist.Actor`; запись в `Kv` — два `Sync` на пачку; пачка
  собирается только из задач, пишущих одновременно (раздел 8).
- Узлы: `ActorNetTcp` шлёт кадры открытым текстом и не удостоверяет поле «от кого»: держатель
  одного действующего пропуска может слать от чужого имени и двигать окно повторов этого имени.
  `ActorNetTls` шифрует те же кадры по TLS 1.3, требует клиентский сертификат, доверяет только
  корню кластера и сверяет «от кого» с SAN соединения (раздел 10). Узел принимается, пока его имя и
  отпечаток сертификата есть в составе; список применяет владелец, а сам транспорт службу состава
  не спрашивает. Списков отзыва, OCSP и смены сертификатов нет: единственный отзыв — удаление из
  состава. Оба транспорта только на Linux. Доставка «не более одного раза». `ActorGrain` сам не
  согласует: при разделении сети возможны два воплощения ключа, и без согласованного журнала писать
  могут оба. С `RaftJournal` второе не пишет и перед чтением догоняет поток (раздел 11, руководство
  `Raft`). Живость узла известна только по обрыву TCP-соединения; аренда службы состава отдельная и
  живёт в `Raft`.
- Маршрутизатор — актор одного процесса; его маршруты — заданные адреса, а пул рождает
  локальных детей. В пуле не больше `maxRoutes` (64) маршрутов;
  маршрут, остановленный надзором или `StopActor`, уходит из набора и заново не создаётся — нужен
  `SetCount`. Выбор `random` детерминирован от зерна и не служит источником энтропии. Ключ несёт
  только письмо, расширяющее `ActorRouter.Keyed`; письмо без него идёт по пустому ключу.
- Маршрутизатор не рассчитан на перезапуск надзором: `NewPool` и `NewGroup` кладут настройку в
  экземпляр, а фабрика повторяет только то, что осталось в глобалах модуля к моменту вызова.
  Перезапуск актора-маршрутизатора дал бы пустой набор и остановил детей пула; маршрутизатор
  держат корнем или под надзором с `Resume`.
- Поток — актор одного процесса. Он не хранит и не повторяет: подписчик, остановленный на
  время, пропускает опубликованное без него, а перезапуск теряет подписку. Приёмник мёртвых писем
  один, приёмник глобальный. `Publish` не ждёт доставки.
- `BecomeStacked` выделяет узел на каждое откладывание; обработчик, откладывающий на каждое
  письмо, растит стек до перезапуска.
- Окно `AllForOne` и `RestForOne` принадлежит объекту стратегии. Если один экземпляр стратегии
  отдан нескольким супервизорам, их отказы считаются в одном окне.
- Пока пул жив, планировщик не объявляет тупик прочих задач (раздел 3).
- `Ask` к самому себе из обработчика трапует с кодом 23.

```
		DeadHook = POINTER TO ABSTRACT RECORD
			(h: DeadHook) Dead (m: Msg; sender, to: Ref), NEW, ABSTRACT
		END;
		Started = POINTER TO RECORD (Msg) END;
		Stopping = POINTER TO RECORD (Msg) END;
		Stopped = POINTER TO RECORD (Msg) END;
		Restarting = POINTER TO RECORD (Msg) END;
		ReceiveTimeout = POINTER TO RECORD (Msg) END;
		Terminated = POINTER TO RECORD (Msg)
			who-: Ref;
			reason-: INTEGER
		END;

		Context = POINTER TO LIMITED RECORD (Ref)
			dedicated-: BOOLEAN;
			(c: Context) Post (m: Msg; sender: Ref);
			(c: Context) AddWatcher (w: Ref);
			(c: Context) RemoveWatcher (w: Ref);
			(c: Context) Stop;
			(c: Context) Tell (to: Ref; m: Msg), NEW;
			(c: Context) Sender (): Ref, NEW;
			(c: Context) Respond (m: Msg), NEW;
			(c: Context) Parent (): Ref, NEW;
			(c: Context) Watch (r: Ref), NEW;
			(c: Context) Unwatch (r: Ref), NEW;
			(c: Context) SetReceiveTimeout (ms: LONGINT), NEW;
			(c: Context) Become (b: Behavior), NEW;
			(c: Context) BecomeStacked (b: Behavior), NEW;
			(c: Context) Unbecome, NEW;
			(c: Context) Stash, NEW;
			(c: Context) Unstash, NEW
		END;

	VAR
		dispatcher-: Dispatcher;
		dir-, stdDir-: Directory;
		node-: Name;
		deadLetters-: LONGINT;

	PROCEDURE NewProps (f: Factory): Props;
	PROCEDURE Spawn (parent: Context; p: Props; IN name: ARRAY OF CHAR): Ref;
	PROCEDURE Tell (to: Ref; m: Msg);
	PROCEDURE StopActor (r: Ref);
	PROCEDURE Ask (to: Ref; m: Msg; ms: LONGINT; OUT reply: Msg): INTEGER;
	PROCEDURE InitRef (r: Ref; IN node, name: ARRAY OF CHAR);
	PROCEDURE Terminate (w, who: Ref; reason: INTEGER);
	PROCEDURE SetDispatcher (d: Dispatcher);
	PROCEDURE SetDir (d: Directory);
	PROCEDURE SetDeadHook (h: DeadHook);

END ActorCore.
```

`Context` — ящик актора, контекст его обработчика и локальный адрес. Модуль мониторов не берёт:
операции над ящиком между двумя точками переключения неделимы. Методы `Dispatcher`, кроме
`Schedule`, служат модулю исполнителей (`ActorRun`) и работают только у исполнителя, установленного
`SetDispatcher`: у любого другого `Dispatcher` они трапуют с кодом 20.

**PROCEDURE (r: Ref) Post (m: Msg; sender: Ref)**
Пред: `m # NIL` — трап 20.
Пост: `m` в ящике адресата или учтено как мёртвое письмо; отправитель не ждёт. Ящик полон, когда
писем в нём вместе с отложенными не меньше `capacity > 0`; письмо `Urgent` идёт мимо предела.

**TYPE Urgent**
Служебное письмо: в ящик идёт мимо предела `Props.capacity`. Им отвечают актору, который без этого
ответа из ожидания не выйдет (ответ журнала стойкому актору).

**TYPE DeadHook**
Приёмник мёртвых писем. `ActorCore` зовёт `Dead` на каждое письмо, не дошедшее до адресата;
`to` — адресат, `NIL` — адреса нет. Трап внутри `Dead` перехватывается и не становится отказом
актора, пославшего мёртвое письмо; мёртвое письмо, возникшее во время вызова, повторно не
считается, поэтому приёмник, ставящий письмо остановленному актору, не замыкает круг.

**PROCEDURE SetDeadHook (h: DeadHook)**
Пост: каждое мёртвое письмо с этого момента передаётся `h.Dead`; `h = NIL` — приёмника нет.

**PROCEDURE (r: Ref) AddWatcher (w: Ref)**
Зовёт `c.Watch` и `Ask`.
Пред: `w # NIL` — трап 20.
Пост: после остановки `r` наблюдатель `w` получит `Terminated` с `who = r` один раз; `r` уже
остановлен — получит сразу; повторный вызов с тем же `w` ничего не добавляет.

**PROCEDURE (r: Ref) RemoveWatcher (w: Ref)**
Пред: `w # NIL` — трап 20.
Пост: `w` не наблюдает `r`.

**PROCEDURE (r: Ref) Stop**
Пост: `r` получит остановку раньше своих пользовательских писем; остановленный `r` не меняется.

У адреса ответа `Ask` методы `AddWatcher`, `RemoveWatcher` и `Stop` ничего не делают.

**PROCEDURE (a: Actor) Receive (c: Context; m: Msg)**
Пред: зовёт только исполнитель, один вызов на актор за раз.
Пост: письмо обработано; трап — отказ актора, кроме трапа 127 (раздел 7).

**PROCEDURE (b: Behavior) Receive (a: Actor; c: Context; m: Msg)**
То же, что `Actor.Receive`, после `c.Become(b)`; `a` — экземпляр актора.

**PROCEDURE (s: Strategy) Decide (child: Ref; reason: INTEGER; VAR st: Stats): INTEGER**
Пред: ребёнок `child` отказал с трапом `reason`; `st` — его счёт отказов.
Пост: директива; значение вне `Resume..StopRest` исполняется как `Stop`, `Resume` ребёнку без
экземпляра — тоже; `RestartAll` и `StopAll` действуют на всех детей родителя, `RestartRest` и
`StopRest` — на отказавшего и рождённых после него; трап — отказ родителя, решение отложено до его
возобновления.

**PROCEDURE (d: Dispatcher) Schedule (c: Context)**
Пред: у `c` есть работа, `c` не стоит у исполнителя.
Пост: исполнитель зовёт `d.Process(c, ...)`, пока тот возвращает `TRUE`.

**PROCEDURE (d: Dispatcher) Process (c: Context; max: INTEGER): BOOLEAN**
Пред: `d` — установленный исполнитель — трап 20; `c # NIL` — трап 21; `c` стоит у исполнителя и
не в обработке — трап 22; `max > 0` — трап 23; вызов из задачи — трап 24.
Пост: обработаны все системные сообщения и не более `max` пользовательских; `TRUE` — работа
осталась, `c` по-прежнему у исполнителя; `FALSE` — работы нет, `c` снят с исполнителя. Отмена
задачи исполнителя — трап 127 после того, как шаг жизненного цикла доведён до конца, ящик снят с
исполнителя и, если в нём есть работа, снова отдан `Schedule` (раздел 7).

**PROCEDURE (d: Dispatcher) Pending (c: Context): BOOLEAN**
Пред: `d` — установленный исполнитель — трап 20.
Пост: `c` стоит у исполнителя.

**PROCEDURE (d: Dispatcher) Stopped (c: Context): BOOLEAN**
Пред: `d` — установленный исполнитель — трап 20.
Пост: `c` остановлен; письма ему — мёртвые.

**PROCEDURE (d: Dispatcher) Host (c: Context): ANYPTR**
Пред: `d` — установленный исполнитель — трап 20.
Пост: данные исполнителя при ящике `c` (`ActorRun` хранит здесь собственную задачу актора); `NIL`
— нет.

**PROCEDURE (d: Dispatcher) SetHost (c: Context; h: ANYPTR)**
Пред: `d` — установленный исполнитель — трап 20.
Пост: `d.Host(c) = h`.

**PROCEDURE (d: Dispatcher) Live (): INTEGER**
Пред: `d` — установленный исполнитель — трап 20.
Пост: число неостановленных акторов.

**PROCEDURE (d: Dispatcher) StopRoots**
Пред: `d` — установленный исполнитель — трап 20.
Пост: каждый неостановленный актор без родителя получил остановку.

**PROCEDURE (d: Directory) Lookup (IN node, name: ARRAY OF CHAR): Ref**
Пост: адрес актора или ждущего адреса ответа `name` на узле `node`; `NIL` — неизвестен.
Стандартный каталог знает только `node = ActorCore.node`.

**PROCEDURE (c: Context) Tell (to: Ref; m: Msg)**
Пред: `to # NIL` — трап 20; `m # NIL` — трап 21.
Пост: `m` послано `to`, отправитель — `c`.

**PROCEDURE (c: Context) Sender (): Ref**
Пост: отправитель письма в обработке; `NIL` — без отправителя.

**PROCEDURE (c: Context) Respond (m: Msg)**
Пред: `m # NIL` — трап 20.
Пост: `m` послано отправителю письма в обработке; без отправителя — мёртвое письмо.

**PROCEDURE (c: Context) Parent (): Ref**
Пост: адрес родителя; `NIL` — у `c` нет родителя.

**PROCEDURE (c: Context) Watch (r: Ref)**
Пред: `r # NIL` — трап 20.
Пост: после остановки `r` обработчик `c` получит `Terminated` с `who = r` один раз; повторный
`Watch` того же `r` ничего не добавляет; `r` уже остановлен — получит сразу. Остановка `c` снимает
его подписки.

**PROCEDURE (c: Context) Unwatch (r: Ref)**
Пред: `r # NIL` — трап 20.
Пост: `c` не получит `Terminated` от `r`, даже посланное раньше `Unwatch`.

**PROCEDURE (c: Context) SetReceiveTimeout (ms: LONGINT)**
Пред: вызов из обработчика `c` — трап 20.
Пост: `ms > 0` — после `ms` мс без пользовательских писем обработчик получит `ReceiveTimeout`
один раз, следующий отсчёт начнёт следующее письмо; тайм-аут не обгоняет ждущие письма и после
`Resume` отсчитывается заново; `ms <= 0` — тайм-аута нет. Перезапуск снимает тайм-аут.

**PROCEDURE (c: Context) Become (b: Behavior)**
Пред: вызов из обработчика `c` — трап 20.
Пост: следующие письма обрабатывает `b.Receive`; `b = NIL` и перезапуск возвращают `Actor.Receive`.

**PROCEDURE (c: Context) BecomeStacked (b: Behavior)**
Пред: вызов из обработчика `c` — трап 20.
Пост: текущее поведение отложено; следующие письма обрабатывает `b.Receive`; перезапуск и
остановка очищают стек.

**PROCEDURE (c: Context) Unbecome**
Пред: вызов из обработчика `c` — трап 20.
Пост: текущее поведение отброшено, восстановлено последнее отложенное; пустой стек возвращает
`Actor.Receive`.

**PROCEDURE (c: Context) Stash**
Отложить письмо в обработке: обработчик сейчас не может его принять.
Пред: вызов из обработчика `c`, обрабатывающего пользовательское письмо (не шаг жизненного цикла) —
трап 20.
Пост: письмо и его отправитель отложены; в предел ящика `capacity` они входят по-прежнему.
Перезапуск возвращает отложенные в начало ящика, остановка делает их мёртвыми письмами.

**PROCEDURE (c: Context) Unstash**
Пред: вызов из обработчика `c` — трап 20.
Пост: отложенные письма — в начале ящика в порядке `Stash`, с прежними отправителями.

**PROCEDURE NewProps (f: Factory): Props**
Пред: `f # NIL` — трап 20.
Пост: описание с фабрикой `f`, ящик без предела, исполнитель пула, без стратегии.

**PROCEDURE Spawn (parent: Context; p: Props; IN name: ARRAY OF CHAR): Ref**
Пред: `p # NIL` и `p.new # NIL` — трап 20; `p.capacity >= 0` — трап 21; исполнитель установлен —
трап 22; `parent = NIL` или `parent` работает — трап 23; имя свободно — трап 24; полное имя
короче `nameLen` — трап 25; фабрика не возвращает `NIL` — трап 26. Трап фабрики — трап
вызывающего.
Пост: новый актор, ребёнок `parent` (`NIL` — корня); имя — `name`, у ребёнка — «имя родителя/
name», пустое `name` — `"$номер"`; первым обработчик получит `Started`.

**PROCEDURE Tell (to: Ref; m: Msg)**
Пред: `to # NIL` — трап 20; `m # NIL` — трап 21.
Пост: `m` послано `to` без отправителя; ожидания нет.

**PROCEDURE StopActor (r: Ref)**
Пред: `r # NIL` — трап 20.
Пост: `r.Stop`.

**PROCEDURE Ask (to: Ref; m: Msg; ms: LONGINT; OUT reply: Msg): INTEGER**
Ждёт ответа.
Пред: вызов из задачи — трап 20; `to # NIL` — трап 21; `m # NIL` — трап 22; вызов не из
обработчика самого `to` — трап 23; отмена задачи — трап 127.
Пост: `ok` — `reply` — первое письмо на адрес ответа; `timedOut` — за `ms` мс ответа нет; `dead`
— вопрос стал мёртвым письмом или `to` остановился, не ответив. Кроме `ok`, `reply = NIL`.

**PROCEDURE InitRef (r: Ref; IN node, name: ARRAY OF CHAR)**
Для модулей транспорта.
Пред: `r # NIL` — трап 20; `node` и `name` короче `nameLen` — трап 21.
Пост: `r.node = node`, `r.name = name`.

**PROCEDURE Terminate (w, who: Ref; reason: INTEGER)**
Для модулей транспорта: известить наблюдателя `w` о конце адреса `who`, который не является
локальным ящиком (удалённый адрес).
Пред: `w # NIL` — трап 20; `who # NIL` — 21; `reason` — `byStop`, `byFailure` или `byNodeLoss` — 22.
Пост: `w` получит `Terminated` с полями `who` и `reason`.

**PROCEDURE SetDispatcher (d: Dispatcher)**
Для модулей исполнителей.
Пред: `d # NIL` — трап 20.
Пост: `dispatcher = d`; методы `Dispatcher`, кроме `Schedule`, работают только у `d`.

**PROCEDURE SetDir (d: Directory)**
Пред: `d # NIL` — трап 20.
Пост: `dir = d`; первый установленный каталог остаётся в `stdDir`.

### 15.2. ActorSup

```
DEFINITION ActorSup;

	IMPORT ActorCore;

	PROCEDURE NewOneForOne (directive, max: INTEGER; withinMs: LONGINT): ActorCore.Strategy;
	PROCEDURE NewAllForOne (directive, max: INTEGER; withinMs: LONGINT): ActorCore.Strategy;
	PROCEDURE NewRestForOne (directive, max: INTEGER; withinMs: LONGINT): ActorCore.Strategy;

END ActorSup.
```

**PROCEDURE NewOneForOne (directive, max: INTEGER; withinMs: LONGINT): ActorCore.Strategy**
Пред: `directive` — `Resume`, `Restart`, `Stop` или `Escalate` — трап 20; `max >= 0` — трап 21;
`withinMs > 0` — трап 22.
Пост: стратегия отвечает на отказ ребёнка директивой `directive`; для `Restart` — `Stop`, если
это отказ с номером `max + 1` за `withinMs` мс от первого отказа окна.

**PROCEDURE NewAllForOne (directive, max: INTEGER; withinMs: LONGINT): ActorCore.Strategy**
Пред: как у `NewOneForOne` — трапы 20, 21, 22.
Пост: для `Restart` — `RestartAll`, пока отказы всех детей укладываются в `max` за окно
`withinMs` мс, иначе `StopAll`; для `Stop` — `StopAll`; `Resume` и `Escalate` — без изменений.
Окно считает отказы всех детей вместе.

**PROCEDURE NewRestForOne (directive, max: INTEGER; withinMs: LONGINT): ActorCore.Strategy**
Пред: как у `NewOneForOne` — трапы 20, 21, 22.
Пост: как у `NewAllForOne`, но группа — отказавший ребёнок и рождённые после него; её директивы —
`RestartRest` и `StopRest`.

### 15.3. ActorRun

```
DEFINITION ActorRun;

	VAR
		n-: INTEGER;

	PROCEDURE Start (k: INTEGER);
	PROCEDURE Stop;
	PROCEDURE Shutdown;

END ActorRun.
```

`n` — число исполнителей пула; 0 — пул остановлен.

**PROCEDURE Start (k: INTEGER)**
Пред: `0 < k <= 64` — трап 20; пул остановлен — трап 21.
Пост: пул из `k` исполнителей установлен в `ActorCore`; ящики, ждавшие в очереди, обслуживаются.

**PROCEDURE Stop**
Пост: задачи пула отменены (трап 127 в их точке переключения); ящики с работой ждут следующего
`Start`. Собственные задачи акторов не затронуты.

**PROCEDURE Shutdown**
Общая остановка.
Пред: вызов не из задачи исполнителя — трап 20.
Пост: каждый актор без родителя получил остановку, все акторы остановлены (дети раньше родителей);
задачи пула завершились сами, без отмены; собственные задачи акторов завершаются вместе с
акторами; `n = 0`. Актор, не остановившийся за 5 с, остаётся, а задачи пула тогда отменяются.

### 15.4. ActorJournal

```
DEFINITION ActorJournal;

	CONST
		ok = 0; conflict = 1; absent = 2; failed = 3; corrupt = 4;
		nameLen = 128;

	TYPE
		Bytes = POINTER TO ARRAY OF BYTE;
		Name = ARRAY 128 OF CHAR;

		Meta = RECORD
			seq, time, cause: LONGINT;
			author: Name
		END;

		Sink = POINTER TO ABSTRACT RECORD
			(s: Sink) Event (IN m: Meta; IN body: ARRAY OF BYTE; len: INTEGER): BOOLEAN, NEW, ABSTRACT
		END;

		Journal = POINTER TO ABSTRACT RECORD
			(j: Journal) Last (IN stream: ARRAY OF CHAR): LONGINT, NEW, ABSTRACT;
			(j: Journal) Append (IN stream: ARRAY OF CHAR; expected: LONGINT; IN m: Meta;
				IN body: ARRAY OF BYTE; len: INTEGER; OUT res: INTEGER), NEW, ABSTRACT;
			(j: Journal) Read (IN stream: ARRAY OF CHAR; from: LONGINT; s: Sink; OUT res: INTEGER), NEW, ABSTRACT;
			(j: Journal) SaveSnapshot (IN stream: ARRAY OF CHAR; seq: LONGINT;
				IN data: ARRAY OF BYTE; len: INTEGER; OUT res: INTEGER), NEW, ABSTRACT;
			(j: Journal) LoadSnapshot (IN stream: ARRAY OF CHAR; OUT seq: LONGINT;
				OUT data: Bytes; OUT len, res: INTEGER), NEW, ABSTRACT;
			(j: Journal) Close, NEW, EMPTY;
			(j: Journal) Submit (IN stream: ARRAY OF CHAR; expected: LONGINT; IN m: Meta;
				IN body: ARRAY OF BYTE; len: INTEGER; r: Request), NEW, EXTENSIBLE;
			(j: Journal) SubmitSnapshot (IN stream: ARRAY OF CHAR; seq: LONGINT;
				IN data: ARRAY OF BYTE; len: INTEGER; r: Request), NEW, EXTENSIBLE;
			(j: Journal) SubmitLast (IN stream: ARRAY OF CHAR; r: Request), NEW, EXTENSIBLE;
			(j: Journal) Replay (IN stream: ARRAY OF CHAR; r: Request), NEW, EXTENSIBLE
		END;

		Request = POINTER TO ABSTRACT RECORD (Sink)
			(r: Request) Event (IN m: Meta; IN body: ARRAY OF BYTE; len: INTEGER): BOOLEAN, EXTENSIBLE;
			(r: Request) Snapshot (seq: LONGINT; IN data: ARRAY OF BYTE; len: INTEGER), NEW, EMPTY;
			(r: Request) Last (seq: LONGINT), NEW, EMPTY;
			(r: Request) Done (res: INTEGER), NEW, ABSTRACT
		END;

	VAR
		dir-, stdDir-: Journal;

	PROCEDURE NewMem (): Journal;
	PROCEDURE SetDir (j: Journal);
	PROCEDURE Now (): LONGINT;

END ActorJournal.
```

Журнал — набор потоков; поток — события с номерами 1, 2, 3 … без пропусков. `res`: `ok`; `conflict`
— ожидаемый номер не совпал; `absent` — снимка нет; `failed` — ошибка среды; `corrupt` — данные не
читаются.

`Submit`, `SubmitSnapshot`, `SubmitLast` и `Replay` — те же `Append`, `SaveSnapshot`, `Last` и чтение
снимка с событиями, но итог приходит в запрос `r` методом `Done(res)` — ровно один раз, внутри вызова
или позже, из чужого контекста; `Replay` отдаёт снимок в `r.Snapshot` и события в `r.Event` до
`Done`, `SubmitLast` — номер в `r.Last`. По умолчанию
они зовут синхронные методы и отвечают сразу, поэтому синхронному журналу их не переопределяют;
журнал с ответом позже (`RaftJournal.Client`) переопределяет. Пред: `r # NIL` — трап 23 (`Replay` — 20).

`Meta` — метаданные события: номер `seq`, время записи `time` (UTC, `ГГГГММДДччммсс`), причина
`cause`, автор `author`. Журнал хранит их отдельно от тела и отдаёт без разбора тела.

**PROCEDURE (s: Sink) Event (IN m: Meta; IN body: ARRAY OF BYTE; len: INTEGER): BOOLEAN**
Получатель событий `Read`. `body[0 .. len-1]` — кадр события. Пост: `FALSE` — чтение прекращается.

**PROCEDURE (j: Journal) Last (IN stream: ARRAY OF CHAR): LONGINT**
Пост: номер последнего события потока; 0 — поток пуст.

**PROCEDURE (j: Journal) Append (IN stream; expected: LONGINT; IN m: Meta; IN body; len: INTEGER; OUT res: INTEGER)**
Пред: `stream # ""` — трап 20; `m.seq = expected + 1` — 21; `0 <= len <= LEN(body)` — 22.
Пост: `res = ok` — событие записано с номером `m.seq`; `res = conflict` — `Last(stream) # expected`,
ничего не записано; иначе `failed`.

**PROCEDURE (j: Journal) Read (IN stream; from: LONGINT; s: Sink; OUT res: INTEGER)**
Пред: `s # NIL` — трап 20. Пост: события с номерами `>= from` отданы `s.Event` по возрастанию номера,
пока `s.Event` отвечает `TRUE`; `res = ok` или ошибка журнала.

**PROCEDURE (j: Journal) SaveSnapshot (IN stream; seq: LONGINT; IN data; len: INTEGER; OUT res: INTEGER)**
Пред: `0 < seq <= Last(stream)` — трап 20; `0 <= len <= LEN(data)` — 21.
Пост: `res = ok` — снимок `data[0 .. len-1]` после события `seq` заменил прежний снимок потока.
События до снимка остаются.

**PROCEDURE (j: Journal) LoadSnapshot (IN stream; OUT seq: LONGINT; OUT data: Bytes; OUT len, res: INTEGER)**
Пост: `res = ok` — последний снимок потока, `seq` — номер события, после которого он снят;
`res = absent` — снимка нет, `seq = 0`.

**PROCEDURE (j: Journal) Close**
Пост: ресурсы журнала освобождены; после `Close` журнал не используется.

**PROCEDURE NewMem (): Journal**
Пост: новый пустой журнал в памяти.

**PROCEDURE SetDir (j: Journal)**
Пред: `j # NIL` — трап 20. Пост: `dir = j`; первый установленный журнал остаётся в `stdDir`. При
загрузке модуля `dir` — журнал в памяти.

**PROCEDURE Now (): LONGINT**
Пост: текущее время UTC в виде `ГГГГММДДччммсс`.

### 15.6. ActorPersist

```
DEFINITION ActorPersist;

	IMPORT Stores, ActorCore, ActorJournal;

	CONST
		conflictTrap = 70; storeTrap = 71; decodeTrap = 72;
		mutNoStash = 0; mutNoFresh = 1; mutKeepOnConflict = 2; mutNoCatchUp = 3;

	TYPE
		Event = POINTER TO ABSTRACT RECORD (Stores.Store)
			meta-: ActorJournal.Meta
		END;

		ReplayComplete = POINTER TO RECORD (ActorCore.Msg) END;

		Actor = POINTER TO ABSTRACT RECORD (ActorCore.Actor)
			seq-: LONGINT;
			fresh: BOOLEAN;
			snapEvery: INTEGER;
			journal: ActorJournal.Journal;
			stream: ActorCore.Name;
			(a: Actor) Apply (e: Event), NEW, ABSTRACT;
			(a: Actor) Handle (c: ActorCore.Context; m: ActorCore.Msg), NEW, ABSTRACT;
			(a: Actor) Persisted (c: ActorCore.Context; e: Event), NEW, EMPTY;
			(a: Actor) Busy (): BOOLEAN, NEW;
			(a: Actor) Snapshot (): Stores.Store, NEW, EXTENSIBLE;
			(a: Actor) Restore (s: Stores.Store), NEW, EMPTY;
			(a: Actor) Receive (c: ActorCore.Context; m: ActorCore.Msg), EXTENSIBLE;
			(a: Actor) SaveSnapshot (c: ActorCore.Context), NEW;
			(a: Actor) Persist (c: ActorCore.Context; e: Event; cause: LONGINT), NEW
		END;

		Visitor = POINTER TO ABSTRACT RECORD
			(v: Visitor) Visit (e: Event), NEW, ABSTRACT
		END;

	VAR
		mutations: SET;

	PROCEDURE Read (j: ActorJournal.Journal; IN stream: ARRAY OF CHAR; from: LONGINT; v: Visitor;
		OUT last: LONGINT; OUT res: INTEGER);

END ActorPersist.
```

Поток актора — `stream`, а если оно пустое, — имя ящика (`c.name`); виртуальные акторы задают
`stream`, чтобы поток не зависел от узла (раздел 11). `journal = NIL` — `ActorJournal.dir`. `seq` — номер последнего
применённого события. `snapEvery > 0` — снимок после каждого события с номером, кратным `snapEvery`;
0 — только по `SaveSnapshot`. `fresh = TRUE` — перед каждым пользовательским письмом актор сверяет
`seq` с последним номером потока (`SubmitLast`) и дочитывает недостающие события, поэтому ответ не
старше подтверждённой записи. Виртуальные акторы включают это поле.

**PROCEDURE (a: Actor) Apply (e: Event)**
Пост: состояние `a` изменено событием `e`. Без писем, записей и трапов.

**PROCEDURE (a: Actor) Handle (c: ActorCore.Context; m: ActorCore.Msg)**
Обработчик команд. Первым получает `ReplayComplete`; `Started` не получает.

**PROCEDURE (a: Actor) Persisted (c: ActorCore.Context; e: Event)**
После записи: `e` записано, применено, `seq = e.meta.seq`; `c.Sender()` — отправитель письма, обработчик
которого записал `e`. Здесь отвечают на команду; можно звать `Persist`.

**PROCEDURE (a: Actor) Busy (): BOOLEAN**
Пост: идёт восстановление или запись без ответа журнала — пользовательские письма откладываются.

`mutations` — только для тестов: `mutNoStash` — письмо во время записи обрабатывается сразу;
`mutNoFresh` — сверка свежести пропускается; `mutNoCatchUp` — отставание видно, но догона нет;
`mutKeepOnConflict` — событие с несовпавшим номером применяется и подтверждается.

**PROCEDURE (a: Actor) Snapshot (): Stores.Store**
Пост: объект, кадр которого — снимок состояния. По умолчанию — сам актор (его `Externalize`).

**PROCEDURE (a: Actor) Restore (s: Stores.Store)**
Пост: состояние `a` взято из `s` — объекта, прочитанного из снимка. Вызывается при восстановлении,
когда `seq` уже равен номеру снимка.

**PROCEDURE (a: Actor) Receive (c: ActorCore.Context; m: ActorCore.Msg)**
На `Started`: `Replay` журнала — снимок потока (если есть) — `Restore`, затем события после него —
`Apply`, затем `Handle(c, ReplayComplete)`. Ошибка журнала — трап `storeTrap`, нечитаемый кадр —
`decodeTrap`. Ответ журнала — применение события и `Persisted`. Пока `Busy`, пользовательские письма
откладываются (`Stash`) и возвращаются после ответа; `Stopping`, `Stopped`, `Restarting` — сразу в
`Handle`. Остальные письма — `Handle`.

**PROCEDURE (a: Actor) SaveSnapshot (c: ActorCore.Context)**
Пред: вызов из обработчика `a` (не проверяется); `a.seq > 0` — трап 20.
Пост: снимок состояния после события `seq` отдан журналу (`SubmitSnapshot`) после ждущих записей;
отказ журнала — трап `storeTrap`.

**PROCEDURE (a: Actor) Persist (c: ActorCore.Context; e: Event; cause: LONGINT)**
Пред: вызов из обработчика `a` (не проверяется); `e # NIL` — трап 20.
Пост: `e` отдано журналу (`Submit`) с номером `seq + 1` плюс число событий, ещё ждущих ответа,
автором — отправителем команды (без отправителя — сам актор), причиной `cause` и временем записи. По
ответу журнала: `e.meta` заполнено, `Apply(e)`, `seq` увеличен, `Persisted(c, e)`; снимок, если `seq`
кратен `snapEvery`. Журнал ответил сразу — всё это до возврата. Поток дописан другим — трап
`conflictTrap`; ошибка хранилища или неизвестный итог — `storeTrap`; в обоих случаях `e` не
применено. Точек переключения нет.

**PROCEDURE (v: Visitor) Visit (e: Event)**
Пост: событие `e` (метаданные — в `e.meta`) учтено.

**PROCEDURE Read (j; IN stream; from: LONGINT; v: Visitor; OUT last: LONGINT; OUT res: INTEGER)**
Чтение потока для стороны чтения (CQRS).
Пред: `j # NIL` — трап 20; `v # NIL` — 21.
Пост: события с номерами `>= from` разобраны и отданы `v.Visit` по порядку; `res = ok` — `last` —
номер последнего отданного (`from - 1`, если новых нет); иначе `res` — ошибка журнала или `corrupt`
(кадр не читается), `last` — номер последнего удачного.

### 15.9. ActorNet

```
DEFINITION ActorNet;

	IMPORT Stores, ActorCore;

	CONST
		notNetMsg = 30;

	TYPE
		Msg = POINTER TO ABSTRACT RECORD (ActorCore.Msg)
			(m: Msg) Write- (VAR wr: Stores.Writer), NEW, EMPTY;
			(m: Msg) Read- (VAR rd: Stores.Reader), NEW, EMPTY
		END;

		Node = POINTER TO LIMITED RECORD
			name-: ActorCore.Name;
			up-: BOOLEAN;
			incarnation-: LONGINT;
			sent-, received-, duplicates-, refused-: LONGINT
		END;

		Transport = POINTER TO ABSTRACT RECORD
			(t: Transport) Send (IN from, to: ARRAY OF CHAR; IN frame: ARRAY OF BYTE; len: INTEGER), NEW, ABSTRACT
		END;

	PROCEDURE New (IN name: ARRAY OF CHAR; t: Transport; secret: LONGINT): Node;
	PROCEDURE Down (n: Node);
	PROCEDURE Up (n: Node);
	PROCEDURE SetIncarnation (n: Node; inc: LONGINT);
	PROCEDURE Export (n: Node; r: ActorCore.Ref; OUT cap: ARRAY OF CHAR);
	PROCEDURE Import (n: Node; IN cap: ARRAY OF CHAR): ActorCore.Ref;
	PROCEDURE WriteRef (VAR wr: Stores.Writer; r: ActorCore.Ref);
	PROCEDURE ReadRef (VAR rd: Stores.Reader; OUT r: ActorCore.Ref);
	PROCEDURE WriteMsg (VAR wr: Stores.Writer; m: Msg);
	PROCEDURE ReadMsg (VAR rd: Stores.Reader; OUT m: Msg);
	PROCEDURE Deliver (n: Node; IN frame: ARRAY OF BYTE; len: INTEGER);
	PROCEDURE Lost (n: Node; IN node: ARRAY OF CHAR);

END ActorNet.
```

**TYPE Msg** — письмо, которое может уйти на другой узел. `Write` пишет поля, `Read` читает их в том
же порядке; адреса в полях — `WriteRef` и `ReadRef`. Тип письма должен быть доступен по имени
(`Kernel.ThisType`) на узле-получателе; письмо неизвестного типа отклоняется (`refused`).

**TYPE Node** — узел: `name` — имя корневого актора, `up` — узел поднят, `incarnation` растёт при
каждом `Up`; счётчики кадров: послано, принято, отброшено как повтор, отклонено (неверная метка,
битый кадр, неизвестный тип).

**TYPE Transport** — транспорт кадров. `Send` отдаёт кадр `frame[0 .. len - 1]` от узла `from` узлу
`to`; кадр может пропасть. Принятый кадр транспорт передаёт `Deliver` узла-адресата, о потере связи
с узлом сообщает `Lost`.

**PROCEDURE New (IN name: ARRAY OF CHAR; t: Transport; secret: LONGINT): Node**
Пред: `name # ""`, без `"/"`, короче `ActorCore.nameLen` — трап 20; `t # NIL` — 21.
Пост: узел поднят, воплощение 1. Метки адресов узла зависят от `secret`. Корневой актор узла создаёт
пользователь: `Spawn(NIL, …, name)`.

**PROCEDURE Down (n: Node)**
Пост: узел упал: кадры от него и к нему пропадают, его память о кадрах и наблюдениях стёрта, корневой
актор остановлен. Журналы в хранилище не затронуты.

**PROCEDURE Up (n: Node)**
Пред: узел упал, его корневой актор остановлен — трап 20.
Пост: узел поднят с новым воплощением; корневой актор создаёт пользователь заново.

**PROCEDURE SetIncarnation (n: Node; inc: LONGINT)**
Для узла, перезапущенного в новом процессе. Окно повторов соседа помнит номера кадров прежнего
воплощения, поэтому кадры процесса, который начинает счёт с 1, были бы отброшены как дубли;
владелец хранит счётчик сам и поднимает его при каждом запуске процесса.
Пред: `n # NIL` — трап 20; `inc >= n.incarnation` — 21.
Пост: `n.incarnation = inc`, счётчик кадров `n.seq = 0`; метки адресов не меняются, потому что
зависят только от секрета.

**PROCEDURE Export (n: Node; r: ActorCore.Ref; OUT cap: ARRAY OF CHAR)**
Пред: `r` — локальный адрес — трап 20.
Пост: `cap` — пропуск `"узел|имя|метка"` к `r` для передачи другому узлу вне писем.

**PROCEDURE Import (n: Node; IN cap: ARRAY OF CHAR): ActorCore.Ref**
Пост: адрес по пропуску для писем с узла `n`; `NIL` — пропуск не разобран. Метку проверяет
узел-владелец при доставке.

**PROCEDURE WriteRef (VAR wr: Stores.Writer; r: ActorCore.Ref)**
**PROCEDURE ReadRef (VAR rd: Stores.Reader; OUT r: ActorCore.Ref)**
Пред: вызов из `Msg.Write` и `Msg.Read` — трап 20 у `WriteRef`.
Пост: адрес записан пропуском узла, который кодирует кадр, и прочитан: свой адрес с верной меткой —
локальный актор, с неверной — `NIL`, чужой — удалённый адрес.

**PROCEDURE WriteMsg (VAR wr: Stores.Writer; m: Msg)**
**PROCEDURE ReadMsg (VAR rd: Stores.Reader; OUT m: Msg)**
Письмо внутри письма (поле конверта): `WriteMsg` пишет имя модуля и типа и поля `m` (или признак
`NIL`), `ReadMsg` читает его; тип ищется только среди загруженных модулей, не найден — `m = NIL` и
`rd.cancelled`. Письмо удобно делать последним полем.

**PROCEDURE Deliver (n: Node; IN frame: ARRAY OF BYTE; len: INTEGER)**
Для транспорта. Пост: повтор, чужая метка и битый кадр отброшены и посчитаны; иначе письмо в ящике
адресата.

**PROCEDURE Lost (n: Node; IN node: ARRAY OF CHAR)**
Для транспорта. Пост: каждый наблюдатель адреса на `node` получил `Terminated`; наблюдения по
просьбам `node` сняты.

**PROCEDURE Crash (net: Net; IN name: ARRAY OF CHAR)** — Пред: узел есть в сети — трап 20. Пост:

**PROCEDURE Attach (net: Net; n: ActorNet.Node)** — Пред: узла ещё нет — трап 20. Пост: принятые
кадры идут узлу `n` (созданному на `net`).
**PROCEDURE Address (net: Net; OUT adr: ARRAY OF CHAR)** — Пост: адрес, который слушает `net`.
**PROCEDURE Peer (net: Net; IN name, adr: ARRAY OF CHAR)** — Пост: кадры узлу `name` идут на `adr`.
**PROCEDURE Close (net: Net)** — Пост: слушатель и соединения закрыты, задачи завершаются; другие
узлы видят обрыв.

### 15.13. ActorNetTls

```
DEFINITION ActorNetTls;

	IMPORT ActorCore, ActorNet;

	CONST
		badRoot = 1; badCertificate = 2; badKey = 3;

	TYPE
		Fingerprint = ARRAY 32 OF BYTE;
		Member = RECORD
			name: ActorCore.Name;
			fp: Fingerprint
		END;
		Net = POINTER TO LIMITED RECORD (ActorNet.Transport) END;

	VAR
		audit: PROCEDURE (IN text: ARRAY OF CHAR);

	PROCEDURE New (IN listen: ARRAY OF CHAR; OUT net: Net; OUT res: INTEGER);
	PROCEDURE (net: Net) Configure (IN rootFile, certFile, keyFile: ARRAY OF CHAR; OUT res: INTEGER);
	PROCEDURE (net: Net) ConfigureNoClient (IN rootFile, certFile, keyFile: ARRAY OF CHAR; OUT res: INTEGER);
	PROCEDURE Attach (net: Net; n: ActorNet.Node);
	PROCEDURE Address (net: Net; OUT adr: ARRAY OF CHAR);
	PROCEDURE Peer (net: Net; IN name, adr: ARRAY OF CHAR);
	PROCEDURE (net: Net) SetMembers (IN m: ARRAY OF Member; n: INTEGER);
	PROCEDURE Close (net: Net);
	PROCEDURE (net: Net) Stats (OUT sent, read, refused, forged, rejected, revoked: LONGINT);
	PROCEDURE (net: Net) Detail (OUT accepts, acceptFails, hsOk, hsFail, hsStarted, accTicks: LONGINT);
	PROCEDURE (net: Net) Counts (OUT links, readers: INTEGER);
	PROCEDURE (net: Net) ConnAlive (): BOOLEAN;
	PROCEDURE (net: Net) HandshakeState (): INTEGER;
	PROCEDURE (net: Net) PeersText (OUT text: ARRAY OF CHAR);

END ActorNetTls.
```

Транспорт на TLS 1.3 со взаимной проверкой, только Linux. Кадр уходит по соединению, открытому
первым письмом; `Send` не ждёт сети. Первое сообщение соединения — не имя: имя второй стороны берётся
из SAN её сертификата. Рукопожатие с сертификатом чужого корня, без клиентского сертификата или с
именем вне состава не завершается. Кадр, у которого «от кого» не совпадает с этим именем,
отбрасывается, считается в `forged`, передаётся в `audit`, а соединение закрывается. Обрыв даёт
`ActorNet.Lost`; кадры в очереди оборванного соединения пропадают. Читатель ждёт сокет
кооперативно, поэтому главному циклу не нужно опрашивать дескриптор.

**PROCEDURE New (IN listen: ARRAY OF CHAR; OUT net: Net; OUT res: INTEGER)** — Пост:
`res = CommStreams.done` — `net` создан; `listen` — адрес, на котором он будет слушать после
`Attach`.
**PROCEDURE (net: Net) Configure (IN rootFile, certFile, keyFile: ARRAY OF CHAR; OUT res: INTEGER)** —
Пред: `net # NIL` — 20. Пост: `res = 0` — корень, сертификат узла и ключ загружены, сервер требует
клиентский сертификат; иначе `badRoot`, `badCertificate` или `badKey`.
**PROCEDURE (net: Net) ConfigureNoClient (IN rootFile, certFile, keyFile: ARRAY OF CHAR; OUT
res: INTEGER)** — то же без клиентского сертификата; сервер, принявший такой узел, рвёт рукопожатие.
**PROCEDURE Attach (net: Net; n: ActorNet.Node)** — Пред: `net`, `n` не NIL — 20; узла ещё нет —
21; `Configure` вызван — 22. Пост: слушатель открыт, принятые кадры идут узлу `n`.
**PROCEDURE Address (net: Net; OUT adr: ARRAY OF CHAR)** — Пост: адрес, переданный в `New`.
**PROCEDURE Peer (net: Net; IN name, adr: ARRAY OF CHAR)** — Пост: кадры узлу `name` идут на `adr`;
соединение сверяет сертификат `name` со списком участников.
**PROCEDURE (net: Net) SetMembers (IN m: ARRAY OF Member; n: INTEGER)** — Пред:
`0 <= n <= 64` — 20. Пост: состав — `m[0 .. n-1]`; соединения с именами вне его закрыты, их
наблюдатели получили `Terminated`, новые рукопожатия от них отвергаются.
**PROCEDURE Close (net: Net)** — Пост: слушатель и соединения закрыты; другие узлы видят обрыв.
**PROCEDURE (net: Net) Stats**, **Detail**, **Counts**, **ConnAlive**, **HandshakeState**,
**PeersText** — счётчики кадров, отказов, рукопожатий и открытых соединений, состояние нижнего
TCP-соединения, шаг рукопожатия и строка на каждого соседа — для диагностики.
**VAR audit** — вызывается строкой, когда «от кого» кадра не совпало с сертификатом; NIL — записи
нет.

### 15.14. ActorGrain

```
DEFINITION ActorGrain;

	IMPORT ActorCore, ActorJournal, ActorPersist, ActorNet;

	CONST
		maxMembers = 32;
		capLen = 256;
		notNetMsg = 31;
		mutNoApply = 0;
		mutKeepAlive = 1;
		mutNoRejoin = 2;

	TYPE
		Actor = POINTER TO ABSTRACT RECORD (ActorPersist.Actor)
			kind-, key-: ActorCore.Name;
			(a: Actor) Receive (c: ActorCore.Context; m: ActorCore.Msg)
		END;

		Cluster = POINTER TO LIMITED RECORD
			node-: ActorNet.Node;
			journal-: ActorJournal.Journal;
			idle: INTEGER;
			activations-, passivations-: LONGINT
		END;

		MemberInfo = RECORD
			id: INTEGER;
			cap: ARRAY capLen OF CHAR;
			key: ActorJournal.Bytes;
			alive: BOOLEAN
		END;

	PROCEDURE New (n: ActorNet.Node; j: ActorJournal.Journal): Cluster;
	PROCEDURE HostRef (cl: Cluster): ActorCore.Ref;
	PROCEDURE HostCap (cl: Cluster; OUT cap: ARRAY OF CHAR);
	PROCEDURE Member (cl: Cluster; IN cap: ARRAY OF CHAR);
	PROCEDURE ApplyMembers (cl: Cluster; IN list: ARRAY OF MemberInfo; n: INTEGER);
	PROCEDURE Key (cl: Cluster; IN name: ARRAY OF CHAR): ActorJournal.Bytes;
	PROCEDURE Rejoin (cl: Cluster; IN name: ARRAY OF CHAR);
	PROCEDURE Leave (cl: Cluster; IN name: ARRAY OF CHAR);
	PROCEDURE Alive (cl: Cluster; IN name: ARRAY OF CHAR): BOOLEAN;
	PROCEDURE Members (cl: Cluster): INTEGER;
	PROCEDURE AliveCount (cl: Cluster): INTEGER;
	PROCEDURE MemberName (cl: Cluster; i: INTEGER; OUT name: ActorCore.Name);
	PROCEDURE Register (cl: Cluster; IN kind: ARRAY OF CHAR; f: ActorCore.Factory);
	PROCEDURE Ref (cl: Cluster; IN kind, key: ARRAY OF CHAR): ActorCore.Ref;
	PROCEDURE Owner (cl: Cluster; IN kind, key: ARRAY OF CHAR; OUT node: ARRAY OF CHAR);
	PROCEDURE Tick (cl: Cluster);

END ActorGrain.
```

**TYPE Actor** — воплощение. `kind` и `key` заданы до `Started`; поток журнала — `kind.key`, журнал —
журнал кластера. `Receive` перехватывает письмо пассивации (снимок, если есть события, и
остановка), прочие отдаёт `ActorPersist`.

**TYPE Cluster** — кластер узла: `idle` — тиков простоя до пассивации (0 — без пассивации),
счётчики поднятых и пассивированных воплощений.

**PROCEDURE New (n: ActorNet.Node; j: ActorJournal.Journal): Cluster** — Пред: `n # NIL` — 20;
`j # NIL` — 21; корневого актора с именем узла нет — 22. Пост: хозяин создан, член — сам узел.
**PROCEDURE HostRef (cl: Cluster): ActorCore.Ref** — Пост: адрес хозяина узла.
**PROCEDURE HostCap (cl: Cluster; OUT cap: ARRAY OF CHAR)** — Пост: пропуск хозяина для `Member`
других узлов.
**PROCEDURE ApplyMembers (cl: Cluster; IN list: ARRAY OF MemberInfo; n: INTEGER)** — Пред: каждый
`list[i].cap` разбирается `ActorNet.Import`; не проверяется. Пост: члены `cl` — записи
`list[0 .. n-1]` с `alive = TRUE`; новый член добавлен, вернувшийся снова живой, пропавший помечен
мёртвым; `id` и `key` записаны в запись члена. Размещение считается по живым членам при следующей
отправке.
**PROCEDURE Key (cl: Cluster; IN name: ARRAY OF CHAR): ActorJournal.Bytes** — Пост: открытый ключ
члена из последнего `ApplyMembers`; `NIL` — такого члена нет. Ключ не проверяется.
**PROCEDURE Members (cl: Cluster): INTEGER** — Пост: число членов, включая сам узел.
**PROCEDURE AliveCount (cl: Cluster): INTEGER** — Пост: число живых членов, включая сам узел.
**PROCEDURE MemberName (cl: Cluster; i: INTEGER; OUT name: ActorCore.Name)** — Пост: имя члена `i`
(0 — сам узел); пусто — вне списка.
**PROCEDURE Member (cl: Cluster; IN cap: ARRAY OF CHAR)** — Пред: пропуск разобран — 20; мест меньше
`maxMembers` — 21. Пост: член живой, его хозяин наблюдается.
**PROCEDURE Rejoin (cl: Cluster; IN name: ARRAY OF CHAR)** — Пред: член есть — 20. Пост: член живой
и снова наблюдается.
**PROCEDURE Leave (cl: Cluster; IN name: ARRAY OF CHAR)** — Пред: член есть и это не сам узел — 20.
Пост: член считается мёртвым (решение снаружи).
**PROCEDURE Alive (cl: Cluster; IN name: ARRAY OF CHAR): BOOLEAN** — Пост: член живой, по мнению `cl`.
**PROCEDURE Register (cl: Cluster; IN kind: ARRAY OF CHAR; f: ActorCore.Factory)** — Пред:
`kind # ""`, без `.` и `/` — 20; `f # NIL` — 21. Пост: воплощения вида создаёт `f`; `f`, вернувшая не
`Actor`, — воплощение не поднимается.
**PROCEDURE Ref (cl: Cluster; IN kind, key: ARRAY OF CHAR): ActorCore.Ref** — Пред: `key # ""`, без
`/` — 20. Пост: `Tell` и `Ask` к адресу идут воплощению у текущего владельца; письмо не
`ActorNet.Msg` — трап `notNetMsg`; `Watch` не действует.
**PROCEDURE Owner (cl: Cluster; IN kind, key: ARRAY OF CHAR; OUT node: ARRAY OF CHAR)** — Пост: узел-
владелец среди живых членов, по мнению `cl`.
**PROCEDURE Tick (cl: Cluster)** — Пост: воплощения узла без писем `idle` тиков подряд пассивируются.

```
DEFINITION ActorRouter;

	IMPORT ActorCore;

	CONST
		roundRobin = 0; random = 1; broadcast = 2; consistentHash = 3;

	TYPE
		Keyed = POINTER TO EXTENSIBLE RECORD (ActorCore.Msg)
```

**PROCEDURE NewPool (factory: ActorCore.Factory; n: INTEGER; kind: INTEGER; seed: LONGINT; strategy: ActorCore.Strategy): ActorCore.Ref**
Пред: `factory # NIL` — трап 20; `0 < n <= maxRoutes` — трап 21; `kind` — один из четырёх —
трап 22. Пост: корневой маршрутизатор с `n` детьми фабрики `factory`; отказ ребёнка решает
`strategy`.

**PROCEDURE NewGroup (IN refs: ARRAY OF ActorCore.Ref; kind: INTEGER; seed: LONGINT): ActorCore.Ref**
Пред: `0 < LEN(refs) <= maxRoutes` — трап 20; каждый адрес не `NIL` — трап 22; `kind` — один из

Пред: `r # NIL` — трап 20; `0 < LEN(refs) <= maxRoutes` — трап 21; каждый адрес не `NIL` —
трап 22. Пост: маршрутизатор получает письмо, заменяющее набор маршрутов в порядке ящика.

**PROCEDURE SetCount (r: ActorCore.Ref; n: INTEGER)**
Пред: `r # NIL` — трап 20. Пост: маршрутизатор-пул получает письмо о `n` маршрутах; группа его
игнорирует.

**PROCEDURE SetKind (r: ActorCore.Ref; kind: INTEGER)**
Пред: `r # NIL` — трап 20. Пост: маршрутизатор получает письмо о смене правила; недопустимое
правило ничего не меняет.

### 15.17. ActorEvent

```
DEFINITION ActorEvent;

	IMPORT ActorCore;

	TYPE
		Filter = POINTER TO ABSTRACT RECORD
			(f: Filter) Match (m: ActorCore.Msg): BOOLEAN, NEW, ABSTRACT
		END;

		DeadLetter = POINTER TO RECORD (ActorCore.Msg)
			m-: ActorCore.Msg;
			to-, sender-: ActorCore.Ref
		END;

	PROCEDURE New (): ActorCore.Ref;
	PROCEDURE Subscribe (s, r: ActorCore.Ref; f: Filter);
	PROCEDURE Unsubscribe (s, r: ActorCore.Ref);
	PROCEDURE Publish (s: ActorCore.Ref; m: ActorCore.Msg);
	PROCEDURE SetDefault (s: ActorCore.Ref);
	PROCEDURE Default (): ActorCore.Ref;

END ActorEvent.
```

**TYPE Filter** — предикат подписки; `Match` отвечает, идти ли письмо подписчику.

**TYPE DeadLetter** — событие мёртвого письма: `m` — исходное письмо, `to` — адресат (`NIL` —
нет), `sender` — отправитель исходного письма.

**PROCEDURE New (): ActorCore.Ref** — Пост: новый актор-поток без подписчиков; приёмником мёртвых
писем он не становится.

**PROCEDURE Subscribe (s, r: ActorCore.Ref; f: Filter)** — Пред: `s # NIL` — трап 20; `r # NIL` —
трап 21. Пост: поток получает письмо: `r` подписан с `f` (`NIL` — все письма); повторная подписка
того же `r` заменяет предикат.

**PROCEDURE Unsubscribe (s, r: ActorCore.Ref)** — Пред: `s # NIL` — трап 20; `r # NIL` — трап 21.
Пост: поток получает письмо: `r` больше не подписан.

**PROCEDURE Publish (s: ActorCore.Ref; m: ActorCore.Msg)** — Пред: `s # NIL` — трап 20; `m # NIL` —
трап 21. Пост: `m` ушло потоку; подписчики получат его в порядке ящика потока, с отправителем
письма потоку. Поток остановлен — `m` мёртвое.

**PROCEDURE SetDefault (s: ActorCore.Ref)** — Пост: поток `s` — приёмник мёртвых писем;
`s = NIL` — приёмника нет.

**PROCEDURE Default (): ActorCore.Ref** — Пост: поток, поставленный приёмником мёртвых писем;
`NIL` — нет.

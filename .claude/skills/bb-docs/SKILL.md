# Документация active_bb

Документ читает программист, который знает Component Pascal и не знает этой работы. Он должен понять,
зачем вещь нужна, как ею пользоваться и что случится, если нарушить правило, — не открывая код. Текст
сухого справочника этой цели не достигает: в нём есть определения, но нет повода и рассуждения. Образцы
тона — книги Вирта и заметки Дейкстры: простая речь, точные утверждения, пример на каждую мысль.

## 1. Жанры

У документа один жанр. Жанр определяет, насколько развёрнуто писать.

| Жанр | Файлы | Как писать |
|---|---|---|
| Сообщение о языке | `Docu/ru/Active-CP-Lang.md`, `Docu/Active-CP-Lang.md` | Кратко, как Component Pascal Language Report: синтаксис в EBNF, затем смысл, затем ограничения. Примеры малы. Рассуждений о реализации нет. |
| Руководство модуля или подсистемы | `Docu/*/Tasks.md`, `Docu/*/Async.md`, `<Sub>/Docu/**` | Глава книги (раздел 2). В конце — справочная часть «Интерфейс» (раздел 4). |
| Устройство реализации | `docs/implementation.md` | Рассказ по ходу работы системы: что происходит с задачей от создания до конца, кто кого вызывает и почему так. Имена модулей и процедур, без номеров строк. |
| Сборка и запуск | `docs/building.md` | Действующие команды и их смысл. Каждая команда существует в `tools/` и выполнена перед коммитом. |
| Замеры | `docs/measurements.md` | Что мерили, чем, при каких условиях, числа, команда воспроизведения. Вывод из чисел — словами. |
| План | `docs/kernel-plan.md` | Что ядро делает сейчас и что следует изменить. Выполненное удаляется. |

## 2. Руководство как глава книги

Порядок раздела:

1. Повод. Задача или случай, из которого видно, зачем вещь нужна. Не определение.
2. Рассуждение. Как вещь решает задачу; термин вводится здесь, в тот момент, когда он понадобился.
3. Пример. Полный модуль `MODULE … END`, который компилируется. Перед коммитом его компилируют.
4. Нарушение. Что произойдёт, если правило не соблюсти: какой трап, какая ошибка компилятора, какое
   зависание. Правило без разобранного нарушения читатель не запомнит.
5. Цена и границы. Число стоит внутри предложения, с условием замера и сравнением, понятным без таблицы.

Сплошной текст, абзацами. Список — только для перечислимого: операции, состояния, директивы, номера
трапов. Таблица — когда у перечислимого несколько свойств. Рассуждение в список не превращают.

Пример. Справочная запись:

> Между двумя точками переключения задача исполняется неделимо. Точки переключения: `Yield`, `Sleep`,
> `Park`, `Join`, вход в занятый монитор, `AWAIT`.

То же главой книги:

> Две задачи увеличивают общий счётчик: каждая читает его, прибавляет единицу и записывает обратно. В
> системе с нитями ОС одно из двух прибавлений иногда теряется, потому что нить могут прервать между
> чтением и записью. Здесь этого не случится. Задачу никто не прерывает; она отдаёт процессор сама и
> только в известных местах: когда зовёт `Yield`, `Sleep`, `Park` или `Join`, когда входит в занятый
> монитор и когда ждёт условия в `AWAIT`. Эти места называются точками переключения. Всё, что задача
> делает между двумя такими точками, другие задачи видят как одно неделимое действие — поэтому счётчик
> из примера обходится без монитора.

## 3. Язык

- Настоящее время и только итоговое состояние. Документ не рассказывает, как код менялся: нет «раньше»,
  «теперь», «было», «исправлено», «добавлено», номеров этапов и заданий, хешей коммитов, «взято из …».
  Отличия от исходного BlackBox перечислены в одном разделе `README.md` и в приложении сообщения о языке.
- Один термин на понятие. Термины сообщения о языке: задача, монитор, исключающая процедура, точка
  переключения, точка уступки. Синонимы («процесс», «нить», «корутина», «точка ожидания») не заменяют
  термин. Новый термин определяется при первом употреблении и выделяется курсивом один раз.
- Предложение несёт одну мысль. Подлежащее названо: «планировщик выбирает задачу», а не «выбирается
  задача». Длинное объяснение чередуется с коротким выводом.
- Утверждение о свойстве идёт с причиной или следствием: «…поэтому счётчик обходится без монитора».
- Без канцелярита: «является», «представляет собой», «осуществляет», «в рамках», «данный», «следует
  отметить». Без оценок: «удобно», «просто», «мощный», «элегантно», «ключевой», «уникальный».
- Без примет машинного текста: полужирный в середине фраз; списки вида «**Название:** пояснение»;
  «не X, а Y» и «не только X, но и Y» чаще одного раза на раздел; перечисление из трёх по привычке;
  хвост после запятой, который ничего не сообщает («…, обеспечивая надёжность»); таблица из двух строк
  вместо фразы; заголовок, под которым только заголовки; концовка «таким образом».
- Оговорку и ограничение не выбрасывают ради краткости: они часть определения. Но говорят один раз.
- Ссылка на код — имя модуля и процедуры (`Tasks.Step`). Локальных путей вида `/home/…` нет.

## 4. Справочная часть «Интерфейс»

Форма документации модулей BlackBox. Стоит в конце руководства.

1. Блок `DEFINITION Модуль; … END Модуль.` — точно по экспорту кода: константы, типы, процедуры.
2. По каждой экспортной процедуре: одна-две фразы, что она делает, затем строки

   ```
   Пред: t # NIL — 20
   Пред: вызов из задачи — 21
   Пост: t ждёт в состоянии Ready
   ```

   Номер — из `ASSERT` или `HALT` в коде (20–59 предусловия, 60–99 постусловия, 100–120 инварианты,
   127 — отмена). Условие, которое код не проверяет, помечается «не проверяется». Предусловий, которых
   нет в коде, не выдумывают. В английской версии — `Pre` и `Post`.

## 5. Факты

Живость — в языке, а не в фактах.

- Каждое утверждение сверено с кодом: сигнатура, номер трапа, константа, состояние, переход.
- Правило языка либо проверяет компилятор (тогда назван номер ошибки), либо оно помечено фразой
  «Компилятор этого не проверяет».
- Число приводится с условием замера (архитектура, одна нить, загрузка машины, число прогонов) и с
  командой из `tools/`, которая его воспроизводит. Невоспроизводимое число не приводят. Оценка названа
  оценкой.
- Таблицы одного замера в разных документах согласованы; руководство ссылается на
  `docs/measurements.md`, а не копирует таблицу.

## 6. Две версии

Руководства и сообщение о языке существуют на русском (`…/Docu/ru/`) и английском (`…/Docu/`). Английская
версия — точный перевод русской, тем же стилем; правятся в одном коммите. Заголовки, нумерованные
правила и блоки кода совпадают по числу.

## 7. Порядок работы

1. Прочитать код, который описывает документ, и выписать, что изменилось.
2. Для руководства — найти повод каждого раздела: задачу, которую читатель узнает.
3. Написать по порядку раздела 2. Справочную часть править по экспорту кода.
4. Прочитать вслух: где спотыкаешься — переписать; где скучно — выбросить.
5. Пройти проверки.

## 8. Проверки перед коммитом

```sh
# история и запрещённые слова (осмысленные вхождения допустимы — просмотреть каждое)
git grep -n -i -E "этап|шаг [0-9]|раньше|вынесен|было |теперь |применено|исчезл|точк[аиу] ожидания" -- '*.md'
git grep -n -i -E "является|представляет собой|следует отметить|в рамках|данн(ый|ая|ое)" -- '*.md'
# локальные пути
git grep -n "/home/" -- '*.md'
```

- Каждый полный пример из документа скомпилирован временным модулем (`tools/go64.sh`); временные файлы
  удалены.
- Каждая команда из `docs/building.md` существует и выполнена.
- `DEFINITION` совпадает с экспортом: сравнить с `PROCEDURE …*` и `…-` в исходнике.
- Ссылки между документами не битые; новая страница внесена в карту документации `README.md` и в
  таблицу «Documentation» в `AGENTS.md`.
- Изменены только `.md`; если документ вскрыл ошибку в коде, она исправляется отдельным коммитом с
  тестом.
